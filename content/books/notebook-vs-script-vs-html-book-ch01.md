# 第 1 章 · 三种形态：它们根本不是同一层的东西

> **全书结构（24 章 · 三篇）**
>
> - **篇一 · 形态与原理（1–8 章）**：Notebook / Python 脚本 / HTML 三种形态的本质差异、执行模型、可复现性、交互性、版本控制、工程化与数据连接
> - **篇二 · 平台与选型（9–16 章）**：AI Native Notebook 的演进、四类版图、五层架构、AI 层两种范式、AI 能力层、协作发布与主流平台横向对比
> - **篇三 · 自建与落地（17–24 章）**：基于 marimo 开源引擎自建内部平台的产品架构、技术架构、差距清单、AI 接入、投入与 ROI



## 1.1 先各给一句话定义

| 形态 | 一句话定义 | 核心动词 |
|---|---|---|
| **Notebook** | 一个**保留运行时状态、可分段执行、代码与输出共存**的交互式文档 | **探索** |
| **Python 脚本** | 一个**从头到尾一次性执行、执行完状态即消失**的纯文本文件 | **固化** |
| **HTML** | 一个**不含计算能力（或只有前端 JS）的呈现文档** | **交付** |

注意定义里的关键词——**Notebook 的定义里有「状态」，脚本的定义里有「一次性」，HTML 的定义里没有「计算」**。这三个词决定了后面所有差异。

## 1.2 ★ 三层模型：厨房台面 / 工厂产线 / 成品橱窗

一个被广泛引用的比喻是：**Notebook 是厨房的操作台（kitchen counter），不是工厂流水线（factory line）**。把它扩展成三层：

```
┌──────────────────────────────────────────────────────┐
│ ③ 交付层：HTML / 静态报告 / App                       │
│    成品橱窗 —— 给人看、给人用，不负责生产              │
├──────────────────────────────────────────────────────┤
│ ② 执行层：Python 脚本 / 流水线任务                     │
│    工厂产线 —— 无人值守、可重复、可调度、可测试        │
├──────────────────────────────────────────────────────┤
│ ① 生产层（探索）：Notebook                             │
│    厨房台面 —— 边做边尝、随时改、看得见每一步          │
└──────────────────────────────────────────────────────┘
```

**三层不是竞争关系，是一条管线**：在台面上试出配方（Notebook）→ 确认后上产线批量生产（脚本）→ 装盒放进橱窗（HTML）。

> 绝大多数「X 和 Y 哪个好」的争论，都是因为**把不同层的东西当成同类在比**。问「HTML 能不能替代 Notebook」等于问「橱窗能不能替代厨房」。

## 1.3 六维差异总表（全书地图）

| 维度 | **Notebook** | **Python 脚本** | **HTML** |
|---|---|---|---|
| **执行模型** | 分段执行，内核常驻 | 一次性从头到尾 | 不执行（或前端 JS） |
| **状态** | ★有状态（Jupyter）/ 响应式 DAG（marimo） | 无残留状态，进程结束即消失 | 无状态 |
| **可复现** | 中（Jupyter 差、marimo 好） | ★**最强** | ★**最弱**（快照，无法重跑） |
| **交互性** | ★控件触发**真实重算** | 仅 CLI 参数 | 前端过滤/切换，**不重算后端** |
| **版本控制** | .ipynb 差（JSON+output）、.py 好 | ★天然 Git 友好 | 生成物，不入版本库 |
| **工程化** | 弱～中（需 papermill/nbconvert 辅助） | ★最强（pytest/CI/import/调度） | 无 |
| **数据连接** | ★可连数仓、下推、TB 级 | ★同样可，是生产管线主力 | 不连接（除非 JS 调 API） |
| **分发阅读** | 需要环境/平台 | 需要环境 | ★**一个链接就能看** |
| **典型产出** | 分析过程 + 结论 | 可调度任务、库、服务 | 报告、看板、文档 |

## 1.4 三个比喻，帮助团队对齐认知

| 比喻 | 含义 | 用于说服谁 |
|---|---|---|
| **厨房台面 vs 工厂产线** | 台面上可以随手试、随时改；产线必须稳定可重复 | 想把 notebook 直接挂 cron 的人 |
| **草稿 vs 出版物** | Notebook 是带演算过程的草稿纸；HTML 是排版好的出版物 | 问「为什么不直接给我 HTML」的业务方 |
| **实验记录本 vs SOP** | Notebook 记录「我怎么发现这个结论」；脚本是「照着做就能复现」的 SOP | 要交接、要审计的场景 |

> 第三个比喻对合规场景特别有用：**实验记录本的价值在于可追溯，SOP 的价值在于可执行**。两者都要有，不能互相替代。

## 1.5 为什么这个区分在今天更重要了

AI 普及后，三种形态的**可信度**出现了巨大分化：

| 形态 | AI 生成它时，内容可信吗 |
|---|---|
| **HTML 报告** | ★**不可信**——模型生成的是「文本」，没有任何环节保证数字真被算过 |
| **Python 脚本** | 可信——跑一遍就知道，跑不通就是错的 |
| **Notebook** | ★**最可信**——每段代码都在 kernel 里跑过，输出是真实执行结果 |

> 这是本书最重要的现实判断：**当 AI 参与产出时，「能不能重跑」决定了「能不能相信」**。HTML 无法重跑，脚本能重跑但看不见过程，Notebook 既能重跑又能看见过程。

## 1.7 本章要点

- 一句话定义：**Notebook=探索（有状态）／脚本=固化（一次性）／HTML=交付（无计算）**。
- ★**三层模型：厨房台面（Notebook）→ 工厂产线（脚本）→ 成品橱窗（HTML）**，是管线不是竞争。
- 六维总表：可复现 **脚本最强 > Notebook > HTML 最弱**；分发 **HTML 最强**；探索 **Notebook 最强**；工程化 **脚本最强**。
- 三个比喻（台面/产线、草稿/出版物、实验记录本/SOP）用于团队对齐。
- ★**AI 时代的新判据：能不能重跑 = 能不能相信**。HTML 无法重跑 → 风险最高；Notebook 能跑且看得见过程 → 最可信。
