# MRL-SPANN：把套娃前缀塞进 SSD 倒排，单机扛万亿多模态检索

## TL;DR

万亿级多模态向量检索一直卡在一个死结上：**装在内存里的索引（HNSW/IVF-PQ）撑不到千亿，扛得住千亿的图索引（DiskANN）构建成本高得离谱**。MRL-SPANN 的解法是把最近两年两件独立的技术拼起来——**Matryoshka 表征（MRL）**的前缀可截断特性，和 **SPANN** 的 SSD 常驻倒排结构。它让同一个 embedding 的前 64 维当「粗召回指纹」、前 1024 维当「精排距离」，质心只存前缀、posting list 顺序布局，最终在一台 64GB 内存 + 16 块 NVMe 的机器上做到：

- **1 万亿条 2048 维多模态向量**，总索引体积约 41TB（含 SS 侧向表）
- **P99 延迟 9.4ms**，平均 3.1ms
- **recall@10 = 0.951**（比同等压缩率的 IVF-PQ 高 6 个点，比 DiskANN 图索引低 1.2 个点）
- **构建成本为 DiskANN 的 1/8**——因为只需要跑 k-means，不需要构图

---

## 一、研究背景：三条路线各自的死穴

| 路线 | 代表 | 内存/存储形态 | 卡在哪 |
|------|------|--------------|--------|
| 图索引 | HNSW、DiskANN/Vamana | 内存 / SSD 常驻图 | 图构建 O(N log N) 且难以增量；万亿级构建成本不可接受 |
| 倒排 + 量化 | IVF-PQ（Faiss） | 内存常驻 posting list | 压缩到 64B 以下时 recall 崩塌；内存撑不住千亿 |
| SSD 倒排 | SPANN | 质心内存 + posting list 落 SSD | 原方案只用 int8/PQ，**没法和现在的 Matryoshka embedding 配合** |

论文的出发点是一个很朴素的观察：2024 年之后新出的嵌入模型（包括 CLIP 的诸多后继者）几乎都支持 **Matryoshka 训练**——向量的前 d' 维就是一个完整可用的低维表征。但**没有任何检索系统真的把这件事用起来**：大家都完整地存一个高维向量，然后在压缩环节再想办法。这等于把模型免费赠送的「多档精度解码器」扔掉了。

---

## 二、核心方法：三个改动，各自解决一个成本项

### 2.1 质心只存 64 维前缀

k-means 聚类的目的是判断「查询落在哪个胞腔」，并不需要完整 2048 维的空间分辨率。论文发现：**用前 64 维前缀聚类，胞腔分配的一致性与全维度相差不到 1.5%**，但质心表从

```
1e6 质心 × 2048 维 × 4B = 8.2GB   →   1e6 × 64 × 4B = 256MB
```

内存占用降了两个数量级。省下来的内存全部交给...nothing——本来就不够用的 posting 缓存和热点向量。

### 2.2 posting list 按距离排序 + 连续布局

SPANN 原方案的精髓在于把 SSD 的随机读变成顺序读。MRL-SPANN 加了一点：**同一胞腔内，向量按「到质心的距离」升序存储**，查询时对 δ 附近的桶做带宽感知截断；同时把前 64 维前缀紧邻主数据存放，让「读一条 → 算粗距离」完全在一页 SSD 里完成，不需要二次寻址。论文给出的吞吐对比：

| 读取方式 | 单块 NVMe 吞吐 | 有效带宽利用 |
|---------|---------------|------------------|
| 纯随机 4K 读 | ~1.2 GB/s | 低 |
| 排序后顺序读 | ~11.4 GB/s | 接近满带宽 |

这就是「9.4ms P99」里最大的一块收益来源。

### 2.3 双档距离：同一份存储服务粗召回与精排

```
粗召回：query 前 64 维  vs  候选前 64 维（同一份存储，顺序读出，无需额外 IO）
         → 每向量成本 ~0.3μs，负责把候选从 10^12 砍到 10^4
精排：  query 前 1024 维 vs  候选前 1024 维（同样顺序读出，只是多读 1920B）
         → 每向量成本 ~6μs，负责从 10^4 砍到 top-10
```

关键点：**两次计算读的是同一个 SSD 位置的不同偏移**，不需要「召回之后再回 SSD 取原始向量」这一跳。这一步把传统两阶段架构里最贵的一段 IO 砍掉了。

### 2.4 与 nprobe / 带宽预算的联合调优

论文给了一个经验公式，用于决定在给定延迟预算下探多少胞腔：

```
延迟 ≈ nprobe × (单胞腔顺序读时间) + candidate × (精排计算时间)
建议在 fixed budget 下优先加 nprobe 而非加 candidate——
因为顺序读的单位成本远低于随机精排，nprobe 的边际收益在前 64 个胞腔内都不衰减
```

## 三、关键实验结果

**数据集**：内部多模态池（图像 + 交错文档 embedding，2048 维，Matryoshka 训练）1 万亿条；公开对照 1B 规模用 LAION-2B 子集 + Hy-Vector-3 类 embedding。

| 方法 | 硬件 | recall@10 | P99 延迟 | 构建成本 | 索引体积 |
|------|------|-----------|---------|---------|---------|
| IVF-PQ（64B/向量）| 512GB 内存集群 | 0.891 | 4.2ms | 中 | 64TB（全内存）|
| DiskANN/Vamana | 64GB 内存 + NVMe | 0.963 | 7.8ms | **高（8x）** | 88TB |
| **MRL-SPANN** | **64GB 内存 + 16×NVMe** | **0.951** | **9.4ms** | **低（1x）** | **41TB** |
| SPANN（原版 int8）| 同上 | 0.919 | 10.1ms | 低 | 96TB |

几个值得单独拎出来的数：

- **MRL 前缀的召回贡献**：只用 64 维前缀做粗召回，比用独立的 64 维模型进行粗召回高 4.7 个点——验证了「同一表征的不同前缀」比「两个不同模型」更一致。
- **存储 - 召回曲线**：把粗召回前缀从 64 提到 128，recall@10 提升 1.1 个点，但 SSD 带宽压力 +37%——**64 维是明显的拐点**。
- **增量插入**：新向量只写对应胞腔的尾部 append log，定期合并；每小时百万级插入时，recall 衰减小於 0.3%，不需要像图索引那样周期性重建。

## 四、创新点分析

1. **第一次让「套娃表征」真正影响索引设计**。此前 Matryoshka 只被用来做「省 embedding 存储」（截断发给下游），MRL-SPANN 把它变成了索引内部的数据结构：质心、posting、粗排、精排全部建立在同一份前缀上。这是把模型侧的一个训练技巧，翻译成了系统侧的一整套布局。
2. **把「单次 IO 服务两级计算」做实**。传统两级架构里，粗排和精排要么读两份数据（内存 + SSD），要么读完 SSD 还要再读一次 SSD 取原始向量。这里两级共享一次顺序 IO，代价模型完全不同。
3. **构建成本的量级下降**。图索引的致命伤是构建；k-means 可以在 GPU 上几小时跑完万亿样本。这让「按需重建」从不可能变成可能——对训练数据工程这种「批量建、批量查、用完就扔」的场景尤其合适。

⚠️ **一个容易被忽略的前提**：这套方法只在 embedding 本身支持 Matryoshka 的前提下成立。如果用老式 CLIP ViT-L/14（不支持 MRL），截断前缀会直接掉点，此时必须回退到其他 SSD 倒排方案。这也是为什么腾讯 Hy-Vector-3 这类「MRL + int8 原生出厂」的模型这么重要——**检索系统的可行性，正在被 embedding 训练方式反向决定**。

## 五、局限性

- **对 SSD 硬件布局敏感**：论文数据来自 NVMe RAID，机械盘或网络存储（EBS 类）下顺序读优势会被削弱不少，P99 可能翻倍。
- **交叉模态的监督偏差**：图像 embedding 是各向异性的，**各向异性越强，前缀截断损失越小**；文本 embedding 分布更均匀，同一套 nprobe 参数在纯文本检索上 recall 低约 2 个点。
- **更新期的读放大**：append log 与主线 posting list 并存时，热胞腔会退化成两次读，需要在合并策略上做代价平衡。
- **没有解决「要不要检索」的问题**：如果 embedding 质量本身不足以区分候选（例如上万类别的细粒度商标），再快的 ANN 也救不回 recall——这是表征质量的天花板，不是索引的天花板。

---

## 六、工程启示

1. **如果你正在做十亿级以上的多模态检索，先换 embedding 再换索引**。MRL + int8 原生（如 Hy-Vector-3、Matryoshka Ada 类）能把同样的硬件容纳能力抬高 3~8 倍；这一步的收益大于任何索引调优。
2. **nprobe 优先于 candidate**。在延迟预算分配上，先加探测的胞腔数，再加候选深度——顺序读的边际成本远低于精排计算。
3. **离线数据工程可以完全绕开向量数据库**。训练数据去重、配比、难例挖掘这类「批建批查」场景，直接走 GPU k-means + SSD 倒排是最省钱的路线，不需要 HNSW/图索引，也不需要分布式集群。
4. **敏感图库 / 版权检测这类 99% recall 场景要留重排层**。0.951 的 recall@10 对推荐够用，对内容审核不够——务必保留原始向量（或 1024 维前缀）做最后一级精排，并在政策变化时重刷。
