# 第 4 章 · 可复现性：为什么这是第一评价指标

## 3.1 可复现的六要素

「能重跑出同样的结果」不是一句话，它至少由六个要素决定。任何一项失守，可复现就崩：

| # | 要素 | 说明 | 常见失守点 |
|---|---|---|---|
| 1 | **代码** | 逻辑本身 | 改了但没同步、版本对不上 |
| 2 | **依赖** | 库版本 | 没锁版本，半年后 pandas 升级行为变了 |
| 3 | **数据** | 输入数据 | 源表被更新、快照丢失、口径改了 |
| 4 | **环境** | OS / Python / 系统库 | 「我这能跑」 |
| 5 | **执行顺序** | 先跑什么后跑什么 | ★hidden state（第 2 章） |
| 6 | **随机性与时间** | 随机种子、当前时间 | 没设 seed；用了 `now()` 做口径 |

## 3.2 三种形态逐项打分

| 要素 | **Notebook** | **Python 脚本** | **HTML** |
|---|---|---|---|
| ① 代码 | ✅ 有 | ✅ 有 | ❌ **通常没有**（或只有截图） |
| ② 依赖 | ⚠️ 需额外声明（PEP 723 / requirements） | ✅ 锁文件成熟 | ❌ 无 |
| ③ 数据 | ✅ 可连源 | ✅ 可连源 | ❌ 只有结果快照 |
| ④ 环境 | ⚠️ 靠平台/容器 | ✅ 容器化成熟 | ❌ 无关 |
| ⑤ 执行顺序 | ⚠️ ★Jupyter 有坑 / marimo 可靠 | ✅ 天然确定 | ❌ 无从谈起 |
| ⑥ 随机性与时间 | ⚠️ 需自觉设 seed | ⚠️ 需自觉设 seed | ❌ 无从谈起 |
| **综合** | **中**（Jupyter 偏弱，marimo 强） | ★**最强** | ★**最弱** |

> **一句话结论**：脚本最可复现，是因为它**没有给人犯错的空间**；HTML 最不可复现，是因为它**根本没有重跑这回事**。

## 3.3 ★ AI 时代最致命的问题：HTML 里的数字可能从未被算过

这是本书最想强调的一点。

当人写 HTML 报告时，数字至少还经过一次人工计算（虽然可能抄错）。但当**让 AI 直接生成一份 HTML 分析报告**时：

```
模型的产出路径：生成文本
   → 它写出 <td>增长 23.5%</td>
   → 但没有任何环节保证这个 23.5% 真的被计算过
   → 图表若是 SVG/JS 画的，曲线形状也可以是编的
```

| 形态 | AI 参与时的可信度 | 原因 |
|---|---|---|
| **HTML** | ★**最低** | 数字是「生成的文本」，无验证环节 |
| **Python 脚本** | 高 | 跑一遍就知道；跑不通就是错的 |
| **Notebook** | ★**最高** | 每个输出都必须是 kernel 真实执行的结果 |

> **判据**：**能不能重跑 = 能不能相信。** HTML 不能重跑，所以它是三种形态里唯一「无法自证」的那个。

**实践建议**（AI 参与产出时）：

1. **结论类数字必须在 Notebook/脚本里跑出来**，再由 HTML 呈现，绝不直接让模型写数字
2. 若必须用 AI 起草，**跑一遍验证**（suggest → run → verify）
3. 在 Notebook 里加**断言 cell**：`assert 0 <= rate <= 1`、`assert df.notna().all()`——把「看起来对」变成「机器验证过」

## 3.4 让 Notebook 可复现的六件事

| # | 做法 | 工具 |
|---|---|---|
| 1 | **提交前 Restart & Run All** | Jupyter 内置 |
| 2 | **把全量执行接进 CI** | `nbconvert --execute`（任何 cell 报错即失败） |
| 3 | **锁依赖** | PEP 723 内联（marimo）/ requirements.txt / uv.lock |
| 4 | **参数化而非改代码** | papermill（parameters 标签 cell）／ marimo CLI 参数 |
| 5 | **设随机种子** | `random.seed` / `np.random.seed` / 框架 seed |
| 6 | **换响应式引擎**（治本） | marimo：无 hidden state、删除真生效 |

> 第 2 条值得单独强调：**`nbconvert --execute` 把「Restart & Run All」从人的纪律变成流水线的闸门**——这是投入产出比最高的一步。

## 3.5 让脚本可复现的六件事

| # | 做法 |
|---|---|
| 1 | 依赖锁文件（`uv.lock` / `poetry.lock` / `pip freeze`），**不要用 latest** |
| 2 | 容器化（Docker 固定基础镜像 + Python 版本） |
| 3 | 输入数据用**快照 / 版本化路径**，不要直接读「当前最新」 |
| 4 | 随机种子显式设置，并在输出里记录 |
| 5 | 时间口径**显式传参**（`--date 2026-09-30`），不要用 `now()` |
| 6 | 输出带**运行指纹**（代码 commit、依赖哈希、输入数据版本、运行时间） |

> 第 6 条是很多团队的缺口：**产物里不带指纹，三个月后没人知道这批数是哪个版本算出来的。**

## 3.6 HTML 怎么补救（它不是原罪，是不能单独存在）

HTML 本身没问题，问题在于**让它成为唯一产物**。补救三招：

| 招 | 做法 |
|---|---|
| **① 附上生成它的源** | 报告里给出生成脚本/Notebook 的链接或 commit |
| **② 带上指纹** | 页脚写明：源 commit、数据快照时间、依赖版本、生成时间 |
| **③ 可回溯** | 保留「从源到 HTML」的构建产物与日志，任何人能重跑出同一份 HTML |

> **标准应是**：**任何一份 HTML 报告，都必须能回答「它是从哪个代码、哪份数据、什么时间算出来的」。** 答不上来，它就不是报告，是传言。

## 3.7 本章要点

- 可复现六要素：**代码 / 依赖 / 数据 / 环境 / 执行顺序 / 随机性与时间**。
- 综合评分：**脚本最强 > Notebook（marimo 强、Jupyter 弱）> HTML 最弱**。
- ★**AI 时代致命风险**：让模型直接生成 HTML 报告，数字可能从未被计算过；**能不能重跑 = 能不能相信**。
- Notebook 可复现六件事，其中 **`nbconvert --execute` 接 CI** 性价比最高；治本是换响应式引擎。
- 脚本可复现六件事，最易漏的是 **产物不带运行指纹**。
- **HTML 不是原罪，但不能是唯一产物**——必须能回答「从哪来」。
