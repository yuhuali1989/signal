# 第 1 章：两种架构的诞生背景与核心差异

> **学习目标**：理解离线批量推理的工程需求，掌握 Ray+Triton 与 Ray+vLLM Actor 两种架构的核心设计差异，能判断在单机推理场景下应该选哪种方案。

---

## 1.1 问题定义：什么是离线批量推理

在线推理（Online Serving）和离线推理（Offline Inference）是 LLM 应用的两种基本模式。在线推理关注延迟——用户发一个请求，系统在 200ms 内返回首 token；离线推理关注吞吐——给定 100 万条数据，用最短时间全部跑完。

离线推理的典型场景包括：

- **大规模数据集标注**：用 70B 模型给 500 万条未标注文本打标签
- **合成数据生成**：用 LLM 生成训练数据，批量产出 100 万条 instruction-response 对
- **文档摘要/翻译**：批量处理企业内部文档库
- **评测基准跑分**：在 MMLU/HumanEval 等基准上跑完整评测集

这些场景的共同特征是：**数据量已知、延迟不敏感、吞吐是唯一指标**。

当模型可以放进单机的 GPU 时（比如 7B/13B 模型放一张 A100，70B INT4 放一张或两张 A100），工程师面临一个关键架构选择：**如何用 Ray 编排推理流水线？**

---

## 1.2 两种架构的一句话定义

**架构 A：Ray + 远程 Triton 服务**

```
┌─────────────────────────────────────────────────┐
│                  Ray Cluster                     │
│                                                   │
│  ┌──────────┐     gRPC/HTTP     ┌──────────────┐ │
│  │ Ray Worker│ ──────────────→  │ Triton Server│ │
│  │ (数据加载 │ ←──────────────  │ (模型推理)    │ │
│  │  预处理)  │     response     │              │ │
│  └──────────┘                   └──────────────┘ │
│       ↑                                ↑          │
│    CPU tasks                      GPU process    │
└─────────────────────────────────────────────────┘
```

Ray 负责「数据加载 + 预处理 + 后处理」，Triton 作为独立进程运行在同一台机器上，通过 gRPC/HTTP 接收推理请求。两者是**进程间通信（IPC）**关系。

**架构 B：Ray + vLLM Actor 内离线推理**

```
┌─────────────────────────────────────────────────┐
│                  Ray Cluster                     │
│                                                   │
│  ┌──────────────────────────────────────────┐    │
│  │            Ray Actor (GPU)               │    │
│  │                                            │    │
│  │  ┌─────────┐    ┌──────────────────┐     │    │
│  │  │ 数据加载 │───→│  vLLM LLM Engine │     │    │
│  │  │ 预处理   │    │  (模型推理)       │     │    │
│  │  └─────────┘    └──────────────────┘     │    │
│  │       ↑              ↓                    │    │
│  │    CPU tasks      GPU compute             │    │
│  │  ┌─────────┐                             │    │
│  │  │ 后处理   │                             │    │
│  │  └─────────┘                             │    │
│  └──────────────────────────────────────────┘    │
└─────────────────────────────────────────────────┘
```

Ray Actor 直接在进程内实例化 vLLM 的 `LLM` 引擎，数据加载、预处理、推理、后处理全部在同一个 Actor 进程内完成。推理调用是**进程内函数调用**，没有网络开销。

---

## 1.3 核心差异矩阵

| 维度 | 架构 A: Ray + Triton | 架构 B: Ray + vLLM Actor |
|------|----------------------|--------------------------|
| **通信方式** | gRPC/HTTP（序列化 + 网络） | 进程内 Python 函数调用 |
| **进程模型** | Ray Worker（CPU）+ Triton Server（GPU）= 2 个进程 | Ray Actor（CPU+GPU）= 1 个进程 |
| **GPU 所有权** | Triton 独占 GPU，Ray Worker 无 GPU | Actor 持有 GPU，CPU/GPU 共享进程 |
| **批处理机制** | Triton Dynamic Batcher（服务端聚合） | vLLM Continuous Batching（引擎内调度） |
| **数据传递** | Tensor → protobuf 序列化 → gRPC → 反序列化 | Python 对象直接传递，零拷贝 |
| **部署复杂度** | 需要 Triton 模型仓库 + server 配置 | 只需模型路径 + vLLM 参数 |
| **故障恢复** | Triton 崩溃 → 重启 server，Ray 继续工作 | Actor 崩溃 → 重新加载模型（慢） |
| **多模型支持** | 一个 Triton 可同时服务多个模型 | 一个 Actor 一个模型 |
| **可观测性** | Triton Metrics API + Ray Dashboard | Ray Dashboard + vLLM 日志 |
| **GPU 利用率** | Triton 管理实例，可配多模型实例 | vLLM 独占，`gpu_memory_utilization` 控制 |

---

## 1.4 为什么这个对比重要

在 2024-2026 年的 LLM 工程实践中，这两种架构都有大量真实生产部署：

- **架构 A（Ray + Triton）** 的典型用户是已有 Triton 基础设施的传统 ML 团队。他们的在线服务用 Triton，离线推理也想复用同一套部署，避免维护两套推理栈。Triton 的多模型、多框架（TensorFlow/PyTorch/ONNX/TensorRT）能力是核心优势。

- **架构 B（Ray + vLLM Actor）** 的典型用户是 LLM 原生团队。他们只做 LLM 推理，vLLM 是天然选择，把 vLLM 嵌入 Ray Actor 可以最大化吞吐、最小化部署复杂度。

两者不是简单的「谁好谁坏」，而是**不同的工程权衡**。本书的目标是把这个权衡的每个维度都拆开讲透，让你能根据自己的场景做出正确选择。

---

## 1.5 本书的范围限定

本书**只讨论单机可以完成推理的场景**，即模型可以放进一台机器的 GPU。具体来说：

- 7B/13B 模型：单张 A100 80G 或 H100
- 70B 模型（INT4 量化）：单张 A100 80G 或 2 张 A100
- 70B 模型（FP16）：2-4 张 A100（单机）

不涉及跨节点分布式推理（如 405B 模型需要多机 Tensor Parallelism）。这个限定让对比更聚焦——因为跨节点场景下，网络通信的开销会改变两种架构的 trade-off 天平。

## 1.8 本章小结

两种架构的本质差异是**「推理服务是独立进程还是嵌入进程」**：

- 架构 A（Ray + Triton）选择了**隔离**——推理服务独立运行，通过网络通信。好处是故障隔离、多模型复用；代价是序列化开销和部署复杂度。
- 架构 B（Ray + vLLM Actor）选择了**融合**——推理引擎嵌入 Ray Actor，进程内直接调用。好处是零序列化、部署简单；代价是故障耦合、模型独占。

在单机推理场景下，这个选择更加尖锐——因为网络通信变成了 localhost IPC，开销虽然比跨网络小，但仍然不是零；而 Actor 内调用的优势被放大，因为没有任何中间层。

后续章节将逐一拆开每个维度，深入到代码和数据层面。
