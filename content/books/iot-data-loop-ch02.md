# 第2章：端侧硬件架构——手机厂商量级的芯片与传感器设计

## 2.1 规模假设与约束

假设设备规模对标手机厂商（5,000 万 - 2 亿台），每台设备需具备：

- **端侧 NPU 算力**：**100 TOPS**（INT8），可运行 7B 参数量化 VLM
- **实时推理**：端侧 VLA 模型推理延迟 < 50ms（7B INT4 量化）
- **数据采集**：多传感器同步（摄像头 30fps + IMU 100Hz + 麦克风 16kHz）
- **断网续传**：离线缓存 ≥ 24h 数据，联网后自动回传
- **功耗**：持续推理功耗 < 3W（电池供电设备）
- **BOM 成本**：端侧芯片成本 < $25-40/颗（亿级量产后）

**云端算力约束**：
- 云上训练推理总卡：**1 万张 GPU/NPU 卡**（包含训练和推理共享）
- 端云分工：端侧 100 TOPS 处理大部分实时推理，云端 1 万卡处理大规模训练和长尾困难样本

## 2.2 芯片架构设计

### 2.2.1 SoC 架构

与 4 TOPS 方案不同，100 TOPS NPU 意味着端侧 SoC 接近 **旗舰级边缘计算平台**（对标 NVIDIA Orin / Qualcomm Snapdragon Ride）：

```
┌────────────────────────────────────────────────────┐
│                IoT VLA SoC（100 TOPS）              │
├─────────────────────┬──────────────────────────────┤
│                     │  ┌──────────────────────────┐│
│    CPU 集群          │  │      NPU 核心集群       ││
│  8×Cortex-X4        │  │  - 100 TOPS @ INT8       ││
│  + 4×Cortex-A720    │  │  - 20 TOPS @ FP16        ││
│  + 2×Cortex-M4      │  │  - 专用 Transformer      ││
│  (安全域)            │  │  加速器 (SDPA 硬件化)    ││
│                     │  │  - 4-bit 张量核心         ││
│                     │  │  - 硬件稀疏化引擎         ││
│                     │  └──────────────────────────┘│
├─────────────────────┼──────────────────────────────┤
│  ISP（图像信号）     │   DSP（传感器融合）          │
│  4× MIPI CSI        │   C23 DSP 1.5 TOPS          │
├─────────────────────┴──────────────────────────────┤
│  内存：16GB LPDDR5X（共享 CPU+NPU，8533 MT/s）      │
│  存储：256GB UFS 4.0（端侧缓存+多版本模型存储）      │
│  连接：WiFi 7 + BLE 5.4 + 蜂窝 5G RedCap            │
│  安全：HSM 安全芯片 + TEE（Trusted Execution）       │
└────────────────────────────────────────────────────┘
```

**CPU 升级原因**：100 TOPS NPU 需要配套的高性能 CPU 做数据预处理、调度和 I/O。8×Cortex-X4 是高通骁龙 8 系的 CPU 配置，足以处理相机数据流和量化推理框架的调度。

**NPU 架构**：100 TOPS 的 NPU 采用 **多核设计**（8-16 个计算核），每个核包含专用的 Transformer 加速单元（SDPA 硬件化），支持 INT4/INT8/FP16 混合精度。

### 2.2.2 NPU 关键设计

NPU 是为端侧 VLA 推理定制设计的加速器，核心指标：

| 指标 | 目标 | 对标方案 |
|:----|:----|:--------|
| 算力 | 100 TOPS @ INT8 | NVIDIA Orin ~200 TOPS，Qualcomm Snapdragon Ride ~100 TOPS |
| 内存带宽 | 128 GB/s | LPDDR5X 8533 MT/s |
| 模型容量 | 7B INT4 量化（~3.5GB 参数） | 可运行 LLaMA 7B / Qwen3-7B / Gemma 7B |
| Transformer 加速 | 硬件化 SDPA（Scaled Dot-Product Attention）×16 核 | NVIDIA Tensor Core |
| 量化支持 | INT4/INT8/FP16 混合精度 + NF4 | Qualcomm AI Engine |
| 稀疏化 | 2:4 结构化稀疏（2× 加速） | NVIDIA Ampere 架构 |
| 功耗 | < 2W @ 持续推理（100 TOPS 峰值 < 8W） | 高通 Hexagon NPU |
| 面积 | < 40mm² | 5nm/4nm 制程 |

**关键设计决策**：

**为什么选 100 TOPS？** 100 TOPS 是一个关键的「甜点值」：
- 跑 7B INT4 模型（3.5GB 参数）的全 Prefill + Decode 约 40ms，满足实时性
- 支持多路摄像头实时处理（1× RGB + 1× 广角 + 1× ToF）
- 可以在端侧做高质量 VLA 推理，不依赖云端
- 芯片面积和功耗在 5nm/4nm 制程下可控
- 与云端 1 万张卡形成互补——**常用场景由端侧解决，长尾困难样本交云端**

### 2.2.3 与云端算力协同

```
端侧 100 TOPS（亿级设备）   vs   云端 1 万张卡
━━━━━━━━━━━━━━━━━━━━━━━        ━━━━━━━━━━━━
总聚合算力：千万亿 TOPS             总聚合算力：~50 EFLOPS
（100 TOPS × 5000 万设备）         （10K × ~5 PFLOPS/卡）
                                
职责：日常推理 + 预筛选       职责：大模型训练 + 困难样本处理
      实时响应 < 50ms                长尾场景分析
      90% 推理在端侧完成             模型迭代更新
```

**关键协同机制**：
- 端侧处理 90%+ 的日常推理（已知场景、高置信度）
- 端侧置信度 < 0.7 的样本 → 上送云端处理
- 云端 1 万卡不定期做模型蒸馏（大模型→端侧 7B 量化模型）
- 端侧模型通过 OTA 更新（频率：每 1-2 周一次）

## 2.3 传感器阵列设计

| 传感器 | 型号 | 数量 | 采样率 | 数据量/天 | 用途 |
|:-------|:-----|:----|:-------|:---------|:-----|
| RGB 摄像头 | IMX800（1/1.43" 50MP） | 1-2 | 30fps | ~80GB（压缩后~8GB） | VLA 视觉输入 |
| 广角摄像头 | IMX586（48MP） | 1 | 30fps | ~60GB（~6GB） | 环境感知 |
| 长焦摄像头 | IMX758（2×光变） | 1 | 15fps | ~20GB（~2GB） | 远距离检测 |
| 麦克风阵列 | MEMS × 4 | 1组 | 48kHz | ~4GB | 语音交互 |
| IMU | BMI323 | 1 | 100Hz | ~50MB | 姿态检测 |
| ToF 深度 | VL53L9（940nm） | 1 | 60fps | ~400MB | 近距离 3D 感知 |
| 温湿度 | BME280 | 1 | 1Hz | ~1MB | 环境监测 |

> **与 4 TOPS 方案对比**：100 TOPS 的 NPU 允许使用更高分辨率的摄像头（IMX800 50MP vs IMX678）和更高的采样率，因为端侧可以实时做 H.265 编码和关键帧提取，无需降低原始质量。

**数据量总计**：~15GB/天/设备（压缩后），5,000 万台设备日数据量约 **750 PB/天**。

## 2.4 端侧数据预处理 Pipeline

100 TOPS 的端侧算力可以实现比 4 TOPS 方案**更智能的数据筛选**：

```
原始传感器数据（15GB/天）
    │
    ├── 端侧 7B VLA 全推理（全部数据流）
    │   ├── 场景理解 → 仅保留高价值场景
    │   ├── 动作评估 → 标记异常/失败动作
    │   └── 语义分割 → 标注感兴趣区域
    ├── 关键帧提取（场景变化检测 → 仅上传变化帧）
    ├── H.265 硬件编码 + Zstandard 压缩
    ├── 端侧量化压缩（4-bit 特征向量，压缩比 10×）
    └── 缓存队列 → 联网后上传
```

**与 4 TOPS 的核心差异**：
- 4 TOPS 方案：仅能做 1B 模型轻推理，只能上传后由云端分析
- **100 TOPS 方案：端侧直接跑 7B 模型全推理，输出结构化特征向量**
- 上传量：原始 15GB/天 → 结构化特征 **~100MB/天**（压缩比 150:1）

## 2.6 端云推理分工策略

### 2.6.1 哪些推理在端侧，哪些在云端

| 场景 | 处理端 | 原因 |
|:-----|:-------|:-----|
| 日常场景理解 | 端侧（100 TOPS） | 延迟 < 50ms，覆盖 90% 场景 |
| 预定义动作执行 | 端侧 | 确定性高，无需云端 |
| 异常检测 | 端侧初筛 → 云端确认 | 端侧判断异常概率，云端做精确判定 |
| 新场景首次出现 | 端侧 → 云端 | 端侧低置信度 → 上送云端大模型 |
| 模型训练/蒸馏 | 云端（1 万卡） | 端侧无训练能力 |
| 长尾失败案例 | 云端 | 需要大模型 + 人工审核 |

### 2.6.2 端侧推理管线

```
传感器输入（30fps）
    │
    ▼
  端侧 VLA 7B 模型（100 TOPS）
    │
    ├── 高置信度（> 0.95）→ 直接执行动作（无延迟，不上传）
    ├── 中置信度（0.7-0.95）→ 执行动作 + 异步上传统计
    └── 低置信度（< 0.7）→ 执行动作（用最佳 guess）+ 上传全量数据
```

**端侧推理统计**：
- 总推理量：30fps × 全天 = ~260 万次推理/天/设备
- 其中 ~90%（230 万次）高置信度，不上传
- 其中 ~9%（23 万次）中置信度，仅上传统计摘要
- 其中 ~1%（2.6 万次）低置信度，上传感知数据
- **上传带宽节省**：相比不上传任何数据，100 TOPS 的端侧推理大幅减少了需要上传的数据量

## 2.7 本章小结

本章修正了端侧硬件的关键参数：**NPU 100 TOPS + 云上 1 万张卡**。

核心设计原则是 **「端侧做足，云端补拙」**：
- 100 TOPS NPU 可运行 7B 参数量化 VLA 模型，覆盖 90%+ 的日常推理场景
- 端侧 BOM 成本 $83/台（亿级量产后可降至 $50-60）
- 端侧预处理将上传量从 15GB/天降至 ~100MB/天（压缩比 150:1）
- 云端 1 万卡集中处理训练、蒸馏和长尾场景

**与 4 TOPS 方案的核心差异**：
| 维度 | 4 TOPS（旧假设） | 100 TOPS（实际） |
|:-----|:---------------|:---------------|
| 端侧模型 | 1B INT4（520MB） | 7B INT4（3.5GB） |
| 端侧推理能力 | 实时推理 < 50ms，仅完成 70% | 全场景推理 < 45ms，完成 90%+ |
| 端侧预处理 | 仅压缩 + 关键帧提取 | 全推理 + 特征向量提取 |
| 上传量 | 1GB/天/设备 | 100MB/天/设备 |
| 云端训练依赖 | 高（需要云端处理大部分推理） | 低（端侧承担大部分推理） |
| BOM 成本 | $44/台 | $83/台 |
