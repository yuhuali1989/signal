# 第 20 章 · 技术架构：执行面、存储、鉴权与交付怎么搭

## 4.1 总体分层

```
┌────────────────────────────────────────────────────────────┐
│ 接入层：企业 SSO / 内网网关 / 门户嵌入                        │
├────────────────────────────────────────────────────────────┤
│ 控制面（自研）                                               │
│   用户·租户·权限 │ 会话编排 │ 调度器 │ App 发布 │ 审计·配额   │
├────────────────────────────────────────────────────────────┤
│ 执行面（marimo 引擎 + 容器）                                 │
│   marimo kernel (App/Cell/DAG) │ uv sandbox │ 预装包镜像     │
├────────────────────────────────────────────────────────────┤
│ 存储层                                                       │
│   Notebook(Git/对象存储) │ 数据(数仓/湖) │ 产物 │ 缓存       │
├────────────────────────────────────────────────────────────┤
│ 集成层：数据源凭证代管 │ 内部模型端点 │ 告警 │ 工单/发布流程   │
└────────────────────────────────────────────────────────────┘
```

**核心分工**：**控制面自研，执行面直接用 marimo**。控制面通过 marimo 的 Python API 与 CLI 驱动执行面，而不是重写引擎。

## 4.2 执行面：会话调度是全部体验的地基

### 会话生命周期

```
用户点开 notebook
   → 控制面申请会话（规格：CPU×N / 内存 / 是否 GPU）
   → 拉起容器（预装镜像）→ 挂载 notebook 文件与数据源凭证
   → 启动 marimo kernel（edit 或 run 模式）
   → 用户操作（WebSocket）
   → 闲置超时（如 30 min）→ 保存状态 → 回收容器
```

| 设计项 | 建议 | 理由 |
|---|---|---|
| **容器粒度** | 一个 notebook 一个容器 | 隔离简单、故障域小 |
| **镜像分层** | base（Python+marimo）→ 常用包层（numpy/polars/torch…）→ 按需 uv 装 | ★平衡冷启动与灵活性 |
| **冷启动目标** | **< 10 秒** | molab 靠 Modal 做到快速启动；慢了用户就不想用 |
| **闲置回收** | 30 min 无操作回收，状态先落盘 | ★最大的成本节省手段 |
| **GPU 池** | 独立池 + 申请制 + 配额 | GPU 是最贵的资源，不能按需敞开 |
| **长任务** | 与交互会话分离，走调度器的异步执行 | 避免长任务占着交互会话 |

### 镜像与依赖策略（关键工程决策）

```
镜像预装：Python + marimo + 常用科学计算包（numpy/pandas/polars/matplotlib/…）
        + 公司内部公共库
        ↓
notebook 自描述：PEP 723 内联依赖（# /// script 块写在 .py 顶部）
        ↓
运行时装：uv 按 PEP 723 装缺失包（秒级）
        ↓
可选强化：对高频 notebook 预构建专用镜像（固化依赖，彻底消除装包时间）
```

> ★**PEP 723 + uv 是这套架构的关键**：它让「依赖可复现」和「冷启动快」同时成立——依赖写在 notebook 里（可审计、可复现），装包又快到无感。

## 4.3 存储设计

| 数据 | 存哪 | 要点 |
|---|---|---|
| **Notebook 文件** | **Git 仓库**（首选）或对象存储 + 版本 | ★`.py` 的最大优势就是能进 Git；建议按工作空间建仓 |
| **上传的数据文件** | 对象存储（按空间隔离） | 明确大小与保留策略 |
| **运行产物**（图、表、模型） | 对象存储 + 元数据登记 | 挂 `run_id`，可溯源 |
| **缓存** | `mo.persistent_cache` / `mo.cache` → 对象存储 | ★**必须明确告知用户：什么会持久、保留多久** |
| **会话临时态** | 容器本地盘 | 回收即消失，不要让用户误以为持久 |

> **一个必须写进产品说明的边界**：哪些数据会持久、哪些不会。molab 也只对「sidebar 上传」和 `mo.persistent_cache` 保证持久，且有大小与时长限制——**用户误以为「跑出来的东西会自动保存」是常见投诉来源**。

## 4.4 数据接入与凭证代管（★安全红线）

```text
❌ 错误做法：用户把数据库账号密码写进 notebook → 进 Git → 泄露
✅ 正确做法：
   平台维护「数据源连接目录」（名称 + 类型 + 凭证，加密存储）
        → 按工作空间授权哪些连接可见
        → 会话启动时以环境变量/配置注入（不落盘到 notebook）
        → notebook 里只写连接名，不写凭证
```

| 项 | 做法 |
|---|---|
| 凭证存储 | 密钥管理服务（KMS / Vault / 云厂商 KMS），**绝不进代码库** |
| 注入方式 | 会话启动时注入环境变量，容器回收即失效 |
| 审计 | 记录「谁在什么时候用哪个连接查了什么」（至少记连接与次数） |
| 下推 | 尽量让 SQL 在数仓侧执行，只取结果——**避免把全表拉进 notebook 内存** |

## 4.5 鉴权与多租户

| 层 | 方案 |
|---|---|
| **身份认证** | 接企业 SSO（OIDC / SAML / LDAP） |
| **访问控制** | RBAC：Owner / Editor / Viewer，按工作空间授权 |
| **App 访问** | ★独立于源 notebook 的访问控制；支持「仅内网」「指定人群」「链接可见」 |
| **Secret 隔离** | 按工作空间隔离，跨空间不可见 |
| **网络隔离** | 会话容器在独立网络命名空间，只放行授权的数据源与内部服务 |
| **审计** | 记录登录、notebook 读写、会话启停、App 发布、数据源使用 |

> **多租户的最小实现**：不需要做到 SaaS 级隔离，但**工作空间之间的数据、凭证、会话必须互不可见**——这是内部平台的合规底线。

## 4.6 调度与产物

当 notebook 变成生产任务时：

| 能力 | 实现 |
|---|---|
| 定时触发 | 调度器（Airflow / Argo / 自研 cron 服务）触发 `python nb.py` 模式 |
| 参数化 | CLI 参数传入（日期、品类、阈值等） |
| 长任务 | 异步执行 + 状态查询，**不要挂在交互会话里** |
| 失败处理 | 重试策略 + 告警（企微/钉钉/邮件）+ 保留日志与失败现场 |
| 产物归档 | 输出到对象存储，带 `run_id`，登记元数据（谁跑的、什么参数、哪次运行） |
| ★幂等 | 同一 `run_id` 重跑不产生重复副作用 |

> 注意：调度这块的工程量常被低估。**建议一期只做「定时 + 参数 + 告警 + 产物归档」最小闭环**，复杂的 DAG 编排交给公司已有的调度系统（Airflow 等），不要重复造。

## 4.7 交付：App 托管（价值最高的一块）

```
notebook（Editor 写好的分析）
   → 点「发布为 App」
   → 控制面用 `marimo run` 模式起一个常驻会话
   → 分配内部 URL + 访问权限（业务方只读）
   → 业务方改交互控件 → 响应式重算 → 出结果（看不到源码）
```

| 设计点 | 建议 |
|---|---|
| **常驻 vs 按需** | 高频 App 常驻；低频按需拉起（冷启动几秒可接受） |
| **只读** | ★`marimo run` 天然隐藏代码——这是它相对 Jupyter 的巨大优势 |
| **版本** | App 绑定 notebook 的某个 Git 版本，可回滚 |
| **嵌入** | 提供 iframe 嵌入能力，可放进内网门户/文档 |
| **静态导出** | 轻量 App 可导出 WASM HTML 走静态托管（零运行成本） |

> ★**算一笔账**：一个业务方要的交互式看板，传统做法是「分析师出图 + 前端做页面 + 后端接口」，至少 2–3 人周；marimo app 模式下**分析师一个人半天就能交付**。这是整个项目最容易量化的价值（第 8 章展开）。

## 4.8 可观测与成本计量

| 类别 | 指标 |
|---|---|
| **平台健康** | 会话启动成功率、冷启动 P50/P95、容器存活数、OOM/崩溃率 |
| **使用** | 日活用户、活跃 notebook、会话时长、App 访问量 |
| **成本** | ★按工作空间的 CPU/GPU 时长、存储量、模型 token 消耗 |
| **质量** | 定时任务成功率、重跑一致性（同参数同结果？） |
| **安全** | 数据源使用审计、越权尝试、异常下载量 |

**成本可见性本身就是治理手段**：当团队能看到自己空间花了多少算力，浪费会自然下降。

## 4.9 本章要点

- 分工：**控制面自研（调度/权限/审计/发布），执行面直接用 marimo**。
- 执行面：一 notebook 一容器；**镜像分层 + PEP 723 + uv** 同时解决冷启动与可复现；★**冷启动 < 10 秒**、**闲置 30 min 回收**（最大省钱手段）；GPU 独立池 + 配额。
- 存储：notebook 进 **Git**（`.py` 的核心优势）；★**必须明确告知什么会持久、什么不会**。
- ★**凭证永不进 notebook**：平台维护连接目录、按空间授权、会话注入、KMS 加密。
- 鉴权：SSO + RBAC + ★**App 权限独立于源码** + 审计。
- 调度一期只做最小闭环，**复杂编排交给已有 Airflow**。
- ★**App 托管是价值最高的模块**：`marimo run` 天然隐藏代码，分析师半天交付业务看板，替代传统 2–3 人周的前端+后端流程。
