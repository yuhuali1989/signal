## 5.1 差距总表

> 工作量为**量级估算**（人周，按 1 名熟悉 Python/容器的工程师计），实际需按团队能力与现有基建校准。**有现成基建（K8s、SSO、对象存储、调度系统）可显著下浮**。

| # | 能力 | marimo OSS | 技术方案 | 工作量 | 优先级 |
|---|---|---|---|---|---|
| 1 | **SSO 登录** | ❌ | OIDC/SAML 接入 + 反向代理鉴权 | 1–2 | **P0** |
| 2 | **会话编排** | ❌ | 容器平台 + 自研会话服务（生命周期/规格/回收） | 6–10 | **P0** |
| 3 | **持久化与版本** | ❌ | Git 仓库（按空间）+ 对象存储 | 3–5 | **P0** |
| 4 | **依赖沙箱** | ✅ uv+PEP723 | 复用 + 制定镜像预装清单 | 1–2 | **P0** |
| 5 | **App 发布与访问控制** | ⚠️ 有 CLI | `marimo run` 托管 + 独立权限 + 版本绑定 | 4–6 | **P0** |
| 6 | **数据源与凭证代管** | ❌ | 连接目录 + KMS + 会话注入 | 4–6 | **P0** |
| 7 | **监控与告警** | ❌ | 指标采集 + 看板 + 告警 | 2–3 | **P0** |
| 8 | **调度与参数化** | ⚠️ 可脚本跑 | 接 Airflow / 自研 cron + 产物归档 | 3–5 | P1 |

| 10 | **配额与成本计量** | ❌ | 资源计量 + 按空间展示 | 2–4 | P1 |
| 11 | **AI 接内部模型** | ⚠️ 接口已有 | 指向内部端点 + 审计 + 提示词模板 | 2–4 | P1 |

**合计（量级）**：

| 范围 | 人周 |
|---|---|
| **MVP（P0）** | **≈ 25–35 人周** |
| MVP + P1 | ≈ 40–55 人周 |
| 全量（含 P2） | ≈ 45–60 人周 |

> 换算：1 名全职工程师 ≈ 6–9 个月；**2–3 人小组 ≈ 3–5 个月到 MVP**。这组数字是第 7 章算账的基础。

## 5.2 三条实现路径：代价差一个量级

同样补一个能力，路径不同代价天差地别：

| 路径 | 做法 | 代价 | 适用 |
|---|---|---|---|
| **① 外围** | 不改源码，用 CLI/配置/网关 | ★**最小** | SSO、App 托管、静态导出 |
| **② 包一层服务** | 自研控制面，调 marimo Python API / CLI | 中 | 会话编排、调度、发布、计量 |
| **③ 改源码** | fork + patch | ★**最大**（长期维护成本） | 深度存储后端、特殊鉴权注入 |

**推荐配比**：**80% 走 ①②，尽量 0% 走 ③**。

具体落地建议：

| 需求 | 走哪条 |
|---|---|
| SSO | ① 网关层做鉴权，marimo 前面挂一层代理 |
| 会话管理 | ② 自研服务决定何时起/停容器，容器里跑 marimo |
| 审计 | ② 服务侧埋点为主；需要 cell 级细节时再用 `cell_runner` 钩子（②½） |
| 存储后端替换 | ③ 若必须用内部存储协议才改，否则用挂载/同步（①） |

## 5.3 ★ fork 治理：最容易慢性死亡的地方

即便只改一点点源码，也要提前定规矩：

| 规则 | 说明 |
|---|---|
| **patch 最小化** | 每个改动独立成一个小而完整的 patch，附注释说明「为什么必须改」 |
| **尽量上游化** | 改动对社区也有价值 → **提 PR**。上游合了你就少一个 patch |
| **锁版本 + 定期同步** | 固定一个上游版本，每季度评估升级；升级时逐个 rebase patch |
| **patch 清单文档化** | 维护一份 `patches/README`，记录每个 patch 的作用、作者、是否可移除 |
| **设「patch 上限」** | ★约定：patch 数量超过 N（如 5 个）或改动超过 X 行就**触发架构复盘**——说明你可能在错误层面定制 |

> **判断信号**：如果你发现自己在改 `runtime.py` 的执行语义、或改前端主流程，**停下来重新评估**——这通常意味着你想要的其实是另一个产品，而不是「内部 marimo 平台」。

## 5.4 最容易被低估的五件事

| # | 被低估的项 | 为什么容易低估 | 应对 |
|---|---|---|---|
| 1 | **会话编排的运维复杂度** | 看起来就是「起容器」，实际有镜像、网络、存储挂载、OOM、僵尸会话、资源碎片 | 预留 P0 的最大工作量；**尽早做闲置回收** |
| 2 | **持久化边界的沟通成本** | 技术上有答案，但用户会反复误解「什么会保存」 | ★**产品里写清楚 + 首次使用时提示** |
| 3 | **GPU 成本** | 「给算法同学配个 GPU」听起来简单，账单很吓人 | GPU 池 + 申请制 + 配额 + 闲置回收（**比 CPU 更严格**） |
| 4 | **从 Jupyter 迁移的隐性成本** | 软件免费 ≠ 迁移免费：扩展、magic commands、IPython 专有工具要重测/重写 | 只迁移高价值 notebook；**新项目直接用 marimo** |
| 5 | ★**推广与培训** | 平台做出来没人用 = 白做 | 种子用户 + 模板 + 规范文档 + 内部分享（第 8 章展开） |

## 5.5 迁移策略：不要「平移」，要「择优」

从 Jupyter 迁移时最大的错误是「把 1000 个 notebook 全转过来」。

| 做法 | 建议 |
|---|---|
| **存量** | ★**只迁高价值、高频使用的**；其余留在原处，按需再转 |
| **转换** | marimo 支持从 `.ipynb` 转换；转换后**必须人工验证**（尤其 magic、状态依赖、跨 cell 改对象的地方） |
| **常见转换坑** | 跨 cell 修改同一个 dataframe（marimo 要求同 cell 内完成）、依赖执行顺序的副作用、IPython magic |
| **增量** | 新项目一律 marimo；存量自然淘汰 |

## 5.6 本章要点

- **P0（MVP）≈ 25–35 人周**；2–3 人小组 **3–5 个月**到 MVP。有现成 K8s/SSO/调度可下浮。
- 最重的三块：**会话编排（6–10）> App 发布与权限（4–6）≈ 数据源凭证（4–6）> 持久化（3–5）**。
- 三条路径配比：**80% 外围/封装，尽量 0% 改源码**。
- ★**fork 治理**：patch 最小化、尽量上游化、定期同步、清单文档化、设「patch 上限」触发复盘。
- 最易低估：**会话运维复杂度 / 持久化沟通 / GPU 成本 / 迁移隐性成本 / ★推广培训**。
- 迁移要「**择优**」不「平移」；转换后必须人工验证（跨 cell 改对象是头号坑）。
