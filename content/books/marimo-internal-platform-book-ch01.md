## 1.1 先厘清：marimo 现在到底有什么

动手设计之前，必须把「官方已提供什么」和「要自己补什么」分开。按公开资料梳理，marimo 目前是**三件套**：

| 形态 | 是什么 | 定位 | 成本 |
|---|---|---|---|
| **marimo OSS**（核心） | 开源响应式 Python notebook，`pip install marimo`；`marimo edit` / `marimo run` / 脚本执行 / WASM 导出 | **引擎**，不是平台 | **Apache-2.0，零许可费** |
| **molab**（官方托管） | 托管版 marimo，云端算力；默认每 notebook **4 CPU / 32 GB RAM**，可挂 **NVIDIA RTX Pro 6000 Blackwell（96 GB VRAM）**；免费层 + GPU 付费 | 直接用 / **架构范本** | 免费层可用，GPU 按量 |
| **WASM playground** | 浏览器内跑 Pyodide，无需后端 | 轻量演示、文档嵌入 | 免费 |

**几个关键事实**（后续方案的地基）：

- **许可：Apache-2.0**。无许可费、无商业限制、可自由二次开发与内部部署。
- **文件是纯 `.py`**，可 Git 版本化、可作脚本跑、可 `import` 复用、可跑 pytest、可用 uv + PEP 723 管依赖。
- **响应式执行**：改一个 cell，依赖它的 cell 自动重跑（或标记 stale）；删除 cell 会连它的变量一起删——**无 hidden state**。
- **部署形态齐全**：编辑（`edit`）、App（`run`）、脚本（`python nb.py`）、静态 HTML/WASM、slides。
- **AI 已内置接口**：`marimo pair` 可把任意 agent（Claude Code、Codex、OpenCode 等）连到运行中的 session；编辑器内置 AI 支持自带 API key、自定义 system prompt、**本地模型**。

> ⚠️ **一处需要你确认的事实**：公开资料里我没检索到官方名为「**marimo Hub**」或「**marimo Studio**」的独立产品。与它们最接近的是 **molab**（即此前的 marimo Cloud 托管服务）。下文按「marimo OSS 引擎 + molab 形态作为架构参考 + 自建平台层」来设计；如果你指的 Hub/Studio 是某个社区项目或内部已有封装，那一层的复用程度会更高，方案需相应调整。

## 1.2 开源引擎 ≠ 平台：这是全部工作的起点

marimo OSS 给你的是**一个极好的 notebook 引擎**，但它不是平台。把两者分开，才知道要做什么：

| 能力 | marimo OSS | 平台层（要自建） |
|---|---|---|
| 响应式编辑 / 执行 | ✅ | — |
| SQL / 交互元素 / 包管理 | ✅ | — |
| App / 脚本 / WASM 导出 | ✅（CLI 级） | 托管、路由、鉴权 |
| **账号与 SSO** | ❌ | ★必须自建 |
| **多租户 / 权限** | ❌ | ★必须自建 |
| **notebook 持久化与共享** | ❌（本地文件） | ★必须自建（含版本） |
| **云端算力调度** | ❌ | ★必须自建（容器/GPU 池） |
| **定时调度与告警** | ❌ | ★必须自建 |
| **审计 / 配额 / 成本计量** | ❌ | 必须自建 |
| **内部数据源凭证代管** | ❌ | 必须自建 |
| **模板 / 资产库 / 复用治理** | 部分 | 自建 |

> **一句话**：**marimo 解决了「notebook 好不好用」，平台要解决「谁在用、跑在哪、数据从哪来、结果给谁看、花了多少钱」。** 后者一点都不比前者简单。

## 1.3 自建 vs 直接用 molab vs 买 SaaS：判据

三条路，先说结论：**多数有一定规模的公司，自建「平台层 + marimo 引擎」是长期最优，但绝不是无条件最优。**

| 方案 | 适合 | 不适合 | 隐性成本 |
|---|---|---|---|
| **A. 直接用 molab** | 小团队、无强合规约束、不想运维 | 数据不能出内网、要 SSO、要接内部数据源 | 数据在外部；**企业 SSO/专属支持未公开定价，需销售沟通** |
| **B. 买 SaaS**（Hex / Deepnote / Databricks） | 要最快上线、要协作与交付一体化 | 成本敏感、需要深度定制、数据合规严 | Hex 约 **$38–65/seat/月**、Deepnote 约 **$29/editor/月**（量级参考，以官方为准）；**格式锁定** |
| **C. 自建平台层 + marimo OSS** | 数据不出内网、要 SSO、要接内部数据与模型、中长期成本敏感、想定制 | 人手极少、急需上线、无运维能力 | ★**工程量被普遍低估**——开源免费不等于免费拥有 |

### 自建的四个真实动因（按说服力排序）

| # | 动因 | 说明 |
|---|---|---|
| 1 | **数据与合规** | 分析要连内部数仓/湖、含敏感数据；notebook 与产物必须留在内网 |
| 2 | **身份与权限** | 要接公司 SSO、按部门/项目隔离、操作可审计——**molab 的企业 SSO 未公开** |
| 3 | **接入内部生态** | 内部数仓凭证代管、内部模型端点、内部数据目录、工单/发布流程 |
| 4 | **中长期成本** | 人数上来后，seat 订阅的累计成本会超过自建摊销（第 7 章算账） |

**反过来说，什么时候不该自建**：团队 < 10 人、没有专职平台工程、半年内就要见效、且数据可以放外部——**直接买 SaaS，别自研**。自研 notebook 平台的失败案例，绝大多数不是技术做不出来，而是**投入被低估 + 维护做不下去**。

## 1.4 明确自建的边界：做什么、不做什么

自建最容易失控的地方是「顺手把引擎也重做一遍」。**边界必须写死**：

### ✅ 要做（平台层）

- 身份（SSO）、租户与权限、审计
- 会话调度（容器/GPU 池、生命周期、闲置回收）
- 存储（notebook 文件、数据、产物、缓存）
- 调度与告警、参数化运行
- 交付（App 托管、报告、嵌入）
- 数据连接与凭证代管
- AI 接入（接内部模型/端点 + 审计）
- 成本计量与配额

### ❌ 不做（引擎层，交给 marimo）

- **不改响应式执行语义**（DAG、调度、无 hidden state）——这是 marimo 的核心价值，动了就失去意义
- **不换文件格式**（坚持 `.py`）——换掉就丢掉 Git 友好与脚本化
- **不重做编辑器**（React/TS 前端直接用）——可定制主题与插件，但不 fork 主干

> ★**总原则**：**包一层，而不是改里面。** 只有在确属平台刚需（如注入鉴权上下文、自定义存储后端、审计埋点）时才改 marimo 源码，且要把改动做成**可向上游提交的增量**，避免长期 fork 地狱（第 5 章展开）。

## 1.6 本章要点

- marimo 三件套：**OSS 引擎（Apache-2.0）/ molab 托管 / WASM playground**；molab 默认 4 CPU + 32 GB，可挂 96 GB 显存 GPU。
- ★**开源引擎 ≠ 平台**——marimo 不管账号、权限、持久化、调度、审计、成本，这些全要自建。
- 自建的真实动因是**合规、SSO、内部生态、长期成本**；团队小/时间紧/无运维 → 直接买 SaaS。
- 边界原则：**★包一层，不改里面**；不改响应式语义、不换 `.py` 格式、不 fork 编辑器主干。
- 「marimo Hub / Studio」未检索到官方对应产品，本书按 **OSS + molab 形态参考 + 自建平台层** 设计。
