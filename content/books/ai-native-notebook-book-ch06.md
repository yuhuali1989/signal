# 第 13 章 · 协作、发布与工程化：Notebook 之后才是主战场

## 6.1 一句必须先讲的话

行业里有条很务实的忠告：

> **不要只优化 Notebook 编辑器。要优化 Notebook「完成之后」发生的事——协作、部署、调度，以及把结果送到需要它的人手里。**

三个主流工具的编辑体验其实都已经"足够好"。真正的摩擦在下游：

| 下游环节 | 常见摩擦 |
|---|---|
| 协作 | 多人同时改、评论、权限 |
| 复用 | 同样的逻辑每个 notebook 抄一遍 |
| 调度 | 能不能定时跑、参数化跑、失败告警 |
| 交付 | 结果怎么给不看代码的人看 |
| 复现 | 下周跑还是这个数吗 |

本章逐个展开。

## 6.2 实时协作（RTC）

| 平台 | 协作方式 |
|---|---|
| **JupyterLab 5** | 实时协作（RTC）基于 y-py，从 Lab 4 的实验特性转为稳定 |
| **Hex / Deepnote** | 内置类 Google Docs 的实时协作、评论、权限 |
| **本地 Jupyter** | 无原生多人协作（需 JupyterHub + 扩展） |

**选型含义**：如果团队有多人同时编辑的需求，SaaS 的协作体验通常明显好于自建；但要注意**数据/代码是否允许放云端**（合规约束）。

## 6.3 逻辑复用：让 Notebook 不再是孤岛

Notebook 的一个长期问题是**容易变成孤岛**——每个 notebook 各自抄一遍清洗逻辑，KPI 定义各说各话。

| 复用方式 | 说明 |
|---|---|
| **Modules（Deepnote）** | 把代码、SQL、转换逻辑打包成可复用组件，支持参数（input blocks）、发布到共享库；更新源 notebook 后**所有引用的 notebook 都能同步**（对统一 KPI 定义极有价值） |
| **Python 包** | 把共享逻辑抽成内部包，notebook import（通用做法，但需维护包结构与发布） |
| **nbdev** | 从 notebook 直接生成 Python 包与文档 |
| **复制 cell** | 最原始也最常见——也最容易导致口径不一致 |

**建议**：团队规模超过 3–5 人、且有重复分析逻辑时，**优先选有原生复用机制的平台**（Modules 之类），否则口径漂移几乎是必然。

## 6.4 调度与参数化运行

把 notebook 从"手动跑"变成"自动跑"：

| 能力 | 说明 |
|---|---|
| **参数化** | 用不同参数重跑同一 notebook（日期、品类、区域） |
| **定时调度** | cron 式定时运行（Hex / Deepnote 内置；Jupyter 需 papermill + cron 或托管平台） |
| **失败通知** | 跑失败要告警，别让人天天去看 |
| **结果落盘** | 跑完写入表 / 对象存储 / 发邮件，而不是只留在 notebook 里 |

**Jupyter 路线**：papermill（参数化执行）+ cron/调度器 + nbconvert（导出）——能搭出来，但要自己维护这一层。

## 6.5 发布：从分析到交付物

这是"给不看代码的人看结果"的关键路径，也是各平台差异最大的地方。

| 形态 | 说明 | 代表 |
|---|---|---|
| **交互式 App** | notebook 直接变成带输入控件的应用 | **Hex app mode（最成熟）**、Deepnote data apps |
| **静态报告** | 导出 HTML / PDF / Markdown | nbconvert、Quarto |
| **仪表盘式页面** | 发布成可分享页面 | Deepnote published pages |
| **轻量端点** | 把确定性块提升为 HTTP 端点（轻量推理） | Deepnote（正在演进的能力） |
| **自建应用** | 另配 Streamlit / Dash / Voila 并自己部署 | Jupyter 生态 |

**选型含义**：如果你的大量工作最终要变成"给业务方看的东西"，**原生 app 发布能力能省掉一整套前端+部署链路**——这往往是 Hex 这类平台溢价的合理性所在。

## 6.6 工程化：把 Notebook 纳入软件工程纪律

Notebook 常常游离在工程纪律之外。建议把这几条制度化：

| 纪律 | 做法 |
|---|---|
| **版本化** | 纯文本优先；输出不进仓库；AI 改动进 PR |
| **评审** | notebook 的重要分析也要 review（尤其 agent 写的） |
| **测试** | 关键转换逻辑抽成函数/包并写测试 |
| **环境锁定** | 镜像或锁文件，避免环境漂移 |
| **命名与结构** | notebook 命名规范、目录分层（探索 / 生产任务） |
| **生命周期** | 区分"一次性探索"与"要长期维护的资产"——前者可随意，后者要按工程标准 |

**一个实用分层**：

```text
/explore/    探索性 notebook（临时、可随意）
/analysis/   正式分析（需 review、需复现）
/jobs/       定时任务（参数化、有告警、有 SLA）
/apps/       对外的 app / 报告
```

## 6.7 本章小结

- **核心观点**：编辑体验已足够好，摩擦在下游（协作、部署、调度、交付、复现）。
- **协作**：SaaS 的 RTC 体验普遍优于自建；JupyterLab 5 的 RTC 已稳定（y-py）。
- **复用**：团队超过 3–5 人且有重复逻辑时，优先选有原生复用机制（如 Modules）的平台，否则口径必然漂移。
- **调度**：参数化运行 + 定时 + 失败通知 + 结果落盘；Jupyter 可用 papermill + cron 自建。
- **发布**：原生 app 发布（Hex / Deepnote）能省掉整套前端与部署链路，是这类平台溢价的主要来源。
- **工程化**：把 notebook 分层管理（探索 / 正式分析 / 定时任务 / 对外 app），并纳入版本、评审、测试、环境锁定纪律。
