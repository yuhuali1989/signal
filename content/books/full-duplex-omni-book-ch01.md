# 第 1 章 · 先把例子钉死：一块 80ms 时间片里到底有什么

讲全模态最容易犯的错，是先讲「统一表征空间」「早融合」「模态对齐」这些词。听的人点头，但脑子里没有一张具体的表、一个具体的整数。这本书反过来：**先把一个例子、一组数字、一张词表钉死，后面十章每一步都回到它**。

## 1.1 全书唯一的例子

时间 `t = 3200ms`。用户举着一个**金属保温杯**对着摄像头，说：

> 「这个…能微波吗？」

模型正在回答「不能，金属…」。到 `t = 3600ms`，用户插话：

> 「我是说盖子。」

模型闭嘴，改答「盖子是塑料的，可以」。

为什么偏偏选这个例子？因为它一次逼出了全模态系统里所有非做不可的事：

| 现象 | 逼出什么 |
|---|---|
| 「这个」是指代词 | 光听声音解不开，必须看画面 → **跨模态融合是刚需，不是锦上添花** |
| 杯子是金属、盖子是塑料 | 同一帧里两个区域要分别被注意到 → **空间坐标 h/w 不能丢** |
| 用户边听边插话 | 输出不能停，输入也不能停 → **双流建模** |
| 插话改变了指代对象 | 「盖子」必须绑到 3600ms 的帧，不是 3200ms 的帧 → **绝对时间 ID** |
| 模型自己也在说话 | 麦克风会录回自己的声音 → **stream_id 区分谁说的** |

一句话：这 400ms 里，词表、embedding、混合、生成、打断，五件事全都要发生。**后面每一章都是把这一块 80ms 的某一层放大**。

## 1.2 固定超参表（全书不许改）

| 项 | 值 | 为什么是这个数 |
|---|---|---|
| 时间片 | 80 ms | 24kHz ÷ 卷积总步长 1920 = 12.5 Hz；Mimi 的帧长 |
| 主干维度 `d` | 4096 | 7B 级 LLM 的标准宽度 |
| 层数 / 头数 | 32 / 32 | `head_dim = 128` |
| FFN 中间维 | 11008 | SwiGLU 约 8/3 d |
| 统一词表 `V` | 75840 | 65536 文本 + 8192 视觉 + 2048 音频 + 64 控制 |
| 音频 codec | Mimi 类，8 层 RVQ | 1 语义层 + 7 声学层，全因果 |
| 音频码本 | 2048 项 / 层 | 11 bit，1.1 kbps |
| 视觉输入 | 448×448，patch 14 | 32×32 = 1024 patch |
| 视觉压缩 | resampler 64 query | 8×8 网格，1024 → 64 |
| 音频采样率 | 24 kHz | 80ms = 1920 samples |
| 精度 | bf16 | 每参数 2 字节 |

一个必记的派生量：

```
一秒 = 12.5 个时间片
一片 = 87 个序列槽位
一秒 = 1087 个 token 进主干
5 分钟 = 约 32.6 万 token
```

最后这个数字是全书的暗线：它决定了第 9 章必须做 KV cache 压缩，也决定了为什么 Moshi 要把 17 条子序列折成「时间 × 深度」二维，而不是全拍平。

## 1.3 三路原始信号的精确 shape

`t = 3200ms` 这一片，从三个设备同时进来：

```python
wav   = mic.read()      # [1920]          24kHz × 0.08s，用户流
frame = cam.read()      # [3, 448, 448]   本片取 1 帧（30fps → 事件驱动采样）
text  = torch.tensor([5821])  # [1]      Inner Monologue 预测的字「这个」
```

注意第三行：**全双工系统里没有 ASR**。「这个」不是识别出来的转写，是模型自己在生成音频之前，先在心里预测的一个时间对齐文本 token（Inner Monologue）。这一点在第 7 章会展开，它也是避免语音训练拖垮文本能力的关键。

除此之外还有一路「模型流」——模型自己上一片生成的 8 个音频 ID，本片作为历史继续进入序列：

```python
a_model_prev = [74012, 74105, 74208, 74291, 74333, 74362, 74381, 74390]  # 8 个整数
```

所以严格说是**四路**：用户语音、摄像头、内心文本、自己的语音历史。前三路是「读」，第四路是「写」的历史回灌。

## 1.4 这一片最终要变成什么

所有故事都指向同一个张量：

```python
x: [1, 87, 4096]     # 87 个槽位，每个 4096 维
```

87 这个数逐段数一遍，全书会反复引用：

```
pos 0       BOV = 75776                         1
pos 1..64   视觉 token V0..V63                  64
pos 65      EOV = 75777                         1
pos 66      BOA = 75778                         1
pos 67..74  A_user  ×8  (1 语义 + 7 声学)        8
pos 75      EOA = 75779                         1
pos 76      BOA = 75778                         1
pos 77..84  A_model ×8                          8
pos 85      EOA = 75779                         1
pos 86      T「这个」 = 5821                     1
                                            ────
                                              87
```

再强调一次那个反直觉的事实：`x[1, 87, 4096]` 里**没有任何一维写着「这是视频」**。`pos 29`（8×8 网格里 `h=3, w=5`，正好是杯身金属高光）和 `pos 67`（用户音频语义层）在数学上完全等价，都是 4096 个浮点数。模型能区分它们，全靠外加的四层标签——这是第 5 章的主题。

## 1.5 全书路线图

| 章 | 回答的问题 | 回到例子的哪一层 |
|---|---|---|
| 1 | 例子与配置 | 整块 80ms |
| 2 | **词表选哪个** | 75840 怎么切四段，三套方案对比 |
| 3 | 文本/音频怎么 embedding | `E[5821]`、`E[74012]`、两套码本绑定 |
| 4 | 视频怎么 embedding | 1920×1080×30 → 64×4096 的演算 |
| 5 | **怎么混合** | 87 槽位拼接 + 四层标签 + TMRoPE |
| 6 | 主干逐层 shape / 融合在哪 | `scores[1,32,87,87]` 的 `Q[pos86]·K[pos29]` |
| 7 | 怎么生成文本与语音 | 12847 → 75778 → 8 个音频 ID → 1920 samples |
| 8 | **怎么输出图像/视频** | 75776 + 1024 个视觉 ID → VQ decoder |
| 9 | 全双工时序 | 双流、打断、延迟四段账、KV cache |
| 10 | **效果到底好不好** | 真实数据、评测口径、失败模式、选型建议 |

三处加粗正是提问里点名要的：词表选型、混合方式、音视频输出效果。

## 1.6 一条贯穿全书的判断

> **「词表」是写侧概念，「embedding」是读侧概念。**

文本和音频在生成侧必须是整数 ID（才能算 softmax 交叉熵、才能采样）；摄像头画面在理解侧是连续向量（不需要被采样，量化纯亏）。很多困惑都来自把这两件事混成一件事，以为「三种模态各有各的词表」或者「视频 token 也该有个 ID」。

第 2 章先把这句话变成一张可查的表。

## 1.7 本章小结

- 全书只用一个例子：`t=3200ms` 金属保温杯 + `t=3600ms` 插话「我是说盖子」。
- 固定配置 `d=4096 / 32 层 / V=75840 / 80ms 片`，一片 87 个槽位，一秒 1087 个 token。
- 三路输入 + 一路输出历史；没有 ASR，文本是 Inner Monologue。
- 所有模态最终汇入 `x[1,87,4096]`，shape 里不带模态轴，区分靠外加标签。
- 判断锚点：词表管「写」，embedding 管「读」。
