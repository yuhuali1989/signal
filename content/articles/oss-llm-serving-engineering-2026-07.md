# 开源大模型推理工程实战：在有限 GPU 上服务万亿参数模型

> 2026 年 7 月，"开源权重周"把两个怪兽级模型交到了每个人手里：**Kimi K3（2.8 万亿参数，MXFP4 约 594GB）** 与 **DeepSeek V4（1.6 万亿参数，V4-Flash 成本仅顶级 1/100）**。问题立刻变成工程问题——**我手上只有几张 H100，怎么把这种模型跑成高吞吐、低延迟的服务？**
>
> 本文把这个问题拆成一条可落地的工程链路，并与本站《GPU 工作原理与并发模型》的硬件/并发知识对应起来。

---

## 1. 先算账：显存到底够不够

以 Kimi K3 为例，权重以 MXFP4（每参数 0.5 字节）发布约 594GB，加上优化器状态/激活/KV Cache，全量服务需要 8–16 节点 80GB GPU。对中小团队，"全量独占一卡"不现实，必须靠两条路压缩：

1. **量化**：把权重从 FP16 压到 FP8 / MXFP4 / INT4（Kimi 官方就提供 MXFP4 权重）。
2. **切分**：张量并行（TP）/ 流水并行（PP）把模型拆到多卡；或专家并行（EP）只激活部分专家（MoE 天然适合）。

一个常被忽略的事实：**推理时权重是只读的**。这意味着多个推理进程可以 **共享同一份权重显存**（见第 3 节），这正是"多进程共享 GPU"最大的一块红利（对应《GPU》第 7 章 CUDA IPC 与权重共享）。

---

## 2. 连续批处理：让 GPU 永不空转

单条请求在 decode 阶段每次只算 1 个 token，GPU 算力被严重浪费。

**连续批处理（Continuous Batching）** 的核心思想：把"不同请求、不同进度"的 decode step 动态拼进同一个 batch。vLLM / SGLang / TGI 都实现了这一思想。

```
时刻 t:
  请求A 在 decode 第3步 (已生成 3 token)
  请求B 刚到达, 需 prefill
  请求C 在 decode 第1步
  → 三者合并成一个 batch, 一次 kernel 推进
```

这与《GPU》第 4 章的"延迟隐藏 + Streams"完全同构：**用足够多的就绪计算填满 SM 的执行槽**。差别是这里"就绪"的是"不同请求的 micro-step"，调度器从 CPU 端的批处理队列换成 GPU 上的 warp 调度器。

> 工程要点：连续批处理的效果取决于 **调度器能不能及时把新请求喂给 GPU**。如果 Host 端取数据慢（数据预处理、Tokenizer 瓶颈），GPU 仍会空转——这与《GPU》第 8 章"util 低且空转 = Host 喂不上"一致。

---

## 3. KV Cache 分页：把显存当虚拟内存管

自回归生成需要缓存每层的 Key/Value。若按"最大长度预分配"，显存会被碎片和预留撑爆。

**PagedAttention（vLLM）** 借鉴操作系统的 **分页** 思想：把 KV Cache 切成固定大小的 block，像虚拟内存一样按需分配/回收。收益：
- 消除"为最长请求预留"的浪费，显存利用率从 ~20% 提升到 ~90%+。
- 不同请求可共享前缀（如系统提示词）的 KV block，进一步省显存。

这是"共享"思想的另一层落地：**块级共享 + 引用计数**。它和《GPU》第 5 章"共享内存/L2 是协作高速区"是同一哲学在系统层的放大。

---

## 4. prefill 与 decode 分离：进程级协作

prefill（处理 prompt，大矩阵乘，计算密集）与 decode（逐 token，访存密集，长尾）混在同一 batch 会互相拖累。先进框架（DistServe / Splitwise 思想）把二者拆成 **两个进程组**：

```
用户请求 → [Prefill 进程组] 算 KV → (KV Cache 传输: NCCL 跨卡 / IPC 同卡) → [Decode 进程组] 生成 → 返回
```

这恰好是《GPU》第 7 章讲的"流水线范式"：两个进程组通过 **NCCL（跨卡）或 CUDA IPC（同卡共享 HBM）** 衔接 KV Cache。分离后两侧各自按最优 batch 策略调度，整体吞吐可提升数倍。

> 生产建议：若两阶段在同一张卡上，用 **MPS** 合并提交 + **IPC 共享 KV 显存**，避免上下文切换；若跨卡，用 NVLink + NCCL 做 KV 搬运。

---

## 5. 推测解码：用"小模型草稿 + 大模型校验"提速

decode 慢的根因是"每步只产 1 token，且受限于内存带宽（memory-bound）"。

**推测解码（Speculative Decoding）**：用一个小的草稿模型（draft）一次预测 k 个 token，再让大模型 **并行校验** 这 k 个 token，全部接受则一次前进 k 步。

```
草稿模型(小,快): 预测 [t1 t2 t3]
大模型(大,慢): 并行校验 t1,t2,t3 → 全接受 → 前进3步
平均接受率 ~0.7 → 吞吐提升 ~3-4×
```

最近论文 *Speculative Serve* 把"推测解码 + 分页 KV Cache"结合，让 2.8T 模型在 **单卡** 也能提供可观吞吐。这与《GPU》第 8 章"单卡服务超大模型"的诉求直接呼应。

---

## 6. 多进程共享：MPS / MIG 怎么选

当多个模型/多实例要共用一卡（省钱），回到《GPU》第 6 章的三种方案：

| 方案 | 适用 | 风险 |
|---|---|---|
| 默认时间片 | 轻量、互不干扰 | 上下文切换清空 L2，OOM 互不影响 |
| **MPS** | 同信任域、要低延迟共享权重 | 共享上下文，**一崩俱崩** |
| **MIG** | 多租户、要 SLA 强隔离 | 切片粒度粗，不能跨实例组 NCCL |

对"同一可信推理栈的多模型拼卡"：用 MPS + IPC 共享权重最省显存；对"不同客户隔离"：用 MIG 给每个客户固定切片。注意 **Linux cgroup 不能限制 GPU**，所有按份额隔离都靠 MPS/MIG/厂商扩展（如 qGPU、cGPU）。

---

## 7. 一条可落地的部署清单

1. **选权重格式**：优先官方 MXFP4/FP8 量化权重（Kimi K3 / DeepSeek V4 均提供）。
2. **选引擎**：vLLM / SGLang 已原生支持 FP8 权重 + 连续批处理 + PagedAttention（2026-07-28 两家的更新已适配 Kimi K3 / V4）。
3. **定并行**：单卡装不下就 TP/EP 切分；多卡走 NVLink 最快。
4. **分离 prefill/decode**（高吞吐场景），用 NCCL/IPC 传 KV。
5. **开推测解码**提升 decode 吞吐。
6. **省显存**：多实例用 MPS+IPC 共享权重；多租户用 MIG。
7. **监控**：`nvidia-smi dmon` 看 util/显存，`nvidia-smi topo -m` 看 NVLink 拓扑，DCGM 长跑采集。

---

## 8. 小结

服务万亿参数开源模型，本质是 **把《GPU 工作原理与并发模型》里的每一层知识落到系统工程**：
- 量化/切分 → 硬件显存与 Tensor Core（第 2 章）
- 连续批处理 → warp 调度与延迟隐藏（第 4 章）
- KV 分页/共享 → 内存层次与数据共享（第 5 章）
- prefill/decode 分离、推测解码 → 多进程协作（第 7 章）
- MPS/MIG → 多进程共享（第 6 章）

当你把"GPU 是一台为并行而生的协处理器"这件事想透，超大模型推理就从"玄学调参"变成"资源编排"——而这，正是开源权重真正普及的最后一公里。
