# 第 2 章 · 词表选哪个：三套方案的取舍与 75840 的四段划分

「词表怎么体现」这个问题的第一层答案是：**先决定要不要词表**。这不是修辞，全模态模型在这里分成了三条互不兼容的路线。

## 2.1 三套方案对照

| | 方案 A · 全离散统一词表 | 方案 B · 混合式（本书选） | 方案 C · 全连续 |
|---|---|---|---|
| 输入侧 | 三种模态都量化成 ID | 文本/音频 ID，视频连续向量 | 三种都连续向量 |
| 输出侧 | 一个 head 采所有模态 | 一个 head 采文本/音频/视觉 ID | 各模态专用扩散/DiT 头 |
| 代表 | Chameleon、Emu3、早期融合 Omni | Qwen2.5-Omni、LLaVA 类 + codec、Moshi 变体 | SGLang Diffusion、FLUX、多数 DiT |
| 词表 | 一张，四段分区 | 一张，四段分区（输入侧视觉不查） | 无词表 |
| 训练目标 | 全部共用 CE loss | 离散部分 CE，连续部分对齐/回归 | 回归 / 流匹配 / 对比 |
| 优点 | 最纯粹，一个 next-token 吃下所有模态 | 理解侧保真，生成侧可采样 | 音质画质上限最高 |
| 代价 | 视觉量化白丢细节、码本难训 | 两套表示要小心对齐 | 不能和文本共用主干、无法统一采样 |

**本书选 B**，理由回到例子：摄像头画面只用来回答「这个是什么」，不需要被生成出来；而回答的语音必须被采样出来变成波形。一个只「读」的模态没必要量化，一个要「写」的模态必须有离散 ID。

> **2026-11-07 校准（重要）**：Higgs Realtime Duplex 官方**没有公开词表结构**。从技术博客可确认的是「每个 chunk 输出 2 个音频 frame + 2 个图像 latent，交给因果流匹配解码器与因果 DiT 还原波形与画面」——**输出侧是连续 latent + 生成式解码，不是离散 ID 查 softmax**。也就是说真实量产全双工更接近方案 C（全连续）或「主干离散文本 + 输出连续 latent」的第四条路线，而不是本书为了讲清「词表怎么体现」而选的 B。本书选 B 的教学价值仍在（它是唯一能把 ID 区间、logits mask、状态机讲透的设定），但**不能当成业界共识**。详见第 11 章。

方案 A 的诱惑是架构最干净，但把 448×448 的画面塞进 8192 项码本，等于主动丢掉金属杯上那道关键的镜面高光——而例子里恰恰要靠它判断材质。方案 C 音质画质最好，但没有统一序列，双流、打断、指代消解全都要另起炉灶。

## 2.2 75840 怎么切：一张可查的表

```python
V, d = 75840, 4096
E    = nn.Embedding(V, d)      # 唯一一张词表：75840 行 × 4096 列
head = nn.Linear(d, V)         # 唯一一个输出头

TEXT  = range(0,     65536)    # 65536 项  文本 BPE
IMAGE = range(65536, 73728)    #  8192 项  视觉 VQ codebook
AUDIO = range(73728, 75776)    #  2048 项  音频 RVQ codebook
CTRL  = range(75776, 75840)    #    64 项  控制符
# 65536 + 8192 + 2048 + 64 = 75840
```

四个区间**不许重叠**。重叠的后果不是报错，而是静默错误：`which_modality()` 会把一个图像 ID 判成文本，采样出一句乱码，而训练 loss 看起来完全正常。

具体 ID 手册（全书都会用到这些数字）：

| 整数 ID | 含义 | 区间 |
|---|---|---|
| `5821` | 「这个」 | 文本 |
| `12847` | 「不」 | 文本 |
| `20311` | 「能」 | 文本 |
| `33092` | 「金属」 | 文本 |
| `41003` | 「会打火」 | 文本 |
| `67102` | 金属高光的视觉码 | 视觉 |
| `68034` | 杯盖塑料的视觉码 | 视觉 |
| `74012` | `/bu/` 语义层 | 音频 |
| `74105` | 音色层 | 音频 |
| `74390` | 气息层 | 音频 |
| `75776` | `BOV` | 控制 |
| `75777` | `EOV` | 控制 |
| `75778` | `BOA` | 控制 |
| `75779` | `EOA` | 控制 |
| `75780` | `SIL` | 控制 |
| `75781` | `HMM`（附和「嗯」） | 控制 |
| `75782` | `BARGE_IN`（打断） | 控制 |
| `75783` | `EOS` | 控制 |

`E[12847]` 就是取第 12847 行，得到 4096 个浮点数，例如 `[0.021, -0.037, 0.014, …, 0.008]`。**ID 是行号，词表是一张可学习的浮点矩阵**——这就是「词表怎么体现」最直白的答案。

## 2.3 码本规模怎么定

三个区间的大小不是拍脑袋：

| 区间 | 规模 | 依据 |
|---|---|---|
| 文本 | 65536 = 2^16 | BPE 词表常规量级，中文效率与 embedding 参数量的折中 |
| 视觉 | 8192 = 2^13 | VQ-VAE 单码本经验值；再大码本利用率下降、易出现死码 |
| 音频 | 2048 = 2^11 | 单层 RVQ 码本；8 层叠加给出 2048^8 的有效组合，实际码率 1.1 kbps |
| 控制 | 64 | 够放边界符、静音、附和、打断、模态标记、EOS |

音频这里有个容易算错的地方：**2048 是每一层的码本大小，不是整个音频的词表大小**。8 层 RVQ 每层都在这同一本 2048 码本里取值，靠「第几层」区分语义/声学角色。所以 `AUDIO` 区间只有 2048 项，但一片要采 8 次。

码率核对：

```
12.5 帧/秒 × 8 层 × 11 bit = 1100 bit/s ≈ 1.1 kbps
```

对比 PCM：`24000 × 16 bit = 384 kbps`。压缩约 350 倍，且仍可懂。

## 2.4 码本是怎么训练出来的（VQ-VAE 三项 loss）

8192 项视觉码、2048 项音频码都不是人工指定的，是 `nn.Embedding(K, D)` 随机初始化后和 encoder/decoder 一起学出来的：

```python
def quantize(z_e, codebook):
    # z_e:      [B, H, W, D]   连续特征
    # codebook: [K, D]         K=8192, D=128
    distances = (z_e.unsqueeze(-2) - codebook).pow(2).sum(-1)  # [B,H,W,K]
    ids = distances.argmin(-1)                                 # [B,H,W]
    z_q = codebook[ids]                                        # [B,H,W,D]
    return ids, z_q

L = L_recon + L_codebook + beta * L_commit
# 重建 loss 更新 encoder+decoder；codebook loss 只更新码本；
# commitment loss 只更新 encoder（beta 常取 0.25）
```

`argmin` 不可导，用直通估计器绕过：`z_q = z_e + (codebook[ids] - z_e).detach()`。

训练直觉：码本像散落在特征空间里的一堆磁铁，每个 encoder 输出把最近的磁铁吸向自己，同时自己也被吸回去。久了之后 `67102` 这类码会稳定代表「金属高光」，`68034` 代表「哑光塑料」。**ID 的语义是训练涌现的，不是设计出来的**——所以换一个 codec 版本，整张表都要重新对齐，这也是词表版本必须锁进模型 checkpoint 的原因。

音频侧再加一层 split RVQ：把 8 层拆成并行的「1 层语义 + 7 层声学」，第一层用 WavLM 特征蒸馏监督，后 7 层只管音色韵律。Mimi 的消融显示这比级联 RVQ 蒸馏把 MUSHRA 从 57.8 提到 64.0——因为语义层不再被迫在残差里背下全部声学信息。

## 2.5 一个 ID，两套向量（最关键的工程细节）

音频 ID `74012` 会被查两次，查的是**两张不同的表**：

```python
z_llm = E[74012]                       # [4096] 给 Transformer 当 embedding
z_wav = codec.codebook[74012 - 73728]  # [128]  给解码器还原波形
```

| | `E` | `codec.codebook` |
|---|---|---|
| 形状 | `[75840, 4096]` | `[2048, 128]` |
| 学自 | 语言建模 loss | 波形重建 + 对抗 + 感知 loss |
| 用途 | 进主干做语义计算 | 出信号做声学重建 |
| 绑定方式 | ID | `ID - 73728` 偏移 |

视觉同理：`67102 - 65536 = 1566` 才是 VQ decoder 的码本下标。**一个整数 ID 同时是「语义表的行号」和「声学/像素码本的行号」，靠区间偏移绑定**——这是全模态工程里最容易被漏掉的一根线，漏了就会在生成时拿到完全错误的波形。

## 2.6 选型决策树

```
要生成画面吗？
├─ 要，且想和文本共用一套 next-token → 方案 A（全离散统一词表）
│    代价：视觉量化误差、码本训练、主干被多模态梯度拉扯
├─ 要，但画面走扩散/DiT 分支 → 方案 B + 生成侧独立 VQ（第 8 章）
│    本书路线：理解侧连续，生成侧才量化
└─ 完全不生成画面，只出文本+语音 → 方案 B 的最小版
     视觉区间可以整段砍掉，V = 67648
```

如果只做「边看边听边说」不出画面（站内 GPT-Live-1、SeedRealtime 的产品形态），`IMAGE` 那 8192 项其实是闲置的。保留它的唯一理由是将来要扩成出图；否则直接砍掉能省 `8192 × 4096 × 2B ≈ 64MB` 的 embedding + 同等规模的 head 参数。

## 2.7 三个常见误解

1. **「三种模态各有各的词表」** → 只有一张 `E`，四段分区；三套 encoder 产出的东西形态不同，但查表用的是同一张矩阵。
2. **「视频输入也要查表」** → 理解侧不查表，`x_vis = resampler(vit(frame))` 这一行没有 `E`。只有生成画面时才采视觉 ID。
3. **「控制符是特殊逻辑」** → `BOV/EOV/BOA/EOA/SIL/HMM/BARGE_IN` 都是词表尾部的**普通 token**，靠训练数据学会状态切换，不是硬编码的 if-else。推理时拼一个字符串 `"<video>"` 是无效的，模型从没见过它作为独立 ID。

## 2.8 本章小结

- 三套方案：全离散（干净但丢细节）、混合式（本书）、全连续（音画最好但无统一序列）。
- `V=75840` 切成 65536 文本 / 8192 视觉 / 2048 音频 / 64 控制，区间绝不重叠。
- 音频 2048 是**每层**码本，8 层 RVQ 共采 8 次；码率 1.1 kbps。
- 码本靠 VQ-VAE 三项 loss + 直通估计器训练，ID 语义是涌现的，版本必须锁进 checkpoint。
- 一个 ID 绑两套向量：`E[id]` 进主干，`codec.codebook[id - offset]` 出信号。
- 只出文本+语音的产品可以整段砍掉视觉区间，省约 64MB 参数。
- ⚠️ **真实产品未必有统一离散词表**：Higgs 输出侧用连续 latent + 双解码器，官方未公开词表；本书四段分区是教学设定，第 11 章逐条对账。
