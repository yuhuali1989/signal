## 6.1 marimo 已经给了什么（不用从零做）

| 能力 | 机制 | 状态 |
|---|---|---|
| **`marimo pair`** | 把任意 agent（Claude Code、Codex、OpenCode 等）**连接到正在运行的 marimo session** | ✅ 已有 |
| **编辑器内置 AI** | 生成 cell、改写、解释；支持**自带 API key、自定义 system prompt、本地模型** | ✅ 已有 |
| **上下文感知** | AI 能看到内存中的变量 | ✅ 已有 |
| **数据感知生成** | 基于实际 dataframe 生成代码 | ✅ 已有 |

> ★**这是 marimo 相对 Jupyter 的一个结构性领先**：它把「agent ↔ kernel」的通道做成了产品能力，而不是等你自己在 notebook 外面拼。自建平台要做的**不是重做这条通道，而是把它接到内部模型、并加上边界**。

## 6.2 内部接入方案

```
                 ┌─────────────────────────┐
                 │   内部模型 / Agent 网关   │
                 │  （统一鉴权、限流、审计） │
                 └───────────┬─────────────┘
                             │  OpenAI 兼容接口 / 私有协议
              ┌──────────────┼───────────────┐
              ↓              ↓               ↓
     编辑器内置 AI      marimo pair      定时任务里的 AI 步骤
   （自带 key 指向内部）  （外部 agent 连入）   （服务端调用）
              ↓              ↓               ↓
                     ★统一审计与脱敏
```

| 接入点 | 做法 | 要点 |
|---|---|---|
| **编辑器 AI** | 在会话启动时把「内部模型端点 + 临时凭证」注入环境变量 | ★凭证不进 notebook；端点可配置为内部地址 |
| **`marimo pair`** | 允许 agent 连接运行中的 session；需在网关层做鉴权与审计 | ★最强大的能力，也最需要边界（见 6.4） |
| **系统提示词** | 定制 system prompt：注入公司数据字典、规范、常用库用法 | ★**这是提升生成质量最划算的一招** |
| **本地/私有模型** | marimo 支持本地模型；指向内部推理服务即可 | 数据不出内网 |

**推荐的系统提示词内容**（投入极小、收益极大）：

```
- 公司内部数据源清单与每张表的核心字段（数据字典摘要）
- 公司内部公共库的用法示例
- 输出规范：必须用 PEP 723 声明依赖；不要跨 cell 修改对象；SQL 优先下推
- 禁止事项：不要写死凭证；不要全表 SELECT *
```

## 6.3 AI 的两种范式（与引擎设计直接相关）

呼应「AI Native Notebook」的架构分野，marimo 走的是**内生式**：

| | 外挂式（工具调用） | **内生式（marimo pair）** |
|---|---|---|
| Agent 在哪 | notebook 之外，通过 API/MCP 访问 | ★**连接到运行中的 session** |
| 能否读运行时状态 | 不能（只能读文件） | ★**能读内存变量** |
| 能否执行并看到真实结果 | 需额外搭环境 | ★**直接在 kernel 里跑** |
| 生成代码的可信度 | 靠人审 | ★**跑过才有输出**（呼应「数字必须是跑出来的」） |

> 这一点对内部平台的说服力很强：**让 AI 生成的代码必须在 kernel 里真的执行过才成为结论**——这从根本上区别于「让模型直接写一份 HTML 报告」（数字可能是编的）。

## 6.4 典型场景与价值

| 场景 | 做法 | 价值 |
|---|---|---|
| **取数/写 SQL** | 描述需求 → 生成 SQL cell → 直接跑出结果 | ★分析师最高频痛点，省时明显 |
| **探索加速** | 让 AI 基于内存里的 dataframe 写清洗/可视化 | 上下文感知，比凭空生成准得多 |
| **改错** | 报错丢给 AI，在真实 session 里改到跑通 | 闭环验证 |
| **解释与文档** | 为 notebook 生成说明、动态 markdown | 提升可交接性 |
| **生成 app 骨架** | 从分析 notebook 生成带控件的 app | ★加速交付（第 4.7 节的价值放大器） |

## 6.5 ★ 安全边界（必须写进设计与规范）

能力越强，边界越要清楚。以下建议直接作为平台规则：

| 边界 | 要求 |
|---|---|
| **模型端点** | ★默认指向内部模型；用外部模型须显式开启并告知（数据出境风险） |
| **数据脱敏** | 发给模型的上下文做敏感字段过滤/脱敏（手机号、身份证、密钥） |
| **凭证** | ★AI 生成的任何代码**不得包含凭证**；平台侧做静态检查拦截 |
| **危险操作** | 禁止 AI 直接执行删除/写入生产库/对外发布；**高危动作必须人工确认** |
| **人在回路** | AI 的修改可 diff 查看、可撤销；重要 notebook 需 review |
| **审计** | 记录：谁的模型、什么提示词（可脱敏）、执行了什么、消耗多少 token |
| **成本** | 按空间/人设 token 配额，避免「AI 刷爆账单」 |

> **一条硬原则**：**AI 可以建议，执行要可追溯；AI 可以写，但凭证和数据边界由平台强制，不靠提示词自觉。**

## 6.6 落地顺序（AI 不必第一天就上）

| 阶段 | 做什么 |
|---|---|
| **一期** | 只做「编辑器 AI 指向内部模型 + 系统提示词定制」，成本极低（1–2 人周） |
| **二期** | 开 `marimo pair`（agent 连入）+ 审计 + token 配额 |
| **三期** | 定时任务里的 AI 步骤、AI 生成 app 骨架、模板推荐 |

> **建议**：AI 接入**一期就做「指向内部模型 + 提示词」**——投入 1–2 人周，但因为数据安全与生成质量提升，感知很强；`marimo pair` 这种强能力放到二期，配齐审计再开。

## 6.7 本章要点

- marimo 已提供 **AI 通道**（`marimo pair` 连运行中 session + 编辑器 AI 支持自带 key/本地模型/自定义 prompt），**平台不要重做，只做「接内部 + 加边界」**。
- 接入三件套：**内部模型端点 + 会话注入临时凭证 + ★定制 system prompt**（注入数据字典与规范，性价比最高）。
- ★**内生式（agent 在 kernel 执行）意味着 AI 生成的代码必须真的跑过才成为结论**——区别于「直接生成 HTML 报告」的编数字风险。
- 场景价值：SQL 生成 > 探索加速 > 改错闭环 > 文档 > app 骨架。
- ★边界：**端点默认内部、上下文脱敏、代码不得含凭证、高危动作人工确认、全链路审计、token 配额**。
- 节奏：一期只做「指向内部模型 + 提示词」（1–2 人周），`marimo pair` 二期配齐审计再开。
