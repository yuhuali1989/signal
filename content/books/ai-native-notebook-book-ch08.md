## 8.1 决策树：按顺序问自己五个问题

```text
Q1: 你要解决的核心痛点是什么？
    ├─ 结果不可复现 / 执行顺序混乱  → 响应式（Marimo）
    ├─ 结果交付不出去 / 要变 app     → Hex（app mode）
    ├─ 多人协作 + 调度 + 免运维      → 协作 SaaS（Deepnote / Hex）
    ├─ 结果要出版成论文/报告/书      → Quarto
    └─ 只是要个自由的分析环境        → JupyterLab 5

Q2: 有强制的语言需求吗？
    ├─ 需要 R / Julia / Scala 等非 Python → Jupyter（内核最广）
    └─ Python（+SQL）为主                 → 继续

Q3: 数据与合规允许上云吗？
    ├─ 不允许（数据必须本地/私有）→ 本地/自托管（Jupyter / Marimo / 私有化）
    └─ 允许                        → 继续

Q4: 团队规模与协作需求？
    ├─ 1 人                 → Jupyter / Marimo（免费、自由）
    ├─ 3–8 人、常给业务方看  → Hex
    └─ 数据科学团队、要托管  → Deepnote

Q5: AI 要深到哪一层？
    ├─ 只要补全/生成         → 任何平台（差异不大）
    ├─ 要 agent 自主跑并改   → 看执行保证：Marimo pair（深度）或 Jupyter AI v3（广度）
    └─ 要接自己的模型端点     → 确认平台支持自定义 OpenAI 兼容端点
```

## 8.2 典型企业落地架构（推荐：分层混合）

不要指望一个工具满足所有场景。**按用途分层**通常最稳：

```text
① 探索层（个人本地）
   JupyterLab 5 / Marimo 本地
   → 自由探索、离线、快速试错

② 协作分析层（团队云端）
   Deepnote / Hex
   → 实时协作、数据连接、Modules 复用、参数化调度

③ 交付层（结果出口）
   Hex app mode / Deepnote data apps / Quarto 报告
   → 给不看代码的人：交互 app、定时报告、发布页面

④ 治理层（贯穿）
   版本控制（纯文本优先）、AI 用量与成本、权限与审计、数据驻留
```

**关键原则**：

- **探索层要自由**（别给探索加太多流程）
- **生产任务要纪律**（参数化、调度、告警、review）
- **交付层要短**（分析到交付的路径越短越好）
- **治理层要横切**（不因工具切换而失效）

## 8.3 迁移路径：从 Jupyter 出发怎么走

大多数组织已有大量 .ipynb。迁移是真实成本，不是开关。

| 目标 | 路径 | 成本 |
|---|---|---|
| **留在 Jupyter，改善工程性** | jupytext（.ipynb↔.py 配对）+ 清输出 + papermill 调度 + Voila/Quarto 发布 | 低（渐进） |
| **迁到响应式（Marimo）** | 用 Marimo 的迁移/转换能力把 .ipynb 转 .py；**需要重新梳理依赖**（响应式要求顺序正确） | 中（要重构依赖） |
| **迁到协作 SaaS** | 导入 .ipynb（Deepnote 兼容；还支持从 Quarto / percent / marimo 转换） | 低–中（格式友好） |
| **混合（推荐）** | 历史 .ipynb 留在 Jupyter；新项目用响应式或 SaaS | 最低 |

**务实建议**：**不要为了换工具而全量迁移**。用"新项目用新工具、老项目按需迁移"的方式演进，风险最低。

## 8.4 成本模型

总拥有成本 = 许可 + 运维 + AI 用量 + 迁移/学习。

| 项 | Jupyter（自托管） | Marimo（开源） | Deepnote | Hex |
|---|---|---|---|---|
| 许可 | 0 | 0 | ~$29/editor/月 | ~$38–65/seat/月 |
| 运维 | **高**（环境、扩展、调度、发布都要自建） | 低–中 | 0（托管） | 0（托管） |
| AI 用量 | 取决于接的模型 | 取决于接的模型 | 平台内计量 | 平台内计量 |
| 学习/迁移 | 0（已会） | 中（响应式心智） | 低（.ipynb 兼容） | 中（专有格式） |

**判断方法**：把"自建这些能力（协作/调度/发布/环境管理）要多少人力"折成钱，再和订阅费比。**很多团队低估了自运维 notebook 平台的隐性人力成本**。

## 8.5 上线 Checklist

### 通用
- [ ] 明确核心痛点（可复现 / 协作 / 交付 / 出版），不追求"最好"的工具
- [ ] 用**同一批真实任务**在候选平台上实测（别看演示）
- [ ] 确认语言与内核覆盖你的技术栈
- [ ] 确认部署形态符合数据与合规要求（能否上云）

### 可复现
- [ ] 执行模型明确（有状态 or 响应式）
- [ ] 从零跑一遍结果与展示一致（第 5 章 Checklist）
- [ ] 依赖完整锁定（镜像 / 锁文件），随机种子固定
- [ ] 纯文本或可 diff 的格式；输出不污染仓库

### AI
- [ ] AI 能力到达你需要的层级（L4/L5？）
- [ ] Agent 的改动**可审查**（进 diff / PR）
- [ ] Agent 权限最小化、操作可审计
- [ ] 能否切换模型 / 接自建端点（合规与成本）
- [ ] AI token 成本可见、可控

### 工程化
- [ ] 有复用机制（Modules / 包），避免口径漂移
- [ ] 调度与参数化运行、失败告警
- [ ] 发布路径（app / 报告）符合交付需求
- [ ] 协作与权限模型清晰
- [ ] 分层管理：探索 / 正式分析 / 定时任务 / 对外交付

### 安全
- [ ] 密钥托管（不硬编码在 cell）
- [ ] 数据连接权限细粒度
- [ ] 执行沙箱与资源限额
- [ ] 平台自身安全更新（如 Marimo ≥0.23.0 修复的 WebSocket 认证绕过 CVE-2026-39987）

## 8.6 全书总结

八章串成一条主线：**AI Native 不是给 Notebook 加个 AI 插件，而是让 AI 真正成为执行模型的一部分，并且让它继承可复现的执行保证。**

| 章 | 关键结论 |
|---|---|
| 第 1 章 | 四类版图（经典/响应式/出版/SaaS）；**跨类比较必错**；AI Native = AI 操作运行时 + 继承执行保证 |
| 第 2 章 | 五层架构；**AI 层两种范式**：外挂（MCP/ACP，兼容与广度）vs 内生（kernel 内执行，可复现与深度） |
| 第 3 章 | 有状态内核（自由但有 hidden state，约 96% 不可复现）vs 响应式 DAG（确定性、纯文本） |
| 第 4 章 | AI 五层能力；**上下文工程决定好不好用**；Agent 改动要提交前校验、可审查；模型可换/可接自建端点/成本可见 |
| 第 5 章 | 文件格式是可复现第一道门；环境锁定；数据下推比 AI 能力更决定大数据可用性 |
| 第 6 章 | **别只优化编辑器，要优化 notebook 之后**：协作、复用、调度、发布 |
| 第 7 章 | 全景对比；个人→Jupyter、交付→Hex、托管→Deepnote、可复现→Marimo、跨语言→Jupyter |
| 第 8 章 | 分层混合落地；渐进迁移；成本含隐性运维人力 |

**最后一句**：

> 选 Notebook 平台，本质上是在选**你希望团队的分析怎么被复现、怎么被协作、怎么被交付**。AI 让"写"变快了，但如果"跑得对、说得清、交得出"这三件事没解决，快只是更快地产生不可信的结果。
