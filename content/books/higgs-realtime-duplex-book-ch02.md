# 第 2 章 · 切时间，不切轮次：160ms 不是响应延迟

## 2.1 回合制与全双工的时间结构

绝大多数语音助手是「对讲机」：你说完 → 检测到停 → 转写 → 推理 → 合成 → 播放。整段时间里输入通道是关闭的，所以插话只能靠外挂 VAD 强行打断，且打断后模型往往仍以为你把整段回复听完了。

Higgs 的做法官方一句话概括：**Slice time, not turns**（切时间，不切轮次）。

| | 回合制 | 全双工分片 |
|---|---|---|
| 建模单位 | 一个 turn（数秒） | 一个 chunk（**160ms**【官方】） |
| 输入通道 | 输出时关闭 | **始终打开** |
| 静音 | VAD 判停后丢弃 | **静音也是 chunk，照样进模型** |
| 视觉流 | 通常只在轮次开始取一帧 | 静音期间帧持续流入 |
| 附和 / 打断 | 外挂 VAD + 状态机 | 模型自己决定何时说、何时停 |
| 后台任务 | 阻塞对话 | 异步，结果以 payload 回灌 |

一句话：**回合制是在「等人把话说完」，全双工是在「不停地把刚到的那一小段读进来、把下一小段写出去」**。官方原话是 `Each step, the model reads the chunk that just arrived and writes the chunk that plays next`。

## 2.2 ★160ms 不是响应延迟（本书最想纠正的误读）

中文解读里最容易出现的一句话是「AI 只需 160ms 就能回答问题」。这是错的，而且错得很关键：

| 数字 | 出处 | 到底是什么 |
|---|---|---|
| **160 ms** | 【官方】 | **系统组织输入输出的时间粒度**。所有流被切成这么长的片，每片做一次读+写 |
| **200 ms** | 【官方】 | **人类对话统计**：一方说完后另一方接话的典型间隔。是设计要对齐的目标，不是模型成绩 |
| **10 s+** | 【官方】 | 对「把全部推理甩给大型推理模型」的批评：那种模型可能十秒以上才答 |

官方**从未公布端到端响应延迟的实测值**。一个真实回答还可能包含网络传输、主干推理、工具执行、输出解码、播放缓冲。所以评价这类系统，至少要把三个时间分开量：

1. **打断后多久停止原来的输出**（barge-in latency）；
2. **用户说完后，多久开始给出有意义的回应**（不只是「我来查一下」这种填充语）；
3. **一项实际任务多久被正确完成**（可能十几秒，因为要等工具）。

一个助手可以 160ms 内说出「我查一下」，但查询仍要等 8 秒；也可以 300ms 才开口，却立刻给出做完的结果。**把片长当响应速度，等于把采样率当算力。**

## 2.3 六条泳道：官方八步图还原

官方配图里是 `t-7 … now` 八个格子、每格 160ms。把六条泳道按格铺开（★格内事件为官方图注描述，本书按时间顺序排布）：

| 泳道 | t-7 | t-6 | t-5 | t-4 | t-3 | t-2 | t-1 | now |
|---|---|---|---|---|---|---|---|---|
| 你的语音 | 讲 | 讲 | 讲 | 讲 | 讲 | — | — | **插话** |
| 你的摄像头 | 帧 | 帧 | 帧 | 帧 | 帧 | 帧 | 帧 | 帧 |
| 外部结果 | | | | | | part1 | part2 | part3 |
| 它的语音 | | **mm-hm** | | | | **停下** | | **作答** |
| 它的面部 | 渲染 | 渲染 | 渲染 | 渲染 | 渲染 | 渲染 | 渲染 | 渲染 |
| 它的思考 | | | 思考 | 调工具 | | **重规划** | **委派** | |

三条最容易被漏掉的读法：

- **面部每步都在渲染**，不是「有话要说才出画面」——输出侧面部流与语音流同样是连续的。
- **思考与工具调用的生成跨多个 chunk**，把这几格拼起来才是完整的输出流（官方：`concatenating those chunks recovers the full output stream`）。
- **工具结果分三个 input chunk 到达**，模型不等完整结果就开始说——这是「后台不阻塞快流」在时间轴上的具体形态。

## 2.4 静音为什么要占一格

官方两句连着写，缺一句就理解偏：

> `Silent intervals are represented as chunks too.`
> `With video enabled, frames keep streaming in even during silence, so the model never stops listening and watching.`

静音不是一个可以跳过的空白，而是一个**合法的输入状态**。理由有三层：

1. **模型仍需决定要不要开口**。附和、等待、抢话、保持安静，这些判断都发生在「用户没说话」的片里。静音若被 VAD 丢掉，模型就失去了练习这些决策的输入。
2. **视觉信息没有停**。用户不说话时可能在看白板、皱眉、把杯子转个面、在书上指着某一行——这些都是后续回答的依据。
3. **上下文按墙钟增长**。全双工不区分「有没有在说话」，每片都要算，所以省算力不能靠跳静音，只能靠把每片 token 压到极低（第 4 章）。

回到贯穿例子：`t=3040ms` 工程师在读书，麦克风是静音，但摄像头帧照常进来；`t=3200ms` 他忽然说「先别看价格，重点比维护成本」——模型能立刻反应，正因为静音那几片里它一直在看、一直在跑。

**与上一章那本教学基准书的差异**：那边 4.5 节写过「画面没变化就整片跳过」，Higgs 校准时已收紧为「视觉是否跳过只看画面变化，与用户有没有在说话无关」。本书沿用收紧后的规则，并再补一句：**连音频静音本身也不该成为跳片的理由**。

## 2.5 时间片长度是权衡，不是越短越好

| 片长 | 好处 | 代价 |
|---|---|---|
| 更短（80ms） | 交互更灵敏、打断更快 | 每秒片数翻倍 → 主干前向次数翻倍、序列更长、调度更频繁 |
| **160ms【官方】** | 与人类 200ms 节奏同量级、留出单步算力余量 | 单次最坏延迟至少一片 |
| 更长（300ms+） | 吞吐好、调度省 | 把「抬手—停顿—开口」压进同一片，因果顺序糊掉 |

160ms 的巧妙之处在于它给「每片算完一次前向 + 两个 decoder」留了余量，同时仍小于人类 200ms 的话轮间隔。**决定体验的不是片长本身，而是每片能否稳定在片长内算完**——一旦某片超时，双流立即失步，后面所有片都要追赶。

## 2.6 与教学基准书的对照

| | 《全双工全模态工程全书》前 10 章 | Higgs【官方】 |
|---|---|---|
| 片长 | 80 ms | **160 ms** |
| 每片 token | 87（视觉 64 + 音频 16 + 边界/文本） | 约 7（第 3 章算） |
| 静音 | `SIL` 控制符，视觉片可跳 | 静音即 chunk，视频帧持续流入 |
| 输出画面 | 几乎不逐 token 采，走异步分支 | **每片 2 个 latent → 因果 DiT，面部连续渲染** |
| 主干 | 7B dense / 32 层 / d=4096 | 45B MoE，配置未公开 |

教学基准的作用是让每个 shape 能手算；Higgs 的作用是给出真实预算。本书后面 10 章，一律以 Higgs 数字为准，教学基准只在对照时出现。

## 2.7 本章小结

- 建模单位从 turn 变成 160ms chunk；输入通道始终打开，静音是合法状态。
- **160ms 是分片粒度、200ms 是人类统计、官方没公布端到端延迟**；三个时间尺度（停 / 开口 / 办完）必须分开量。
- 六条泳道里，面部每步渲染、思考跨多片、工具结果分三片到达。
- 静音期间视频帧持续流入，是「模型从不停止听和看」的实现方式，也是指代消解与打断的前提。
