# 第 3 章 · 文本与音频怎么 embedding：两次查表与 12.5Hz 的来历

回到 `t=3200ms`。这一章只做一件事：把文本和音频这两路，从原始信号一路算到 4096 维向量，每个数字都落地。

## 3.1 文本：一次最朴素的查表

```python
t_ids  = torch.tensor([5821])     # 「这个」
x_text = E(t_ids)                 # [1, 4096]
```

`E` 是 `nn.Embedding(75840, 4096)`，`E[5821]` 就是把第 5821 行整行取出来。没有卷积、没有归一化、没有投影——文本是全模态系统里唯一「向量完全来自查表」的模态。

一个语义提醒：这里的「这个」**不是 ASR 转写**。全双工系统里没有 ASR 模块，这句文本是模型自己在生成音频之前，先在心里预测的时间对齐文本 token。它的作用在第 7 章讲，但先记住它的身份：`type=0, stream=1`（模型流），是内心独白，不播放。

## 3.2 音频：先量化成 8 个整数，再查同一张表

```python
wav   = mic.read()                 # [1920]  24kHz × 0.08s
a_ids = mimi.encode(wav)           # [8]     8 个整数，例如：
#       [74012, 74105, 74208, 74291, 74333, 74362, 74381, 74390]
x_aud = E(a_ids)                   # [8, 4096] ← 同一个 E，不是另一张表
```

注意 `a_ids` 全部落在 `[73728, 75776)`。这 8 个整数是**同一帧的 8 层残差量化结果**，不是 8 个连续采样点。第一层管「说了什么」，后七层一层层补「听起来像谁、什么情绪、什么气息」。

## 3.3 1920 → 8：Mimi 编码器的精确链路

```
24 kHz 波形 [1920]
   │
   ├─ 4 个残差卷积块，步长分别 4, 5, 6, 8
   ├─ 末端一维卷积，步长 2
   │      总步长 = 4×5×6×8×2 = 1920
   │      帧率  = 24000 / 1920 = 12.5 Hz  → 每帧 80 ms
   ▼
连续 latent [1, 128]
   │
   ├─ 因果 Transformer 瓶颈（8 层 / d=512 / RoPE / 上下文 250 帧）
   ▼
split RVQ：1 层语义码本 + 7 层声学码本（各 2048 项）
   ▼
8 个整数 ID
```

**12.5Hz 不是调出来的超参，是采样率和卷积步长的整数关系算出来的**。这个设计的全部价值在于：分帧等待只有 80ms（延迟账第一段），而文本 token 的生成速率也在同一量级，两种 token 可以自然交错进一条序列。

对比一下常见帧率，就知道它有多激进：

| 系统 | 送入主干帧率 | 每帧代表 | 相对 16kHz 压缩 |
|---|---|---|---|
| Mel 频谱 | 100 Hz | 10 ms | 160× |
| Whisper-large-v3 | 50 Hz | 20 ms | 320× |
| Qwen2.5-Omni | 25 Hz | 40 ms | 640× |
| **Mimi / Moshi** | **12.5 Hz** | **80 ms** | **1920×** |
| MiniCPM-o 4.5 | 10 Hz | 100 ms | 1600× |

5 分钟对话：100Hz 是 30000 帧，12.5Hz 只有 3750 帧——注意力计算差 64 倍、KV cache 差 8 倍。**帧率是语音架构里杠杆最大的一个数字**。

## 3.4 为什么必须全因果

所有卷积、Transformer 瓶颈、解码器都必须是 causal（只看过去）。

原因很直接：如果编码器要等「整段说完」或看未来 200ms 才能出这一帧的 token，那么 `80ms 分帧 + 40ms 首 token` 的延迟预算立刻崩掉，全双工变成回合制。传统语义 token（HuBERT / wav2vec 2.0）是非因果的双向编码器，音素区分度很好，但实时场景直接出局。

Mimi 的解法是**蒸馏**：用非因果的 WavLM 特征去监督第一层语义码本，把「未来的信息」在训练期灌进一个因果模型里，推理期不需要看未来。这和 AudioLM 那种「先生成语义骨架、再补声学」的两阶段方案形成对比——后者要跑两个编码器、还要等语义段生成完，实时性做不到。

## 3.5 split RVQ 为什么比级联蒸馏好

```
级联 RVQ（旧）：
  latent → VQ 层1(语义蒸馏) → 残差 → VQ 层2 → 残差 → … → VQ 层8
  问题：层1 被要求语义化后，它的残差必须背下全部声学信息 → 两个目标互斥

split RVQ（Mimi）：
  latent ─┬─→ VQ 语义分支（1 层，WavLM 蒸馏）
          └─→ VQ 声学分支（7 层，纯重建）
  两路输出相加送解码器，语义与声学不再抢同一份残差
```

消融结果：MUSHRA 57.8 → 64.0。更重要的副产品是**算力分工**：主干只需要学会第 1 层「说什么」，后 7 层更像「确定音色后的包装」，可以交给一个 6 层 / 1024 维的小模型（Moshi 的 Depth Transformer）。这是全双工能持续 decode 的前提。

## 3.6 三路文本/音频向量的汇总

到这一步，我们手上有：

```python
x_text     # [1, 4096]   「这个」，模型流，type=0
x_aud_user # [8, 4096]   用户语音 8 层，用户流，type=1
x_aud_model# [8, 4096]   自己上一片语音 8 层，模型流，type=1
```

三者的区别只有四处：

| | `type_id` | `stream_id` | `t` 口径 | 边界符 |
|---|---|---|---|---|
| `x_text` | 0 | 1 | 序号 / 时间片对齐 | 无 |
| `x_aud_user` | 1 | 0 | 绝对毫秒 3200 | BOA/EOA = 75778/75779 |
| `x_aud_model` | 1 | 1 | 绝对毫秒 3200 | BOA/EOA = 75778/75779 |

`type_emb` 和 `stream_emb` 都是逐元素相加的可学习向量：

```python
x_aud_user = x_aud_user + type_emb(torch.tensor(1)) + stream_emb(torch.tensor(0))
```

**不要用 concat 拼 type 标签**：`[1, L, 4096+4]` 会破坏 RMSNorm 的尺度和残差流，标准做法永远是加。

## 3.7 两套向量再确认一次

第 2 章讲过的绑定关系，在这里第一次真正被用到：

```python
# 进主干：语义向量
z_llm = E[74012]                        # [4096]

# 出信号（第 7 章）：声学向量
z_wav = codec.codebook[74012 - 73728]   # [128]
```

`codec.codebook` 是 `[2048, 128]`，`74012 - 73728 = 284`。同一个整数 74012，在主干里是第 74012 行 4096 维，在 codec 里是第 284 行 128 维。**两张表通过区间偏移绑死，换 codec 版本必须重新对齐 ID 映射**。

## 3.8 Inner Monologue 为什么不播放

这是最容易被误解的一处。模型在 `t=3200ms` 心里写了「这个」，在 `t=3360ms` 心里写了「不」，但用户一个字都看不到、听不到这些文本。

原因有三：

1. **保住语言能力**：文本流一直按 next-token 目标在跑，主干的语言建模能力不被语音 token 的分布拉扯。这是前几轮讨论的「多模态拖累文本」在结构上的解法——不靠冻结，不靠数据配比，靠把「说什么」和「怎么说」拆成两条流。
2. **给音频一个规划锚**：先定「不」，音频 codec 才知道该合成 `/bu/` 而不是别的音节。文本 token 与同一片的 8 个音频 token 在时间上一一对应，作为前缀指导生成。
3. **可解释性副产品**：这条文本流可以单独 dump 出来做审计，比读 8 层声学码友好得多。

Qwen2.5-Omni 的 Thinker-Talker 是同一思路的另一种实现：Thinker 只出文本和隐状态，Talker 独立小模型从隐状态出语音 token，文本能力完全不被语音训练触碰。

## 3.9 本章小结

- 文本 `E[5821]` 是纯查表；音频要先经 Mimi 量化成 8 个整数，再查**同一张** `E`。
- 12.5Hz 来自 `24000 / (4×5×6×8×2) = 12.5`，每帧 80ms；这是延迟与序列长度的联合最优。
- 全因果是硬约束，非因果语义编码器靠蒸馏把信息灌进因果 codec。
- split RVQ 把「1 语义 + 7 声学」并行拆开，音质更好且允许深度方向用小模型。
- 一个 ID 绑两套向量，靠 `ID - 区间起点` 偏移映射。
- Inner Monologue 不播放，作用是保语言能力、给音频当规划锚、留审计轨迹。
