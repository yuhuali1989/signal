## 6.1 A 方案的一致性：天然免费

A 直查 Iceberg 有一个**被严重低估的优势**：

> 它直接读 Iceberg 的**当前快照**（或指定快照），所以检索结果与你写进去的数据**永远一致**。

具体收益：

| 收益 | 说明 |
|---|---|
| **强一致** | 数据写进 Iceberg 后，下一次查询立刻能看到 |
| **无需同步** | 没有管道、没有延迟、没有漂移 |
| **可 time travel** | 可以查"截止到某个快照的数据"，检索结果可复现 |
| **无双写问题** | 不存在"一边成功一边失败" |

**一句话**：A 方案在一致性上是**零成本、零风险**的。

## 6.2 B 方案的一致性：最终一致 + 一堆债

B 要把 embedding 复制到 Milvus，于是引入了一整条同步链路：

```text
Iceberg（真源）──[同步管道]──→ Milvus（副本）──→ 检索服务
```

**必然的结果**：Milvus 里的数据**滞后于** Iceberg，是**最终一致**，不是强一致。

滞后的后果：

| 后果 | 表现 |
|---|---|
| **新数据检索不到** | 刚写入 Iceberg 的 embedding，Milvus 里还没有 |
| **删除不同步** | Iceberg 里删了，Milvus 里还能被检索到（"幽灵结果"） |
| **更新丢失** | embedding 重算了，Milvus 里还是旧的 |
| **版本漂移** | 两边数据量/版本对不上，且不易察觉 |

**这些问题的共同特点**：**静默出错**。检索看起来在工作，只是结果不完整或过期——业务方往往很久才发现。

## 6.3 快照与版本对齐：B 方案的必修课

既然有滞后，就必须能回答：

> "Milvus 里这份数据，对应 Iceberg 的哪个快照？"

**做法**：

| 做法 | 说明 |
|---|---|
| **记录水位** | 同步时把"已同步到 Iceberg 的哪个 snapshot id"持久化（下次从这里继续） |
| **原子导入** | 按快照批量导入；导入完成后再更新水位（先写数据，后更新水位） |
| **检索可声明版本** | 检索结果里带上"基于哪个 snapshot"，便于排查 |
| **回溯** | 出问题能快速定位"是哪次同步引入的" |

这与第 2 章讲的增量读水位是同一套思路——**任何"真源 + 副本"的架构，水位管理都是必修课**。

## 6.4 同步管道设计要点

| 环节 | 要点 |
|---|---|
| **首次全量** | 1 亿条 300 GB 的导入，要考虑批量大小、失败重试、耗时窗口 |
| **增量同步** | 用 Iceberg 增量读（快照差量）拿新增/变更行，避免每次全量扫 |
| **幂等** | 同步重跑不能产生重复向量——Milvus 侧用主键（id）upsert |
| **删除同步** | 必须处理删除（Iceberg 删了 → Milvus 也要删），这是最容易漏的 |
| **对账** | 定期比对两边条数、抽样比对向量，发现漂移告警 |
| **失败告警** | 同步失败/延迟超阈值要告警，别等业务投诉 |

## 6.5 典型故障模式与应对

| 故障 | 后果 | 应对 |
|---|---|---|
| 同步任务挂了 | Milvus 数据变旧，检索结果不完整 | 监控 lag + 告警；恢复后从水位续跑 |
| 部分批次失败 | 部分数据缺失 | 批次幂等 + 失败重跑 + 对账发现 |
| Milvus 写入重复 | 同一条出现多次，TopK 被污染 | 用主键 upsert（不是 append） |
| Iceberg 删除未同步 | 检索到已删除数据 | 同步管道必须处理 delete |
| Milvus 集群故障 | 检索服务不可用 | 副本 + 备份 + 降级方案（可临时回退到 A 直查！） |
| 版本升级不兼容 | 索引/数据读不了 | 升级前备份，灰度验证 |

**一个实用建议**：保留 A 直查能力作为**降级/兜底路径**。Milvus 出问题时，至少还能用 StarRocks 直接查 Iceberg（慢，但可用）。这种"双通道"设计在本架构里成本很低（A 本来就是写个 SQL 的事）。

## 6.6 监控指标（两边都要看）

**A 方案监控**（复用现有 SR 监控即可）：

- 查询延时 P50/P99
- 扫描量（字节/行）
- 集群 CPU / IO

**B 方案额外要监控**：

| 类别 | 指标 |
|---|---|
| 同步健康 | **同步 lag**（Milvus 落后 Iceberg 多久）、同步成功率、水位 |
| 一致性 | 两边条数差、抽样向量比对结果 |
| Milvus 集群 | QPS、延时 P50/P99、内存占用、索引健康、磁盘 |
| 检索质量 | 召回率（定期用标尺集评估）、空结果率 |

**重点是"同步 lag"和"两边条数差"**——这两个能最早发现一致性问题。

## 6.7 schema 演进与重导

embedding 相关的变更（换模型 → 维度变了 / 重新生成 embedding）是**必然会发生的**：

| 场景 | A 方案 | B 方案 |
|---|---|---|
| 加列（如质量分） | Iceberg 加列，SQL 直接查 | Iceberg 加列 + Milvus 也要加标量字段 + 可能要重导 |
| **换 embedding 模型（维度变）** | Iceberg 加新列，SQL 换列查 | **Milvus 要重建集合 + 全量重导**（最重的操作） |
| 重新生成 embedding（同维度） | Iceberg 更新列 | Milvus 全量更新（upsert）+ 索引可能要重建 |

**B 方案在"换模型"时代价最大**：几十 GB~TB 级的重导 + 索引重建，耗时且占用资源。**设计时要预留这个窗口**（比如支持双集合切换：新集合建好后别名切过去，零 downtime）。

## 6.8 运维复杂度总评

| 维度 | A 直查 | B 导入 Milvus |
|---|---|---|
| 新增系统 | 0 | +1 套 Milvus（+ 依赖组件） |
| 新增管道 | 0 | +1 条同步管道（全量+增量+对账） |
| 一致性 | 强一致（免费） | 最终一致（要维护） |
| 故障模式 | 少（查询慢/失败） | 多（同步、漂移、幽灵结果、集群） |
| 监控项 | 少 | 多（lag、条数差、Milvus 集群） |
| 换模型成本 | 低（换列） | 高（重建 + 重导） |

## 6.9 本章小结

- **A 的一致性是免费的**：直接读 Iceberg 快照 → 强一致、可 time travel、无同步风险。
- **B 必然是最终一致**：引入同步管道 → 滞后、漂移、幽灵结果、漏删除。
- **B 的必修课**：水位管理（记录同步到哪个 snapshot）、幂等 upsert、删除同步、定期对账。
- **保留 A 作为降级通道**：Milvus 挂了还能用 SR 直查（慢但可用），成本极低。
- **监控重点**：同步 lag、两边条数差（最早发现一致性问题）。
- **换 embedding 模型是 B 代价最大的时刻**：要预留重建 + 重导窗口，用双集合切换做到零 downtime。
- 总体：B 在运维上是"**用复杂度换性能**"，团队要有对应的工程能力才接得住。
