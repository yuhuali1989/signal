# 万亿 CLIP 向量检索：多模态大模型时代，检索不是被参数化了，而是被换了个位置

## 引言：一个反直觉的事实

多模态大模型（VLM / MLLM）把视觉理解"装进了权重"，最常听到的质疑是：既然模型自己就能看图说话，CLIP 这类对比学习编码器 + 向量检索的老技术栈是不是要过时了？

把视角放到工程侧，看到的却是相反的景象：**模型越大，周围的向量库越大**。训练一个万亿参数的多模态模型，前置的数据清洗环节动辄要处理上百亿图文对，每一对都要算 CLIP 向量、做近重复去除、按语义聚类配比；上线之后，多模态 RAG、Agent 记忆、语义缓存、版权检测——每个环节都在生产新的向量。参数化知识和检索知识不是替代关系，而是分工关系：**模型负责推理，向量库负责记忆**。模型权重更新一次以月计，向量库以毫秒计。

本文回答两个问题：多模态向量检索还有哪些真实场景？以及其中最硬核的一关——**万亿级 CLIP 向量检索**——在工程上到底怎么落地。

## 一、场景盘点：九类真实需求，最大的一类不是搜索

| # | 场景 | 规模量级 | 关键约束 | 谁在做 |
|---|------|---------|---------|--------|
| 1 | 训练数据工程（去重/过滤/配比） | **10⁹~10¹²** | 吞吐优先，离线 | DataComp、LAION、各大模型厂商 |
| 2 | 多模态 RAG | 10⁷~10⁹ | 延迟 + 精度 | 企业知识库、电商客服 |
| 3 | Agent 长期多模态记忆 | 10⁶~10⁸ | 实时写入 | ChatGPT Memory、Agent 框架 |
| 4 | 语义缓存 | 10⁶~10⁸ | 极低延迟 | GPTCache 类系统、推理网关 |
| 5 | 以图搜图 / 视觉搜索 | 10⁸~10¹⁰ | 毫秒级在线 | 电商、Pinterest、Google Lens |
| 6 | 版权与内容审核 | 10⁹~10¹² | 召回率优先 | 平台内容安全、AIGC 溯源 |
| 7 | 长视频关键帧召回 | 10⁷~10⁹ | 时间元数据过滤 | 视频理解、Video QA |
| 8 | 具身智能情景记忆 | 10⁶~10⁹ | 端侧/低延迟 | 机器人 episodic memory |
| 9 | 检索式推荐召回 | 10⁹~10¹¹ | 多路融合 | 信息流、广告 |

几个值得展开的点：

**场景 1 是被严重低估的"隐形大头"。** DataComp 的做法是最典型的例子：从 128 亿图文对的 Common Pool 里筛选高质量子集，核心手段就是 CLIP 检索——用 800 万高质量种子对的向量，在全量池子里做最近邻检索，"和好数据长得像的数据就是好数据"。LAION-5B 的近重复去除同理。这类任务对延迟不敏感（离线批处理），但对**吞吐和成本极其敏感**——万亿级库往往就诞生在这里，而且它直接决定了后面那个多模态大模型的上限。换句话说：**你看到的是一个万亿参数模型，它背后先站着一个万亿向量库**。

**场景 2/3/4 是 MLLM 时代的新增量。** 多模态 RAG 检索的不只是文本块，而是"图文交错块"（interleaved chunks）——文档里的图表和上下文必须一起召回，否则模型拿到图却没有坐标轴说明。Agent 记忆则把向量检索从"外部知识"变成"经验回放"：机器人每次任务执行的 (图像序列, 动作, 结果) 都入库，下次遇到相似场景先检索成功经验再决策。语义缓存是成本杀手：VLM 一次推理几百毫秒、几厘钱，而 90% 的用户查询高度重复——query 向量先过 ANN，命中相似历史请求直接返回缓存答案，这个模式在多模态场景的收益比纯文本更大，因为"图 + 文"的组合空间虽大，实际分布却高度集中（商品咨询、报表解读、截图报错）。

**场景 6 是召回率导向的反面极端。** 版权检测宁可误杀不可漏放——一条盗版图换个滤镜、裁个边、加个水印都要能召回。这要求索引在高压缩率下仍然保持 99%+ 的 recall@100，是对量化方案最苛刻的考验，实践中往往放弃激进压缩、用 int8 + 原始维度 + 多路索引并集。

**场景 7/8 是 MLLM 长上下文救不了一的部分。** 一个 2 小时视频 24 万帧，全部塞进上下文窗口既不现实也不必要。工业做法是两级：向量检索先召回 top-100 相关帧（每帧/每镜头一个 CLIP 向量 + 时间戳元数据），再让 VLM 精读这 100 帧。具身智能的情景记忆同理——检索先行，模型殿后。**长上下文窗口的扩张没有消灭检索，只是把检索的准入门槛从"必须检索"变成了"检索更便宜"**。

## 二、万亿 CLIP 检索的第一道关：把存储账算清楚

以最常用的 CLIP ViT-L/14（768 维，fp32）为例，1 万亿条向量的裸存储：

```
1e12 × 768 × 4 bytes = 3.07 PB
```

哪怕全用 NVMe SSD（单盘 30TB 市价约 3 万元），光裸数据就是 10 万块盘、3 亿元——还没算副本和索引结构。结论很直接：**万亿级检索的成败 90% 取决于压缩，索引结构只是压缩之上的调度**。

工程上的压缩三件套，按顺序做：

**第一件：降维。** 768 维 → 256 维 PCA，信息损失通常 <3%（CLIP 向量的能量高度集中在前 200~300 主成分），存储直接砍掉 2/3。更新的做法是 **Matryoshka Representation Learning（MRL，套娃表征）**：训练时让向量的前 64/128/256 维就是完整可用的表征，推理时按需截断——OpenAI CLIP、Jina-CLIP-v2 都已原生支持。MRL 的优雅之处在于**一个向量库同时服务多种精度档位**：粗召回用 64 维，精排用全维度，不需要存两份。

**第二件：量化。** 这是存储的大头，一档一档算：

| 量化方案 | 单向量占用 | 1T 总量 | 相对裸 fp32 | 典型 recall 损失 |
|---------|-----------|---------|------------|----------------|
| fp32 原始 | 3072 B | 3.07 PB | 1x | 0 |
| int8 标量量化 | 768 B | 768 TB | 4x | <0.5% |
| PCA-256 + int8 | 256 B | 256 TB | 12x | ~1% |
| PQ-64（64 子码本×256）| 64 B | 64 TB | 48x | 3~8% |
| PCA-256 + PQ-32 | 32 B | 32 TB | 96x | 5~12% |
| 二值量化（Hamming）| 96 B | 96 TB | 32x | 粗召回用，必须重排 |

关键认知：**PQ 是有损的，且损失在召回率上不可忽略**。所以万亿级系统几乎从不"一条索引打天下"，而是两阶段：损失大的压缩方案做粗召回（多召回一些，比如 top-1000），原始向量或 int8 向量做精排。原始向量放哪？不放在内存里——放在 SSD（这就是 DiskANN/SPANN 的核心思想，见下节）。

**第三件：分区（IVF）。** 用 k-means 把全空间切成 10⁵~10⁶ 个胞腔（cell），查询时只探测离 query 最近的 nprobe 个胞腔。这一步把"全库扫描"变成"扫描 0.01%"，是所有万亿级方案的共同前置——区别只在于**胞腔的 posting list 放内存还是放 SSD**。

## 三、索引结构选型：四种路线的正面交锋

| 索引 | 代表 | 数据位置 | 适配规模 | 查询延迟 | 构建成本 | 核心取舍 |
|------|------|---------|---------|---------|---------|---------|
| IVF-PQ | Faiss | 内存 | ≤10 亿 | ~1ms | 中 | 压缩狠但召回受损 |
| HNSW | 几乎所有向量库 | 内存 | ≤10 亿 | <1ms | 高（图构建慢）| 内存吃紧，十亿到顶 |
| DiskANN / Vamana | 微软 | SSD + 少量内存 | 千亿级 | ~5ms | 高 | 单机图索引，增量难 |
| SPANN | 微软 | SSD（posting list）+ 内存（质心）| **万亿级** | ~10ms | 低（k-means 而已）| 延迟换规模 |
| GPU CAGRA | NVIDIA cuVS | 显存 | ≤1 亿/卡 | <0.5ms | 中 | 规模受显存限制 |

三条选型经验：

**1. 十亿以内是"甜点区"，随便选。** HNSW 的 <1ms 延迟和 99% 召回在 10 亿规模内依然是标杆，这也是 Qdrant/Milvus/Vespa 的默认配置能覆盖绝大多数业务的原因。 trillion 之前的所有纠结都是幸福的烦恼。

**2. 千亿到万亿，SSD 索引是唯一的路。** SPANN 的设计最能体现"工程的艺术"：只把 k-means 质心（比如 100 万个质心 × 256 维 int8 = 256MB）放内存，posting list 全部按顺序躺在 SSD 上。查询时内存里算出最近的 nprobe 个质心，然后**顺序读**（不是随机读！）对应 posting list。SSD 顺序读带宽是随机读的 10 倍以上，SPANN 靠"质心内向量排序 + posting list 连续存储"把随机访问变成了顺序访问——这就是它在单台机器（64GB 内存 + 若干 NVMe）上做到万亿级、P99 <10ms 的原理。DiskANN 则走了另一条路：把 Vamana 图直接建在 SSD 上，导航过程在图上逐跳进行，每跳一两次 SSD 读，延迟略低但构建一个万亿图的成本高昂。

**3. GPU 不是用来装全库的，是用来做精排和训练索引的。** H100 80GB 装 int8 的 768 维向量只能放约 1 亿条（还要扣掉索引开销）。GPU 在万亿架构里的正确位置是：k-means 训练加速（10¹² 向量的质心训练，CPU 要跑数周，GPU 天级）、以及粗召回后 top-1000 的 int8 全精度重排（微秒级）。NVIDIA cuVS 的 CAGRA 在"单卡装得下"的规模内确实是最快的图索引，但它的定位是精排器和小规模在线服务，不是万亿存储。

## 四、两阶段检索：万亿架构的标准范式

把上面的零件组装起来，一个生产级万亿 CLIP 检索系统的样子：

```
Query 向量 (768d, fp32)
    │
    ▼
[第一级：粗召回]  分片并行，每片返回 top-500~1000
    IVF 质心路由（内存）→ SSD posting list 顺序读 → PQ 距离粗算
    延迟预算：5~8ms
    │  候选 ~10K（跨分片归并后）
    ▼
[第二级：精排]  int8 原始向量重算精确距离
    GPU 批量 L2/IP 距离 → 全局 top-10~100
    延迟预算：1~2ms
    │
    ▼
[可选第三级：模型重排]  cross-encoder 或 VLM rerank
    只对 top-50 跑，输出最终排序
```

第一级牺牲精度换吞吐（recall@1000 做到 90% 即可），第二级把精度补回来（recall@10 做到 98%+），第三级用重型模型换排序质量。**每一级的候选集缩小 10~100 倍，成本逐级上升——这是所有检索系统的通用经济学**，从搜索引擎到推荐系统到向量检索，无一例外。

## 五、动手环节：Faiss 分片 IVF-PQ 检索（完整可运行）

以下代码演示万亿架构的最小内核：分片 + IVF-PQ 粗召回 + int8 精排。单机跑通后，把分片换成独立进程/机器就是分布式版本。

```python
# pip install faiss-cpu numpy
import numpy as np
import faiss

# ============ 配置：模拟一个小规模的"万亿架构" ============
D = 768              # CLIP ViT-L/14 维度
D_PQ = 256           # PCA 降维后维度（生产中先在 1M 样本上拟合 PCA）
N_SHARDS = 4         # 分片数（万亿级生产中 = 数百个 SSD 分片）
N_PER_SHARD = 200_000   # 演示规模；生产中每片 10~50 亿
NPROBE = 32          # 探测胞腔数：粗召回/延迟的第一调节旋钮
K = 10               # 最终 top-K

rng = np.random.default_rng(42)

# ============ 第 0 步：真实场景中向量来自 CLIP 编码器 ============
# image_emb = clip_model.encode_image(...)   # (B, 768) L2 归一化后
def make_clip_like(n):
    """模拟 CLIP 向量：各向异性 + L2 归一化（真实 CLIP 分布远比高斯集中）"""
    x = rng.standard_normal((n, D)).astype("float32")
    x[:, :64] *= 8.0          # 模拟能量集中在前若干维
    faiss.normalize_L2(x)
    return x

shard_vectors = [make_clip_like(N_PER_SHARD) for _ in range(N_SHARDS)]

# ============ 第 1 步：每分片建 PCA + IVF-PQ 粗召回索引 ============
def build_shard_index(xb, nlist=1024):
    # PCA 768 -> 256（生产中 PCA 用全库采样训练，这里直接拟合）
    pca = faiss.PCAMatrix(D, D_PQ, eigen_power=-0.5)   # 白化，让能量均匀化
    pq  = faiss.ProductQuantizer(D_PQ, 32, 8)          # 32 子空间 × 8bit = 32B/向量
    index = faiss.IndexIVFPQ(faiss.IndexFlatL2(D_PQ), D_PQ, nlist, 32, 8)
    index.set_pq_algorithm(faiss.PQAlgorithm_t.PQ_KS)  # Kernel-Split 加速
    pipe = faiss.PreprocIndexIVFPQ()                   # 组装 PCA -> IVFPQ 流水线
    pipe = faiss.IndexPreTransform(pca, index)
    pipe.train(xb)
    pipe.add(xb)
    return pipe, xb   # 生产中 xb 的 int8 副本放 SSD，供精排读取

shard_indexes, shard_raw = [], []
for xb in shard_vectors:
    idx, raw = build_shard_index(xb)
    shard_indexes.append(idx); shard_raw.append(raw)

# ============ 第 2 步：查询 = 两级检索 ============
def search(query: np.ndarray, k=K, recall_k=500):
    faiss.normalize_L2(query)
    # ---- 第一级：分片并行 IVF-PQ 粗召回，每片 top-500 ----
    cands = []   # (shard_id, local_id, coarse_dist)
    for sid, idx in enumerate(shard_indexes):
        idx.nprobe = NPROBE
        D_, I_ = idx.search(query, recall_k)
        cands += [(sid, int(i), float(d)) for d, i in zip(D_[0], I_[0]) if i != -1]
    # 跨分片归并，取粗排 top-2000 进精排
    cands.sort(key=lambda t: t[2])
    cands = cands[:2000]
    # ---- 第二级：取原始向量精排（生产中从 SSD 读 int8 向量）----
    rerank = []
    for sid, lid, _ in cands:
        v = shard_raw[sid][lid]              # 生产中: int8_ssde[sid].read(lid)
        rerank.append((float(np.linalg.norm(query[0] - v)), sid, lid))
    rerank.sort()
    return rerank[:k]

q = make_clip_like(1)
t0 = faiss.getmillisecs()
results = search(q)
print(f"两级检索耗时 {faiss.getmillisecs()-t0}ms, top-1: shard{results[0][1]}#{results[0][2]}")

# ============ 第 3 步：召回率验证（选型的唯一硬标准）============
def recall_measure(k=10, trials=50):
    hits = 0
    for _ in range(trials):
        q = make_clip_like(1)
        # ground truth：全库暴力扫
        gt = []
        for sid, raw in enumerate(shard_raw):
            d = np.linalg.norm(raw - q[0], axis=1)
            for lid in np.argsort(d)[:k]:
                gt.append((sid, int(lid)))
        gt = set(sorted(gt)[:k])
        two_stage = {(s, l) for _, s, l in search(q, k=k)}
        hits += len(gt & two_stage) / k
    return hits / trials

print(f"recall@{K} = {recall_measure():.3f}")
# 本配置下通常 >0.95；生产中调 nprobe / recall_k / PQ 档位做成本-召回权衡
```

三个生产化要点，代码里没体现但必须做：

1. **PQ 码本要用全库分布训练**。用 500 万均匀采样样本训码本，和用 500 万某类图片训码本，召回率能差 5 个点。
2. **SSD 布局决定一切**。posting list 内向量按"到质心距离"排序并连续存储（SPANN 的做法），顺序读的吞吐可以做到随机读的 10 倍。
3. **id 映射单独一层**。向量 id → (图片 URL / 文本 / 元数据) 的映射放 KV 存储（RocksDB 类），索引只存 id，热数据缓存即可。

## 六、分布式与在线化：从单机脚本到生产集群

单机 SPANN 的上限大约是"一台 64GB 内存 + 16 块 NVMe 的服务器扛 1~2 万亿"，再往上就必须水平扩展。分布式层的核心问题只有两个：

**分片策略。** 按质心分片（相近向量落同一片）查询效率高但负载不均——热门语义区域的分片会过热；按哈希随机分片负载均匀但每片都要查。工业界主流（Milvus 2.x、Vespa）走随机分片 + 每片内部再 IVF 的两层结构，用"全片并行 + 每片只探测少量胞腔"把延迟压住。1T 向量 ÷ 100 个节点 = 每节点 100 亿，正好落在单机 SSD 索引的甜点区。

**一致性与增量。** 图索引（HNSW/DiskANN）的痛点是增量插入会导致图结构退化，需要定期后台重建；IVF/SPANN 系天然增量友好——新向量进最近的胞腔即可，代价是胞心不更新导致的漂移，用"定期局部重聚类 + 冷热分层"解决。做训练数据工程这种纯离线场景可以完全绕开这个问题：**批量建、批量查、用完就扔**，这也是为什么 DataComp 们偏爱朴素的 IVF-PQ 批处理而非向量数据库。

| 方案 | 适用 | 万亿支持 | 备注 |
|------|------|---------|------|
| 裸 Faiss / cuVS + 自研分片 | 离线数据工程 | 手工搭 | 吞吐天花板最高，DataComp 路线 |
| Milvus 2.x / Vespa | 在线多租户 | 集群可到 100B+ | 增删改查、标量过滤齐全 |
| SPANN 论文实现 | 单机海量 | 单机 1T+ | 微软未开源官方实现，需自研复刻 |
| Qdrant / Weaviate | 中小规模在线 | 百亿级 | 开发体验最好，别硬上万亿 |

## 七、展望：向量检索正在被 MLLM 重新定义，而不是取代

三个正在发生的趋势：

**1. 检索器和重排器正在被多模态大模型"吃掉"一层。** 传统三段式（双塔召回 → 交互式重排 → 规则融合）中的重排器正在被 VLM 替代——用 7B VLM 对图文 query-doc 对直接打相关性分，效果显著超过 cross-encoder。但**召回层的双塔 CLIP 反而更稳固了**：它的使命从"端到端理解"收缩为"高吞吐预过滤"，这恰好是 CLIP 架构（双塔、可离线建库）最擅长的。

**2. 训练数据工程的检索规模还会再涨一个数量级。** 后训练 Scaling（见本站前文《后训练 Scaling 革命》）意味着数据配比实验的次数爆炸——每一次配比实验都是一轮全库检索 + 聚类 + 采样。万亿向量库会从"一次性基建"变成"持续运转的数据引擎基础设施"，这也是 SPANN 类技术重新受关注的原因。

**3. 语义缓存会成为 VLM 降本的第一杠杆。** 推理框架的军备竞赛（vLLM 1.0、SGLang 3.2）把单价压下来一个数量级之后，下一个数量级就在缓存里。多模态语义缓存对向量检索提出了新要求：容忍"语义相近但非精确匹配"的命中判定（相似度阈值 0.95 vs 0.99 直接决定缓存命中率和错误率），这是传统 ANN 从没面对过的精度语义。

## 结语

多模态大模型与向量检索的关系，可以浓缩成一张资产负债表：**模型权重是固定资产，折旧以月计；向量库是流动资产，随业务实时增减**。前者负责把通用的看和想参数化，后者负责把具体的、新鲜的、私有的、长尾的一切留给检索。万亿 CLIP 检索不是一项"老技术苟延残喘"，而是多模态数据引擎的地基——它的三件套（降维、量化、分区）和两阶段范式（粗召回 + 精排）没有魔法，只有被规模逼出来的工程纪律。

一个判断：在数据决定上限的多模态竞赛里，**谁能把万亿向量库的检索成本压到对手的十分之一，谁的数据迭代速度就是对手的十倍**。这比多几个点的 benchmark 分数，是更硬的护城河。
