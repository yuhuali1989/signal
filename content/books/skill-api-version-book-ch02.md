## 2.1 先立标准：什么才算破坏性变更

版本号的目的是标记**不兼容**，所以第一步是知道什么不兼容。业界共识（Public APIs、WSO2、Stripe 实践）如下：

| 算破坏性变更（需要新版本） | 不算（同一版本内可直接加） |
|---|---|
| 删除字段 / 端点 / 参数 | 新增端点 |
| 重命名字段 / 端点 | 新增**可选**请求参数 |
| 改变字段类型或格式 | 响应里新增字段 |
| 改变字段**语义**（同名字不同含义） | 性能优化、bug 修复（不改变契约） |
| 把原本可选的输入改成必填 | 新增错误码（在既有错误语义内） |
| 改变认证方式或错误语义 | |

> **判据一句话**：**任何会让「已经写好、且遵守了约定的客户端」行为发生改变的改动，都是破坏性变更。**

注意「字段语义变化」这一条——改个大小写、改个枚举取值，版本号可能没动，但对消费方就是破坏性。这正是第 1 章那个 `open → OPEN` 事故的成因，**也是为什么 L3 形状校验不能省**。

## 2.2 五种版本承载机制

| 机制 | 形态 | 优点 | 缺点 | 谁在用 |
|---|---|---|---|---|
| **URI 路径** | `/api/v2/users` | 显式可见、日志友好、极易测试、缓存友好 | URL 里永远带着版本；同一资源两个 URL | 大多数公开 API |
| **请求头 / 媒体类型** | `X-GitHub-Api-Version: 2026-09-01`<br>`Accept: application/vnd.api+json;version=2` | URL 干净、符合 REST 纯粹主义、URL 稳定 | 不可见（curl 不带头就静默命中默认版本）、难测试、CDN 缓存需按头分片 | GitHub |
| **查询参数** | `/api/users?version=2` | 可缺省、URL 不变 | 易遗漏、缓存键复杂、被中间层剥离、污染每个示例 | 老企业 API |
| **日期钉住**（CalVer + 头） | `Stripe-Version: 2026-05-01`，账户首次请求时钉住 | ★客户端可控升级时机、向后兼容由服务端承担、可日更 | 服务端要维护多个日期版本间的翻译层，**运维成本最高** | Stripe、Twilio、AWS、Salesforce |
| **主机名 / 子域** | `v2.api.example.com` | 完全隔离、可跑独立服务 | DNS、证书、基础设施复杂度高 | 重大重构 |

### 各形态的真实案例

| 厂商 | 策略 |
|---|---|
| **Stripe** | URI 里是 `/v1/`，但用 `Stripe-Version` 头钉住**日期版本**；账户首次请求时的版本被记住，之后除非显式升级，行为永远不变 |
| **GitHub** | `X-GitHub-Api-Version` 头带**日期命名的版本**；承诺新版本发布后**旧版至少再支持 24 个月** |
| **Twilio** | URI 日期版本：`/2010-04-01/` |
| **Salesforce** | URI 版本：`/services/data/v58.0/` |
| **X（Twitter）** | `/2/tweets` |

## 2.3 版本号命名：语义化 vs 日历

| | 语义化（SemVer：v1 / v2 / v3） | 日历（CalVer：2026-05-01） |
|---|---|---|
| 表达力 | 只表达**代际**，不表达时间 | 同时表达**代际 + 时间** |
| 适用场景 | 破坏性变更少而清晰 | 持续演进、小改动频繁 |
| 客户端心智 | 「我是 v2 用户」 | 「我钉在 2026-05-01」 |
| 代表 | GitHub（早期）、多数 REST | Stripe、Twilio、AWS、GitHub（现行） |

**趋势观察**：面向开发者的长生命周期 API 正在向**日期版本**迁移。原因很实在——日期版本天然带有「发布时间」信息，做支持窗口承诺（「24 个月后下线」）时比 v2/v3 更好沟通。

## 2.4 各策略对消费方的语义差异（★最容易踩）

不同策略下，**「不指定版本会发生什么」完全不同**——这直接决定 Skill 要不要显式带版本：

| 策略 | 不带版本时 | 对 Skill 的含义 |
|---|---|---|
| URI 路径 | **不存在「不带」**——路径里必须有 | 安全，但升级要改所有 URL |
| Stripe 式钉住 | 用**账户绑定**的旧版本 | ★很安全：你不主动升级，行为永远不变 |
| GitHub 式默认 | 命中**服务端当前默认（最新）** | ★**危险**：服务端一改默认值，你的行为就漂了 |
| 查询参数 | 通常是默认（最新） | 同 GitHub，且参数易被剥离 |

> **给 Skill 作者的硬规则**：**永远显式指定版本，不要依赖服务端默认值。** 依赖默认值等于把「什么时候升级」的控制权交给了你不认识的人——这是第 1 章行为漂移的头号来源。

## 2.5 ★ 铁律：客户端必须忽略不认识的字段

服务端在非破坏性演进时会往响应里**加字段**。这只有在一个前提下才安全：

> **消费方必须忽略自己不认识的字段，而不是因为「多了个字段」报错。**

这条约定（"clients must ignore unrecognized fields"）是**加字段不算破坏性变更**的全部基础。反过来，如果 Skill 用了严格 schema 校验且拒绝未知字段，那么服务端每加一个字段就等于对你做了一次破坏性变更——你会被自己的严格性反噬。

**做法**：严格 schema 用「**必需字段断言 + 未知字段放行**」的组合，而不是「全量严格匹配」。

## 2.6 生命周期信号：怎么知道一个版本要死了

成熟 API 会用标准信号告知下线计划，而不是靠博客：

| 信号 | 标准 | 含义 |
|---|---|---|
| `Deprecation` 头 | RFC 9745 | 该版本**什么时候开始废弃** |
| `Sunset` 头 | RFC 8594 | 该版本**什么时候起返回 410 Gone** |
| 响应内警告 | 各家自定义 | 迁移提示 |
| 迁移指南 | 文档 | 逐条映射破坏性差异 |

**典型时间线（业界实践）**：

| 阶段 | 时间点 | 动作 |
|---|---|---|
| 宣布废弃 | Day 0 | 加 Deprecation/Sunset 头、通知、发迁移指南 |
| 软下线（Soft sunset） | +6 个月 | 加强警告、对活跃用户发提醒 |
| 硬下线（Hard sunset） | +12 个月 | 全端点返回 `410 Gone` + 迁移链接 |
| 代码退役 | +18 个月 | 从代码库彻底移除 |

> GitHub 的承诺更宽松：**新版本发布后旧版至少支持 24 个月**。行业普遍认为 **6～12 个月是公开 API 废弃的下限**——再短会引发开发者反弹，再长则积累技术债。

**给 Skill 的工程动作**：**监控响应里的 Deprecation / Sunset 头，并把它接进告警。** 这两个头是机器可读的，成本极低，但能把「某天突然全 410」变成「提前半年知道要迁移」。

## 2.7 反模式：混用策略

> **「一处用 /v2/ 路径，另一处用版本头」是严格劣于任何单一策略的选择。**

混用会导致：客户端不知道该看哪个、缓存策略分裂、文档无法自洽、迁移路径模糊。**选定一种，全局一致。**

## 2.8 本章要点

- **破坏性变更的判据**：会让守约定的老客户端行为改变的改动。字段语义变化（大小写、枚举）也算，且版本号可能不动。
- 五种机制里，**URI 路径最显式最好测**，**日期钉住对客户端最友好但服务端成本最高**。
- ★**永远显式带版本，绝不依赖服务端默认值**——依赖默认值 = 把升级控制权拱手让人。
- ★**客户端必须忽略未知字段**，否则服务端每次加字段都等于对你做破坏性变更。
- **Deprecation / Sunset 头（RFC 9745 / 8594）要接进监控**，这是唯一机器可读的下线预警。
- 废弃窗口业界标准 6～12 个月，GitHub 承诺 24 个月；**混用版本策略是严格劣化**。
