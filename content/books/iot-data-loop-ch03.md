# 第3章：多云 K8s 集群与 SaaS 基础设施

## 3.1 多云战略选择

### 3.1.1 为什么必须是多云

| 维度 | 单云 | 多云 | 说明 |
|:-----|:----|:----|:------|
| 全球覆盖 | ❌ 部分区域延迟高 | ✅ 就近接入 | 亿级设备分布全球 |
| 供应商锁定 | ⚠️ 高 | ✅ 可迁移 | 避免单一厂商涨价 |
| 合规 | ❌ 数据本地化困难 | ✅ 区域化存储 | GDPR/PIPL 等 |
| 容灾 | ⚠️ 单云故障影响大 | ✅ 跨云切换 | 云厂商宕机不影响核心功能 |
| 成本谈判 | ❌ 无竞争 | ✅ 竞价空间 | 每年 re:negotiate |

### 3.1.2 三云分工

| 角色 | 主要职责 | 云服务 |
|:-----|:---------|:-------|
| **AWS**（主数据面） | 设备接入、对象存储主湖、训练集群 | IoT Core + S3 + EKS + SageMaker |
| **GCP**（副数据面） | 亚太区域接入、AI 训练 | GKE + GCS + TPU + Vertex AI |
| **Azure**（合规/备份） | 欧洲区域接入、合规存储 | AKS + Blob Storage + IoT Hub |

## 3.2 集群架构

### 3.2.1 全球集群拓扑

```
每个云厂商在每个区域部署 2 套集群：

┌───────────── 区域（如 us-east-1）─────────────┐
│                                                  │
│  ┌──────────────┐     ┌──────────────┐          │
│  │  控制面集群    │     │  数据面集群   │          │
│  │  (SaaS 层)   │     │  (数据处理层) │          │
│  │              │     │              │          │
│  │ - 用户 API   │     │ - 设备数据    │          │
│  │ - OTA 下发   │     │   ETL Pipeline│          │
│  │ - 设备管理   │     │ - 模型推理    │          │
│  │ - A/B 测试   │     │   服务        │          │
│  │              │     │ - 数据标注    │          │
│  │  Node: 10-20 │     │   平台        │          │
│  │  (高可用)    │     │              │          │
│  │              │     │  Node: 100-   │          │
│  │              │     │  500（弹性）  │          │
│  └──────────────┘     └──────────────┘          │
│                                                  │
└──────────────────────────────────────────────────┘
```

**全球集群数量**：3 云 × 8 区域 × 2 套 = **48 个 K8s 集群**

### 3.2.2 托管 K8s vs 自建

| 维度 | 托管 K8s（EKS/GKE/AKS） | 自建 K8s |
|:-----|:----------------------|:--------|
| 控制面运维 | 云厂商负责 | 需 5-10 人 SRE 团队 |
| 升级 | 自动 | 手动 |
| 成本 | 控制面 $0.10/小时×集群 | 控制面节点 $30-50/月×3 |
| 扩展性 | 原生支持数万节点 | 需额外工作 |
| 定制化 | 受限 | 完全可控 |

**结论**：亿级设备规模下，**托管 K8s 是唯一可行选择**。自建 48 个集群的控制面至少需要 50+ 人 SRE 团队。

## 3.3 设备接入架构

```
设备 ──→ IoT Gateway（AWS IoT Core/GCP IoT Hub）
            │
            ├── 设备认证（X.509 证书）
            ├── 消息路由（MQTT/HTTP）
            ├── 影子设备（设备状态同步）
            └── 规则引擎 ──→ 对象存储（原始数据）
                                  │
                                  ▼
                           数据湖 Iceberg
```

## 3.4 多集群管理

### 3.4.1 工具链

| 工具 | 用途 | 替代方案 |
|:-----|:-----|:--------|
| Terraform + Crossplane | 基础设施即代码 | Pulumi / AWS CDK |
| Argo CD | GitOps 多集群部署 | Flux CD |
| Istio（多集群 Mesh） | 服务网格、跨集群流量 | Consul Connect |
| Prometheus + Thanos | 统一监控 | Grafana Mimir |
| Loki + Tempo | 日志 + 链路追踪 | Datadog（商业） |

### 3.4.2 GitOps 工作流

```
开发者 Push ──→ Git 仓库
                    │
                    ▼
              Argo CD（控制面集群）
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
    EKS 集群    GKE 集群    AKS 集群
    (us-east-1) (asia-east1) (westeurope)
```

## 3.5 SaaS 控制面设计

### 3.5.1 多租户隔离

| 隔离级别 | 范围 | 实现 |
|:---------|:-----|:-----|
| 数据隔离 | 租户数据 | Iceberg 分区 + S3 前缀 |
| 计算隔离 | 训练任务 | K8s Namespace + ResourceQuota |
| 网络隔离 | 设备流量 | VPC + 私有子网 |
| 身份隔离 | 用户认证 | OIDC + RBAC |

### 3.5.2 核心 API

```
POST   /v1/devices/register       # 设备注册
POST   /v1/devices/{id}/data       # 设备数据上报
GET    /v1/devices/{id}/config     # 设备配置拉取
POST   /v1/models/deploy           # 模型部署
GET    /v1/models/{id}/status      # 模型状态
POST   /v1/ota/create              # 创建 OTA 任务
GET    /v1/ota/{id}/progress       # OTA 进度查询
```

## 3.6 成本估算（多云 K8s 部分）

| 成本项 | 月成本（48 集群） | 年成本 |
|:-------|:---------------|:-------|
| EKS/GKE/AKS 控制面 | $0.10/h × 24 × 30 × 48 = ~$3,456 | $4.1 万 |
| 数据面节点（按需） | 200 node × 48 cluster × $0.5/h × 24 × 30 = ~$3.5M | $4,200 万 |
| 弹性实例（Spot） | 可节省 60-70% → ~$1.2M | $1,440 万 |
| Istio 控制面 | ~$0 开源 | $0 |
| 监控（Thanos） | ~$500/月 | $6,000 |
| **K8s 总计** | **~$1.2M（使用 Spot）** | **~$1,450 万** |

## 3.7 本章小结

本章设计了多云 K8s 集群架构的核心方案：3 云 × 8 区域 × 2 套 = 48 个托管 K8s 集群，通过 GitOps（Argo CD）+ 服务网格（Istio）+ 统一监控（Thanos）实现全球统一管理。年 K8s 基础设施成本约 $1,450 万（使用 Spot 实例），远低于自建方案的人力成本。下一章讨论对象存储数据湖的设计。
