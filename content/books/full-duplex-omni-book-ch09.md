# 第 9 章 · 全双工时序：双流、附和、打断与持续 decode 的算力账

「全双工」在代码上到底是什么意思？这一章用逐片 ID 流回答，不带任何抽象描述。

## 9.1 双流：用户流只建模、不采样

Moshi 把对话建模成 **17 条并行子序列**：

```
用户语音流   8 层 RVQ  → 来自真实麦克风，只算表示，不采样
模型语音流   8 层 RVQ  → 需要采样输出
文本流       1 个      → Inner Monologue，时间对齐前缀
                        ──
                        17
```

推理时用户流的输入永远来自真实麦克风，模型**只计算它们的表示、不生成它们**。这就是「模型永远在听」在 token 层的唯一含义，也是打断不需要外挂 VAD 的原因：用户流里出现非静音 token，模型在下一个 80ms 片就能反应。

对比半双工：Qwen2.5-Omni 的 Thinker-Talker 是流式语音生成，但技术报告明确标注 turn-based——生成回答时不能同时接收新输入。**「流式输出」≠「全双工」**，这是选型时最容易混淆的一处。

## 9.2 逐片 ID 流（本例完整时间轴）

| 片 | 用户流 `stream=0`（只建模） | 模型流 `stream=1`（采样） | 状态 |
|---|---|---|---|
| 3200 | 1920 samples「这个能微波吗」+ 金属杯帧 | `75780 SIL` | 还在听 |
| 3280 | 尾音 + 画面未变（视觉片跳过） | `75781 HMM`「嗯」 | 附和 |
| 3360 | `SIL` + 帧 | `12847` / `75778` / 8×音频ID / `75779` →「不能」 | 开始答 |
| 3440 | `SIL` + 帧 | `33092` / `75778` / 8×音频ID / `75779` →「金属」 | 继续说 |
| 3520 | `SIL` + 帧 | `41003` / `75778` / 8×音频ID / `75779` →「会打火」 | 继续说 |
| 3600 | **真实音素**「我是说盖子」+ 新帧 | `75782 BARGE_IN` | 闭嘴 |
| 3680 | 继续 | `12847`… 改答「盖子是塑料的，可以」 | 重答 |

两个细节：

- `SIL=75780`、`HMM=75781`、`BARGE_IN=75782` **都是词表尾部的普通 ID**，不是外部模块发的中断信号。附和（backchannel）、重叠语音、静音都必须是训练数据里的合法状态，否则模型学出来的一定是回合制。
- 打断后「盖子」必须绑到 `t=3600` 的帧。若位置编码用序号，跳帧 + 新帧会让指代落到上一帧的杯身，答成「金属还是不行」。**绝对时间 ID 是这里唯一的保险**。

## 9.3 如果没有 `stream_id`

用户说话时，麦克风同时录进模型自己的扬声器输出（回声）。没有 `stream_id`，主干无法区分：

```
pos 67..74  A_user   ← 真实用户声音
pos 77..84  A_model  ← 自己上一片的输出 / 回声
```

两者都是 8 层音频 ID、都落在 `[73728,75776)`、`t` 也相同。唯一区别就是 `stream_emb(0)` 和 `stream_emb(1)` 那 4096 维偏置。漏掉它，模型会把自己的输出当成用户插话，触发 `BARGE_IN`，然后对新输入再输出、再被自己触发——**无限自打断**。

声学前端仍要做回声消除（AEC），但 `stream_id` 是模型侧的语义保险，两者不能互相替代。

> **2026-11-07 校准：真实时间片是 160ms，不是 80ms**。Higgs Realtime Duplex 把每条流切成 **160ms chunk**（6.25 片/秒），每片读刚到的输入 chunk、写下一段要播放的输出 chunk，用户说完约 **200ms** 内开口。本章下面按 80ms 算的四段账是教学基准；改成 160ms 后分帧等待翻倍，但每片 token 数从 87 降到约 5，总算力反而大幅下降。**决定延迟的不是片长，而是「每片能不能在片长内算完」**。

另外本章 9.1 的「17 条子序列 / 8 层 RVQ」是 Moshi 路线；Higgs 是「音频入 1 token/片、音频出 2 token/片、视频每 6 片 12 token、面部 2 latent/片」，没有 8 层 RVQ，也没有显式的 17 条子序列。不变的是**双流只建模不采样**这条核心机制。

## 9.4 延迟四段账（再算一遍，含全双工特有项）

```
① 分帧等待        80 ms   等 1920 samples 收齐
② 编码器 + 主干    约 40 ms   7B 时间维模型一步
③ codec 解码       几 ms     转置卷积，确定性
④ 语义决策        0 ms      每帧都在判「要不要停/附和」，无额外等待
⑤ 打断响应        80 ms     最坏要等下一片才检测到插话
                    ────
   首包约 120~200 ms，打断响应最坏 160 ms
```

人类话轮间隔约 230ms，所以这个量级才「像人」。级联管线 1~3s 的构成也在同一张账上：VAD 静音判定 100~300ms + ASR 200~500ms + LLM 300~2000ms + TTS 200~800ms，而且各段串行、抖动叠加。

**全双工省掉的不是某一段，是「等待轮次」这个协议本身**。

## 9.5 持续 decode 的算力账

半双工空闲时零成本；全双工即便用户沉默，模型流也要每 80ms 出一片（哪怕一片 `SIL`）：

```
单路墙钟 GPU 占用 ≈ 50%（对话中持续 decode）
12.5 片/秒 × 87 token/片 = 1087 token/秒
5 分钟 = 32.6 万 token → KV cache 每层 [1,32,L,128] ×2 ×32 层 ×2B ≈ 171 GB
```

三个缓解手段：

| 手段 | 做法 | 代价 |
|---|---|---|
| **时间×深度分解** | Temporal 7B 只看 4096 个时间步，17 条子序列由 6 层 Depth 小模型片内展开 | 主干序列长度 ÷17；需 RQ-Transformer 结构 |
| **KV 压缩 / 滑窗** | 静态背景持久表示、早期片摘要化、注意力引导丢弃 | 长程记忆可能丢 |
| **多路同拍 batch** | 多个会话对齐到同一 160ms 拍子一起 decode | 需要会话亲和，扩缩容时别重排已有会话 |
| **极紧的每片预算**（Higgs） | 音频入 1 + 音频出 2 + 面部 2 + 视频均摊 ≈ 7 token/片 → 2.6K~5K token/分钟 | 从源头把 KV 压下来，比事后压缩更有效 |
| **渐进 compaction**（Higgs） | 思考轨迹与工具结果边产生边压缩，只把「进行中工作所需信息」往前带；最近 5 分钟的音视频 + 压缩文本 ≈ 13K~25K token | 老历史转纯文本留存，不占多模态窗口 |

第三条和在线服务部署直接接上了：LMArena 11-07 新增的「跨副本会话亲和」子项实测，轮询分发会让 Prefix Caching 命中率从 82% 掉到 24%、TTFT ×3.4、长会话存活率 -9 点。全双工会话是**最长、最不能断**的一类，务必按 `session_id` 做一致性哈希路由。

另有一个张力：Ray 3.1 的自动副本伸缩越勤，会话亲和越难维持。长会话服务的 `target_ongoing_requests` 别调得太敏感，`min_replicas ≥ 2` 常驻 standby 副本，也能顺带把扩容冷启动从 30~120s 压到 8s。

## 9.6 训练数据：全双工能力的真壁垒

模型能不能学会附和、打断、静音，取决于数据分布，不取决于架构。语料必须包含：

| 类型 | 占比参考 | 作用 |
|---|---|---|
| 重叠语音 | 口语时长 10~20% | 学会「同时说」 |
| 非打断式附和 | 「嗯」「对」「我在听」 | backchannel |
| 静音段 | 大量 | 学会不该开口时闭嘴 |
| 真实打断 | 带中断点标注 | 触发 `BARGE_IN` |
| 音视频共时事件 | 「这个」+ 手势/视线 | 指代消解 |

这和「多模态训练里文本占比低于 50% 语言能力退化」是同一条逻辑：**数据分布决定能力边界，架构只是给它让路**。40 万条全双工对话 + DPO 就能让单个自回归 LLM 自己长出话轮感知（BayLing-Duplex 报告 92% 话轮转换、100% 打断成功），说明连外挂话轮模块都不一定必要——前提是数据对。

## 9.7 工程检查清单

- [ ] 用户流 8 条子序列只建模、不采样，输入永远来自真实麦克风
- [ ] `stream_emb` 在 A_user / A_model / T / 视觉片上取值正确
- [ ] `SIL/HMM/BARGE_IN` 在词表里、参与训练、推理时可达
- [ ] `t` 用绝对毫秒，跳帧不重排序号
- [ ] chunk-causal 掩码按 `t` 生成，片内全互通
- [ ] KV cache 有滑窗或压缩策略，长会话不撑爆
- [ ] 部署侧有会话亲和路由 + standby 副本
- [ ] AEC 声学前端与 `stream_id` 语义保险同时具备

## 9.8 本章小结

- 全双工 = 用户流持续进入（只建模）+ 模型流持续输出（采样），两者共享同一个 Transformer 时间步。
- 附和、静音、打断都是词表尾部的普通控制 ID，训练数据必须含重叠语音。
- `stream_id` 漏了会无限自打断；绝对时间 ID 漏了会把「盖子」绑错帧。
- 首包 120~200ms、打断最坏 160ms；省掉的是「等轮次」这个协议。
- 持续 decode 算力空转 + KV cache 线性增长，需要时间×深度分解、滑窗、多路同拍 batch 与会话亲和路由；**最有效的手段是从源头把每片 token 压到个位数**（Higgs 2.6K~5K token/分钟，5 分钟窗口 13K~25K）。
- 真实产品还有本书没展开的一层：**前台/后台并行**。思考、工具调用、委派给更大的后端模型都可以跨越多个 chunk 异步进行，结果以 payload 形式落进某个输入 chunk，不占用固定的文本 token 配额，也不打断对话。详见第 11 章。
