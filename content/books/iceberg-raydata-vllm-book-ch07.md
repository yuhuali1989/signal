## 7.1 写入模式：append / overwrite / merge 怎么选

| 模式 | 语义 | 适用 | 幂等性 |
|---|---|---|---|
| **append** | 追加新行 | 首次处理、结果天然不可变 | ❌ 重跑会产生重复行 |
| **overwrite（按分区）** | 覆盖指定分区 | **按天/按批增量处理的推荐做法** | ✅ 重跑覆盖同一分区 = 幂等 |
| **merge（upsert）** | 按主键更新/插入 | 需要"重跑只更新不重复" | ✅ 最灵活，代价较高 |

**本场景推荐**：

- 若按天增量处理 → **overwrite 当天分区**（配合第 2 章的增量读），简单且天然幂等
- 若需要跨批更新同一行 → `merge`（按 `id` 或 `id + model_version` 做主键）

## 7.2 幂等：离线任务必须设计"重跑不重复"

离线批处理一定会重跑（失败重试、补历史数据、换模型版本重算）。**不幂等会导致目标表出现重复 caption，下游训练直接被污染。**

三层保障：

| 层 | 做法 |
|---|---|
| **源表侧** | `status` 列：`pending` → `done`；处理完标记，下次跳过（第 2 章） |
| **写入侧** | 用 overwrite 分区 或 merge upsert，保证同一批覆盖而非叠加 |
| **目标表侧** | 主键/去重键：`(id, model_version)`——同一模型版本对同一行只保留一条结果 |

**换模型版本重算时**：`model_version` 变了 → 是新的一行（不是重复），下游可以对比两个版本的质量。这正是溯源列设计的价值。

## 7.3 事务与原子性：Iceberg 的核心收益

Iceberg 的写入是**原子提交**：生成一个新快照，读者要么看到旧快照、要么看到新快照，**不会读到写了一半的数据**。

这意味着：

- 跑到一半失败 → **目标表完全不受影响**（读者仍看到旧快照），不需要清理"半截数据"
- 可以直接"边跑边被读"，不用担心脏读
- 配合快照，还能做 **time travel**：查"昨天那版结果是什么样的"

**实践**：长任务放心跑，失败了直接重跑（配合幂等），不必担心污染线上表。

## 7.4 并发写冲突与重试

多个任务同时写同一张 Iceberg 表时，Iceberg 用**乐观并发控制**：提交时检查基快照是否变化，变了则冲突失败。

常见冲突场景：

- 同一个分区被两个批次同时写
- 增量任务与 compaction 任务并发

**对策**：

1. **提交重试**：捕获冲突异常，重新基于最新快照提交（多数客户端/引擎有重试配置）
2. **错开维护任务**：compaction、expire snapshots 等维护作业与写入作业错峰
3. **分区隔离**：不同批次写不同分区，减少冲突面

## 7.5 小文件治理：并行写的副作用

Ray Data 有 N 个 actor 并行写，每个可能产出多个文件 → 目标表迅速堆积小文件，后果：

- 查询 planning 变慢
- 下游（如下一轮训练数据读取）IO 次数暴涨
- 存储元数据膨胀

**对策**：

| 手段 | 说明 |
|---|---|
| **写入前合并输出** | 减少 writer 并行度或先 coalesce 再写（牺牲一点并行换更少文件） |
| **写入后 compaction** | 定期 `rewrite_data_files`，把小文件合并到目标大小（128–512 MiB） |
| **目标文件大小配置** | 写入时设置目标文件大小（若所用写入接口支持） |
| **例行监控** | 监控"平均文件大小"与"文件数"，作为维护触发条件 |

## 7.6 schema 演进：加列不用重写数据

业务会变：要加一个新指标列、加一个溯源列、调整 caption 长度限制。Iceberg 支持 **schema evolution**：

- **加列**（最常见）：直接 `ADD COLUMN`，元数据操作，**不重写历史数据**，老数据该列为 null
- 改列名 / 调整顺序 / 提升类型（int → long 等安全提升）：也支持
- **删列 / 危险类型变更**：谨慎，可能影响下游

**本场景的典型演进**：后来想加 `"clip_score"` 质量分列 → 直接加列，历史行 null，新跑的批次填上，无需重建表。

## 7.7 写入性能：批量与并行度

| 要点 | 建议 |
|---|---|
| **批量提交** | 别一行一 commit；攒批提交，减少元数据文件数量 |
| **并行度** | writer 并行度与文件大小权衡：太并行 → 小文件多；太少 → 写入慢 |
| **commit 间隔** | 超长任务可分段提交（每段一个快照），但会增加快照数，需配合 expire |
| **避免秒级提交** | 元数据膨胀的主要来源，离线场景没必要 |

## 7.8 写入后验证与对账

写完必须校验，否则"跑完了但结果不对"是最糟的情况：

| 校验 | 方法 |
|---|---|
| **行数对账** | 源表本次处理的行数 == 目标表本次写入行数（差值为失败/跳过行数，要能解释） |
| **空值率** | `caption IS NULL` 的比例是否异常 |
| **质量指标** | `valid` 比例、平均 caption 长度、拒答率 —— 与历史批次对比，突变要告警 |
| **重复检查** | 按 `(id, model_version)` 查重，确认幂等生效 |
| **抽样人工/模型抽检** | 抽几十条看质量，尤其换模型版本后 |

这些指标**全部记进 MLflow**（第 8 章），形成跨批次可对比的质量曲线。

## 7.9 常见坑

| 坑 | 后果 | 对策 |
|---|---|---|
| 用 append 且重跑 | 目标表重复行，污染训练集 | overwrite 分区 / merge / 去重键 |
| 不加溯源列 | 无法回答"这批结果谁生成的" | `model_version` / `run_id` / `source_snapshot_id`（第 2 章） |
| 并行写不 compaction | 小文件雪崩 | 例行 compaction + 监控 |
| 并发写不重试 | 任务随机失败 | 捕获冲突并重试，错开维护作业 |
| 写完不校验 | 结果错了也不知道 | 行数对账 + 质量指标 + 抽样 |
| 超长任务不分段 | 失败从头重跑 | checkpoint / 分阶段落盘 |

## 7.10 本章小结

- 写入模式优先 **overwrite 分区**（按天增量）或 **merge upsert**，保证幂等。
- **幂等三件套**：源表 status 标记 + 写入覆盖语义 + 目标表 `(id, model_version)` 去重键。
- Iceberg 的**原子提交**让失败重跑无副作用，还能 time travel。
- 并发写要**重试**，并与维护作业错峰。
- 并行写必然产生小文件 → **例行 compaction** 是标配。
- **schema 演进**加列不重写数据，溯源列/质量列可以后加。
- 写完**必须对账**（行数、空值率、质量指标、重复），指标进 MLflow 做跨批次对比。
