# 第 23 章 · 投入：团队、工期与成本清单

## 7.1 团队配置

| 角色 | 人数 | 职责 | 备注 |
|---|---|---|---|
| **平台后端** | 1–2 | 会话编排、控制面服务、存储与权限 | ★核心，必须熟悉容器/K8s |
| **平台前端** | 0.5–1 | 控制台（门户、空间管理、App 列表、成本页） | ★**不需要改 marimo 编辑器** |
| **数据/集成** | 0.5–1 | 数据源连接目录、凭证代管、SQL 引擎对接 | 可与数据平台团队兼任 |
| **运维/SRE** | 0.5 | 镜像、监控、容量、值班 | 上线后转为常驻 |
| **产品/推广** | 0.5 | 需求、规范、培训、种子用户运营 | ★常被忽略但决定成败 |

**最小可行配置**：**2–3 人**（后端 1–2 + 前端/集成 1）能做出 MVP；**上线后常驻 0.5–1 FTE** 维护。

## 7.2 分阶段工期

| 阶段 | 周期 | 交付物 |
|---|---|---|
| **0. 验证（PoC）** | 2–4 周 | 单机/小范围跑通 marimo + 内部数据源 + 一个示例 app；**验证用户接受度** |
| **1. MVP** | 3–5 个月 | SSO、会话编排、持久化、App 发布与权限、监控（P0 全部） |
| **2. 完善** | +2–3 个月 | 调度、审计、配额成本、AI 指向内部模型 |
| **3. 规模化** | 持续 | 模板库、Gallery、GPU 池、性能优化、推广 |

> ★**强烈建议先做 PoC**：2–4 周，成本极低，但能验证最关键的不确定项——**用户愿不愿意接受响应式范式（尤其「不要跨 cell 改对象」这条）**。这一步能省掉后面几个月的方向性返工。

## 7.3 成本构成

| 类别 | 说明 | 量级（示意，按国内成本粗估） |
|---|---|---|
| **① 一次性人力** | MVP 25–35 人周 ≈ **6–9 人月** | 按 3 万元/人月全成本 → **18–27 万元** |
| **② 持续运维人力** | 0.5–1 FTE | **18–36 万元/年** |
| **③ 算力** | 会话容器（CPU）+ GPU 池 + 常驻 App | 视规模：**数万～数十万元/年**（★GPU 是大头） |
| **④ 存储** | notebook、数据、产物、缓存 | 较小，通常 < 数万元/年 |
| **⑤ 模型/AI** | token 消耗（若用外部模型） | 视用量；**用内部模型则并入算力** |

**第一年总成本（示意）**：一次性 18–27 万 + 运维 18–36 万 + 算力存储数万 ≈ **40–70 万元**（不含 GPU 密集型场景）。

## 7.4 ★ 与采购 SaaS 的诚实对比

这是最容易被「开源免费」误导的地方。算一笔账（**以 50 名活跃使用者为例**）：

| 方案 | 年成本（示意） |
|---|---|
| **Deepnote**（约 $29/editor/月） | 50 × 29 × 12 ≈ **$17.4k ≈ 12.5 万元/年** |
| **Hex**（约 $38–65/seat/月） | 50 × 38～65 × 12 ≈ **16–28 万元/年** |
| **自建**（摊销后） | 第一年 **40–70 万**；第二年起 **20–40 万/年**（不含一次性） |

### 结论必须诚实说

> **单看「许可费替代」，自建并不一定省钱**——尤其在使用人数不多（< 30 人）或没有自有算力时，SaaS 订阅可能更便宜。

自建的成本优势只在以下条件下显现：

| 条件 | 为什么影响 |
|---|---|
| **人数规模大**（≥ 50–100 活跃用户） | SaaS 按 seat 线性涨价，自建边际成本低 |
| **多年摊销** | 一次性投入摊到 3 年，年均显著下降 |
| **已有算力/容器平台** | ★不新买机器，边际成本极低 |
| **需要 GPU** | SaaS 的 GPU 计价通常很贵；自建若已有 GPU 池则便宜 |

> ★**因此：不要把「省 license 费」当作自建的主理由。** 真正的主理由在第 8 章——**交付效率的量级提升**与**合规约束**。

## 7.5 隐性成本（容易漏算）

| 项 | 说明 |
|---|---|
| **迁移成本** | 存量 notebook 转换与验证（第 5.5 节）：2–4 人周起 |
| **培训与推广** | 规范文档、内部分享、种子用户辅导：**持续投入，不是一次性** |
| **上游跟进** | 定期同步 marimo 版本、rebase patch |
| **机会成本** | 2–3 人做 3–5 个月，这些人力本可以做别的 |
| **双轨期成本** | 新旧平台并行期的重复维护 |

## 7.6 风险清单

| 风险 | 影响 | 缓解 |
|---|---|---|
| **用户不接受响应式范式** | ★最高：平台没人用 | **先 PoC 验证**；规范里重点讲「同 cell 内改对象」 |
| **工程量失控** | 工期翻倍 | ★严守 MVP 边界（第 3.6 节）；先 PoC |
| **上游大版本变化** | patch 失效 | patch 最小化 + 尽量上游化（第 5.3 节） |
| **算力成本失控** | 账单超预期 | ★闲置回收 + 配额 + 成本可视化（上线就有） |
| **做成没人维护** | 平台烂尾 | ★**立项时就确定常驻运维归属**，否则不要启动 |
| **合规审查未过** | 中途叫停 | 早期拉安全/法务参与，明确数据边界 |

## 7.7 本章要点

- 团队：**2–3 人做 MVP**（后端 1–2 + 前端/集成 1），**上线后常驻 0.5–1 FTE**。
- 工期：**PoC 2–4 周 → MVP 3–5 个月 → 完善 +2–3 个月**；★**先 PoC 验证用户接受度**。
- 成本：一次性 **18–27 万**；持续 **运维 18–36 万/年 + 算力数万～数十万**。第一年合计示意 **40–70 万**。
- ★**诚实结论：纯许可费视角，自建不必然省钱**（50 人规模下 SaaS 约 12–28 万/年，自建首年更高）。自建优势在**规模大、多年摊销、已有算力、需要 GPU** 时才显现。
- 隐性成本：迁移、★培训推广（持续）、上游跟进、机会成本、双轨期。
- 头号风险是**用户不接受响应式范式**——用 PoC 提前验证；其次是**烂尾**——立项即定运维归属。
