## 3.1 本章要解决的核心问题

很多团队上这套架构后，第一反应是"GPU 不够，加卡"。但加完卡发现吞吐没涨——因为**瓶颈根本不在 GPU**，而在 CPU 侧的：

1. 从 OSS **拉取**图片/视频字节（网络 IO）
2. **解码**成像素/帧（CPU 计算）
3. **预处理**（resize、归一化）（CPU 计算）

**判断方法（很重要）**：跑一次任务，看 GPU 利用率。

- GPU 利用率长期 < 60% → **瓶颈在 CPU 侧**，加卡纯属浪费
- GPU 利用率 > 90% 且 CPU 还有余量 → 才是真的该加卡

这与第 5 章的 `stats()` 定位方法配合使用（见 3.8）。

## 3.2 图片：解码与预 resize

**关键优化：预 resize 到统一尺寸**

```python
# 反例：原图直接送模型
img = Image.open(fetch(oss_path))          # 可能 4000×3000

# 正例：解码后立即 resize 到模型的最佳输入尺寸
img = Image.open(fetch(oss_path)).convert("RGB")
img = resize_keep_ratio(img, target=448)   # 或按模型支持的动态分辨率
```

**为什么有效**：

- **显存**：VLM 的视觉编码器对输入像素数敏感，原图会产生海量 visual token，KV cache 暴涨、并发数骤降
- **带宽与内存**：4K 图解码后几十 MB 内存，批量处理时 CPU 内存先爆
- **padding 浪费**：同一批内尺寸不一致会引入大量 padding，resize 统一后 batch 更紧凑

**原则**：resize 到"刚好够模型看清"的分辨率。caption 任务通常不需要 4K 细节；但 OCR 密集型任务（要读图中文字）需要更高分辨率——按任务定。

## 3.3 视频：抽帧策略决定成本

视频比图片贵一个数量级，优化空间也最大。

**核心原则：不要把所有帧都送进 VLM。**

| 策略 | 做法 | 适用 |
|---|---|---|
| **固定 fps 采样** | 每秒抽 1–2 帧 | 通用，成本可控 |
| **关键帧（I-frame）优先** | 只解关键帧，跳过 P/B 帧 | 成本最低，但可能丢运动细节 |
| **场景切换检测** | 画面变化时多抽，静止段少抽 | 内容变化大的视频 |
| **固定帧数上限** | 整段最多送 N 帧（如 8/16/32） | 控制 token 上限，防止长视频打爆 |

```text
10 分钟视频 @ 30fps = 18000 帧
→ 全送：token 爆炸，单次请求可能几分钟，GPU 被单任务占死
→ 抽 1fps = 600 帧：仍然太多
→ 抽到上限 32 帧：合理，配合"均匀覆盖全片"的采样
```

**配套**：视频解码用**硬件解码**（若有）或高效的解码后端，避免纯 CPU 软解成为死穴。

## 3.4 并发拉取与连接管理

从 OSS 拉对象是网络 IO，**串行拉 = 自废武功**。

| 要点 | 做法 |
|---|---|
| **并发拉取** | 用线程池 / asyncio 并发拉一个 batch 内的多个对象（如 16–64 并发） |
| **限流** | 并发不是越大越好——打爆 OSS 带宽或触发限流反而更慢，要压测找拐点 |
| **Range GET** | 视频只需部分字节时（如只读头信息判断时长），用 Range 请求而非全量下载 |
| **重试与超时** | 网络抖动常态，必须带退避重试；单文件超时则跳过并记录，不能卡死整个 batch |
| **连接复用** | 用长连接 / 连接池，避免每文件一次 TLS 握手 |

**经验值**：并发数通常从"CPU 核数 × 2"起步，再按 OSS 带宽与实际吞吐压测调整。

## 3.5 缓存：别重复拉同一份数据

离线批处理里常见的浪费：**同一个媒体被多次处理**（如"一图多问"：同时生成描述、OCR、属性标签），每次都重新拉取 + 解码 + 编码。

三层缓存对策：

| 层 | 缓存什么 | 收益 |
|---|---|---|
| **本地磁盘/内存缓存** | 已下载的对象字节、已解码的帧 | 省重复的网络与解码 |
| **vLLM encoder-output caching** | 同一张图的**视觉编码结果** | 省掉最贵的视觉编码器重算（第 5 章详述） |
| **结果缓存** | 已处理过的 `(id, model_version)` 结果 | 重跑任务时直接复用，配合幂等 |

**注意**：视频场景下本地缓存很容易撑爆磁盘，要设容量上限 + LRU 淘汰。

## 3.6 CPU / GPU 资源配比

这是最容易被拍脑袋定的参数。配比取决于"每个样本的 CPU 处理成本"：

| 场景 | CPU 成本 | 建议配比（每 GPU） |
|---|---|---|
| 小图 + 短 caption | 低 | 4 CPU : 1 GPU 起步 |
| 大图 / 高分辨率 | 中 | 8 CPU : 1 GPU |
| 视频抽帧 | **高** | 8–16 CPU : 1 GPU，甚至需要独立扩预处理池 |

**做法**：Ray Data 允许给不同 Stage 配不同资源——**把预处理 Stage 和推理 Stage 的资源分开配**，让 CPU 池可以独立于 GPU 池扩缩。这正是 Ray Data "hybrid resource orchestration" 的价值。

**验证**：调完配比后看 GPU 利用率是否上去。没上去说明 CPU 还是不够（或拉取仍是瓶颈）。

## 3.7 坏文件与超大文件：必须优雅处理

生产数据一定有脏数据：损坏的图片、0 字节文件、几 GB 的超大视频、格式不支持的文件。

**必须做的三件事**：

1. **解码前过滤**：利用源表的 `size_bytes` / `duration` 列，在拉取**之前**就过滤掉明显异常的（如 > 100 MB 的图、> 2 小时的视频）
2. **处理时兜底**：解码/推理单条失败要 `try/except` 捕获，标记该行失败，**不能让整个 batch 崩掉**（Ray Data 会整批重试，代价极高）
3. **记录到质量指标**：把 `reject_rate`、失败原因分布记进 MLflow（见第 8 章），否则你永远不知道数据脏到什么程度

```python
def safe_process(row):
    try:
        return process(row)
    except Exception as e:
        return {"id": row["id"], "caption": None,
                "valid": False, "reject_reason": type(e).__name__}
```

## 3.8 用 stats() 定位瓶颈（实操方法）

Ray Data 提供 `ds.stats()`，输出**每个 operator 的耗时与吞吐**。这是定位瓶颈的唯一可靠手段：

```python
result = processor(ds).materialize()
print(result.stats())
```

**怎么看**：

```text
Operator 1 ReadIceberg     : throughput 50,000 rows/s   ← 读表很快
Operator 2 FetchAndDecode  : throughput   300 rows/s    ← 瓶颈在这！
Operator 3 vLLMGenerate    : throughput 2,500 rows/s
Operator 4 WriteIceberg    : throughput 8,000 rows/s
```

- 找出**吞吐最低**的那一环，它就是瓶颈
- 预处理（Fetch/Decode）吞吐远低于推理 → **加 CPU、优化解码、上缓存**，而不是加 GPU
- 推理吞吐低 → 才去调第 5 章的 vLLM 参数

**调优顺序永远是：先量，再改，再量。** 凭感觉加卡是最贵的试错方式。

## 3.9 本章小结

- **先确认瓶颈在哪**：GPU 利用率低 = CPU 侧（拉取/解码）是瓶颈，加卡无效。
- **图片**：解码后立即 resize 到统一尺寸，省显存、省内存、减 padding。
- **视频**：抽帧策略决定成本，控制送进模型的帧数上限，优先关键帧/均匀采样。
- **拉取**：并发 + 限流 + 重试 + 连接复用；Range GET 减少无效传输。
- **缓存**：本地缓存省重复拉解，vLLM encoder caching 省视觉编码重算。
- **配比**：CPU:GPU 按样本处理成本定，视频场景要显著更多的 CPU。
- **脏数据**：解码前过滤、处理时兜底、失败记进质量指标。
- **方法论**：用 `stats()` 逐 operator 看吞吐，先量再改。
