# 第 12 章 · 词表再校准：视频到底有没有词表

## 12.1 先认错：前面写绝对了

有读者指出：Hugging Face 上的视频 tokenizer 明摆着都有词表，书里说「视频理解侧没有词表、不查表」是不是太绝对了？

**这个质疑成立，而且比「说得绝对」更严重一点。** 第 2 章 2.7 节把「视频输入也要查表」直接列进「三个常见误解」，这在 Emu3、Chameleon 那条路线里是**标准做法**，属于事实性错误，不只是措辞过强。第 4 章标题、4.1 表格、4.9 小结，以及第 10、11 章的几处结论，也都把「本书所选方案」当成了「全模态模型的性质」。

这一章做三件事：拆开「词表」这个词、给出 Hugging Face 上可核查的实例、列出逐条修订清单。**教学基准不变**（第 1~10 章那个金属杯例子仍走方案 B），但所有全称判断都改成带路线限定的表述。

## 12.2 「词表」至少是三样东西

争论往往不是「有没有」，而是各说各的：

| 含义 | 长什么样 | 作用 | 谁在用 |
|---|---|---|---|
| **① 主干 embedding 表** | `nn.Embedding(V, d)` | ID → d 维向量，**进 Transformer 主干** | 文本必有；Emu3/Chameleon 的视觉也有 |
| **② 量化码本 codebook** | `nn.Embedding(K, c)` 或 FSQ/LFQ 的整数集 | 最近邻量化成 ID，主要给 **decoder 重建像素/波形** | VQ-VAE、VQ-GAN、MAGVIT、Cosmos DV |
| **③ 连续投影的「无限词表」** | `Conv2d(3, d, k=s=14)` | 任意 patch → d 维浮点，**没有有限集合** | ViT/SigLIP + projector，本书方案 B |

书第 4 章其实自己写过第三种的比喻：*「词表的等价物是所有可能的 patch 组合，但我们不枚举它，只学一个线性函数」*。既然承认这是「无限词表」，再说「视频没有词表」就自相矛盾了——准确说法只能是「视频没有**有限的、可查的离散词表**」。

再加一层反直觉：**有词表大小 ≠ 有一张可查的表。** MAGVIT-v2 的 LFQ（Lookup-Free Quantization）故意把码本 embedding 维度降到 0，用 `sign(z)` 二值化直接拼出整数 ID，默认 `K = 2^18 = 262144`。它有 26 万个 ID，却没有任何 `nn.Embedding(K, d)` 可以查。所以「HF 上这个模型有词表吧」这句话，连在 LFQ 模型上都要再问一句「你指哪一种」。

## 12.3 真正的判据是两问，不是一问

书里原来的判据是「**这个模态要被采样吗？** 要 → 离散有词表；不要 → 连续向量」。这个判据在方案 B 里好用，但不普适。反例就是 Emu3：视频在理解任务里只是「读」，可因为整条序列要统一成一个 next-token 目标，输入也就被离散化了。

正确的判据是两问：

```
Q1  token 是离散 ID 还是连续向量？
Q2  若有 ID，它查的是主干 embedding 表，还是只喂给 decoder 重建？
```

四种组合，全部都有真实系统：

| | 输入侧 token | 主干查表 | 码本 | 代表 |
|---|---|---|---|---|
| **A · 连续投影**（本书方案 B） | `[d]` 浮点 | 否 | 无 | LLaVA / Qwen-VL / Qwen2.5-Omni 视觉侧 |
| **B · 统一离散**（本书方案 A） | 整数 ID | **是** | 有 | **Emu3 / Chameleon / Emu3-VisionTokenizer** |
| **C · 离散但只给 decoder** | 整数 ID | 否 | 有 | MAGVIT-v2 / Cosmos DV / C-ViViT 走生成管线时 |
| **D · 连续 latent + 生成解码** | `[c]` 浮点 | 否 | 无 | Wan / Sora / FLUX 的 3D 因果 VAE + DiT；Higgs 的 2 image latents |

注意 B 和 C 都「有词表」，但一个是**主干词表**（会被 softmax、被采样、参与 CE loss），一个是**重建码本**（只在 decoder 里查）。把这两者混为一谈，正是前面几章出问题的根源。书第 2 章说「一个 ID 绑两套向量」（`E[id]` 进主干 + `codec.codebook[id-offset]` 出信号），那只适用于 **B**；在 C 里根本没有第一套。

## 12.4 Hugging Face 上可核查的实例

以下是能直接查到配置的具体模型，数字来自官方 docs / model card / 论文：

| 模型（HF） | 类型 | 词表 / 码本 | 输入侧长什么样 |
|---|---|---|---|
| **Emu3**（`transformers` 官方 model doc） | B 统一离散 | `Emu3VQVAEConfig(codebook_size=32768, embed_dim=4, temporal_downsample_factor=4)`；`Emu3TextConfig(vocab_size=184622, hidden_size=4096, num_hidden_layers=32)` | `4×512×512` 视频或 `512×512` 图像 → **4096 个离散 token**，直接进 `input_ids` 查主干表 |
| **Chameleon** | B 统一离散 | 图像 VQ 8192 项，与文本共一张表 | 图像输入是 ID |
| **O2-MAGVIT2-preview**（`CofeAI/O2-MAGVIT2-preview`，Apache-2.0，0.4B） | C | **LFQ `2^18 = 262144`**，无可查表 | 视频 → 整数 token，只给 decoder 重建 |
| **MAGVIT-v2 / v1** | C | v2 LFQ 262144；v1 3D-CNN VQ **1024** | K600 帧预测 FVD 5.2（v1 9.9）；ImageNet-512 masked LM FID 1.91 |
| **Cosmos Tokenizer**（NVIDIA，开放权重） | C + D 双版本 | 离散版 **FSQ ~64K vocab**；连续版 latent `C=16` 无码本 | `CV4×8×8 / CV8×8×8 / DV8×16×16`，最高 2048× 压缩；720×1280 编码 34.8ms |
| **C-ViViT**（Phenaki） | C | VQ **8192, dim 32** | 时序感知 tokenizer；对照逐帧 VQGAN 重建 FVD 306.1 → 65.78 |
| **Wan / Sora 类 3D 因果 VAE** | D | 无码本 | `[T/4, H/8, W/8, 16]` 浮点 latent → DiT 流匹配 |

**Emu3 是最硬的反例**：HF 官方文档里 `vocab_size=184622` 的定义写得很直白——「可由 `input_ids` 传入的 token 种类数」。视频 token 就在这 18 万里。也就是说，**理解侧不仅查表，查的还是和文本同一张表**。书第 2 章 2.7 把这种做法叫「误解」，必须改。

另外 Emu3 的 Nature 论文还给了一个有意思的结论：从零训练时，「ViT encoder + LLM」的组合式架构（LLaVA 路线）先天优势几乎消失，纯 decoder 的 next-token 模型在视觉理解上与之相当。所以方案 B 的「理解侧量化纯亏」也不是定律——**它是有代价的取舍，代价换来的东西（统一目标、生成/理解同源）在别的场景里可能值这个价**。

## 12.5 同一帧金属杯，四条路线分别变成什么

回到全书那个 `t=3200ms` 的例子，杯身那道镜面高光：

```python
# A 连续投影（本书前 10 章）
vis = resampler(vit(frame))                 # [64, 4096] 浮点，高光是连续值，材质线索保真

# B 统一离散（Emu3 形态）
ids = vq_tokenizer.encode(frame)            # [4096] 整数，0..32767
x   = E[ids + TEXT_VOCAB_OFFSET]            # [4096, 4096] ★查主干表，与文本共享同一张 E

# C 离散但只给 decoder
ids = causal_3d_tokenizer.encode(clip)      # [21, 56, 56] 整数，LFQ 0..262143
pixels = decoder(ids)                       # 码本只在重建时用，主干拿的是别的表示

# D 连续 latent + 生成解码
z = causal_vae.encode(clip)                 # [21, 56, 56, 16] 浮点，无码本
frames = dit_flow_matching(z, text)
```

四条都能跑通全双工的理解侧，区别在：A 保真但和文本不同空间；B 统一但高光可能被量化成普通灰块（书里的原始担忧，仍然成立，只是不再是「不可能」）；C/D 主要用于生成，理解侧通常另配一路 encoder。

一个细节值得记住：**LFQ 里「码本大小」是 ID 空间大小，不是参数量**。这也是为什么 262144 个视觉 ID 塞进 `V=75840` 的统一表会撑爆 head（书第 8 章算过，head 会涨到约 2.6GB）——但那只针对 B 类路线；C 类路线的 26 万 ID 根本不进 LLM 词表，不产生这个冲突。

## 12.7 那到底该选哪条

| 你的目标 | 选 | 理由 |
|---|---|---|
| 复用现成 LLM、理解保真优先 | **A** | 连续投影不量化，材质/OCR 等细节损失最小；VLM 主流 |
| 一个 next-token 统一理解与生成 | **B** | Emu3/Chameleon 路线，训练目标最干净，代价是量化损失 |
| 长视频 / 高画质生成 | **C 或 D** | 需 3D 因果 tokenizer；怕码本坍缩选 D（连续 latent + DiT），要离散符号选 C（LFQ/FSQ） |
| 全双工实时 + 输出画面 | **D** | Higgs 形态：主干每片只出 2 个 latent，像素交给独立因果 DiT |
| 零样本换音色 / 换脸 | 与词表无关 | 参考音频/图只进 decoder，属于条件注入而非词表设计 |

一句话：**别问「视频有没有词表」，问「我要不要一个统一的离散符号空间」**。要，就接受 B 的量化代价和 head 膨胀；不要，A 和 D 都更省，只是文本与视觉要走两条表示通路再靠注意力融合。

## 12.8 本章小结

- 书里「视频理解侧没有词表 / 不查表」是**把方案 B 的选择写成了事实**，ch02 2.7 更把方案 A 的做法误列为「误解」，已逐处修订并新增本章对账。
- 「词表」有三种含义：主干 embedding 表、量化码本、连续投影的无限词表；**有 ID 空间 ≠ 有可查的表**（LFQ）。
- 正确判据是两问：token 离散还是连续？ID 查主干还是只喂 decoder？由此得到 A/B/C/D 四种组合。
- Hugging Face 上 Emu3（`codebook_size=32768`、`vocab_size=184622`）是最硬的反例：视频输入就是离散 ID 且查主干表；MAGVIT-v2/O2-MAGVIT2、Cosmos Tokenizer、C-ViViT 则是有码本但只用于重建的 C 类。
- 选型结论：**别问有没有词表，问要不要统一离散符号空间**。
