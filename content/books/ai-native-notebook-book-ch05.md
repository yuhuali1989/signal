# 第 12 章 · 状态、数据与可复现：文件格式、环境与数据连接

## 5.1 文件格式：可复现的第一道门

Notebook 存在什么文件里，直接决定了它能不能被版本管理、能不能被 review、能不能被复现。

| 格式 | 代表 | 结构 | 版本管理 | 输出处理 |
|---|---|---|---|---|
| **.ipynb** | Jupyter、Colab、（Deepnote 兼容） | JSON | ❌ diff 噪声大（输出 base64 混在里面） | 输出常随文件保存，污染 diff |
| **.py（响应式）** | Marimo | 纯 Python | ✅ 干净、逐行 diff | 输出不进文件 |
| **.py（percent 格式）** | Jupytext、VSCode | 纯 Python（`# %%` 分格） | ✅ 干净 | 输出不进文件 |
| **.qmd / .Rmd** | Quarto、R Markdown | Markdown + 代码块 | ✅ 干净 | 适合出版 |
| **专有格式** | Hex 等 | 云端 | 依赖平台自带版本能力 | 平台管理 |
| **YAML + .ipynb** | Deepnote（.deepnote YAML） | 人类可读 YAML | ✅ 相对友好 | 平台管理 |

**核心矛盾**：`.ipynb` 把**代码 + 输出 + 元数据**塞进同一个 JSON。这带来三个长期痛点：

1. **diff 噪声**：改一行代码，diff 里可能带一大段 base64 图片变化
2. **合并冲突**：多人协作时 JSON 冲突难解
3. **输出污染仓库**：大图/大表输出让仓库膨胀

**缓解手段**：

- 提交前清空输出（nbconvert / 钩子）
- **jupytext**：.ipynb 与 .py 配对，只版本化 .py
- 换成纯文本原生格式（marimo / percent / Quarto）
- 选择支持**跨格式转换**的平台（如 Deepnote 可在 Jupyter、Quarto、percent、marimo 之间转换）

## 5.2 版本管理与 Code Review

AI 时代这一点更重要：**Agent 会改代码，所以改动必须可审查**。

| 要求 | 做法 |
|---|---|
| 变更可 diff | 优先纯文本格式；.ipynb 需配 jupytext 或清输出 |
| 变更可 review | Agent 的修改要能进入 PR / 平台 diff 视图，不能消失在会话里 |
| 变更可回滚 | 版本历史或平台内置版本（Hex 有分支与 diff；Deepnote 有 Git 集成与评论） |
| 谁改的可追溯 | 记录 author（人 or agent） |

**一条实用纪律**：把"Agent 的改动必须落到可 diff 的产物上"写进团队规范——否则 AI 越能干，审计黑洞越大。

## 5.3 环境复现：别让"在我机器上能跑"重演

即使执行模型完美、文件格式干净，环境不一致照样复现不了。

| 环境方案 | 说明 | 适用 |
|---|---|---|
| **pip / conda 声明** | requirements.txt / environment.yml | 基础，但跨机器仍可能漂移 |
| **Docker 镜像** | 完全固化系统依赖 | 最可靠，自托管场景推荐 |
| **平台托管环境** | 平台预配置 + 自定义镜像/初始化脚本 | 省运维（Deepnote/Hex 路线），但要确认可固化 |
| **内核规格** | 指定语言版本与 kernel | 多语言场景必需 |

**常见坑**：

- 只锁 Python 包，不锁系统库（如 GDAL、CUDA）→ 换机器就挂
- 隐式依赖本地文件（如 `~/data/x.csv`）→ 别人没有
- 用了没声明顺序的随机种子 → 结果每次不同

**建议**：用镜像或锁文件**完整声明**依赖；随机种子显式固定；数据用可访问的路径/连接，而非本地绝对路径。

## 5.4 数据连接与大数据

Notebook 很少只跑本地小数据，关键在于**能不能把计算下推到数据所在的地方**。

| 能力 | 说明 |
|---|---|
| **原生 SQL cell** | 在 notebook 里直接写 SQL，平台下发到数仓执行（Hex / Deepnote 的强项） |
| **数据连接器** | 预置连接：Snowflake、BigQuery、Databricks、Redshift、Postgres、S3、dbt 等 |
| **下推 vs 拉回** | 好的架构把聚合下推到数仓，只把结果取回；差的架构把整表拉到 notebook 内存 |
| **样本/schema 预览** | 浏览数据表时先看 schema 与样本，避免无谓拉取（也是 AI 上下文的来源） |

**架构级影响**：如果你的分析对象是 TB 级数仓表，**"有没有原生 SQL 下推"比"AI 好不好用"更决定平台是否可用**——因为拉不动数据的时候，AI 再聪明也没用。

## 5.5 缓存、检查点与产物

响应式执行的一个现实顾虑是"上游一改，下游全重跑"。缓解手段：

| 机制 | 说明 |
|---|---|
| **中间结果缓存** | 重跑时若上游输出未变，复用缓存结果（避免重复算耗时步骤） |
| **检查点（checkpoint）** | 把昂贵的中间结果落盘（parquet / 特征表），后续直接读 |
| **产物管理** | 输出的表/图/模型作为版本化产物，而非只存在 notebook 里 |
| **变量持久化** | 长任务可分阶段执行 |

**实践建议**：把耗时超过几分钟的步骤显式做检查点——这既加快迭代，也让 notebook 从"一次性的"变成"可恢复的流水线"。

## 5.6 可复现性 Checklist

上线前逐项自检：

- [ ] **执行顺序无关**：从零跑一遍（Restart & Run All）结果与展示的一致
- [ ] **无隐藏变量**：删除 cell 后其定义的变量不再影响结果
- [ ] **依赖完整声明**：包 + 系统库 + 版本锁定（镜像或锁文件）
- [ ] **数据可访问**：不依赖本地绝对路径；连接凭据用托管而非硬编码
- [ ] **随机性可控**：随机种子固定，或结果有容差
- [ ] **输出不污染版本库**：提交产物不含大输出，或用纯文本格式
- [ ] **定时任务可重跑**：调度运行的结果与手动一致
- [ ] **他人可复现**：换一台机器/换一个人，按文档能跑出同样的数
- [ ] **AI 改动可审查**：agent 的修改能进 diff / PR
- [ ] **文档化**：README 说明怎么跑、依赖什么、产出什么

## 5.7 本章小结

- **文件格式是可复现的第一道门**：.ipynb（JSON，输出污染 diff）vs 纯文本（.py / .qmd / percent）vs 专有格式。
- 缓解 .ipynb 痛点：清输出、jupytext 配对、换纯文本原生格式、或用支持跨格式转换的平台。
- **AI 时代版本管理更重要**：agent 的改动必须可 diff、可 review、可回滚、可追溯。
- **环境复现**：完整声明依赖（含系统库）、固定种子、数据与凭据不可硬编码。
- **大数据场景**：原生 SQL 下推比 AI 能力更决定平台可用性。
- 耗时步骤要做**缓存/检查点**，让 notebook 变成可恢复的流水线。
- 给了**可复现性十项 Checklist**——上线前逐项自检。
