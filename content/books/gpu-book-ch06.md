# 第 6 章：多进程共享一块 GPU——资源如何被切分

> **学习目标**：理解「为什么多进程要共享 GPU」，看驱动如何用时间片 + 上下文切换把一块卡「分给」多个进程，以及 MPS / MIG / 虚拟化三种隔离强度递增的方案分别适用什么场景。

---

## 6.1 为什么要共享

一块 H100 价值数万人民币，但 **单一推理任务常常只能用到 10–30% 算力**。让每个任务独占一整张卡，是巨大的浪费。共享的动机：

- **提高利用率**：多个小负载拼满一卡。
- **降低成本**：云上按卡计费，共享 = 省钱。
- **隔离与多租户**：不同用户/服务跑在同一集群，需要互不干扰。

难点在于：GPU 不是天然「多进程安全」的——它有一大块 **共享的全局显存** 和 **单一的命令流入口**，多个进程如何既共享又互不踩踏？

---

## 6.2 默认模式：时间片轮转 + 上下文切换

**最朴素的方式**：操作系统/驱动让多个进程「轮流用」GPU。

- 每个进程拥有 **独立的 CUDA 上下文（context）**、独立的页表、独立的显存分配。
- 驱动用 **时间片（time-slice）** 在进程间切换；某进程时间片用完，保存其状态，恢复下一个。
- 进程完全 **内存与地址隔离**：A 进程看不到 B 进程的显存。

代价是 **上下文切换（context switch）开销**：

| 要保存/恢复的内容 | 量级与代价 |
|---|---|
| SM 寄存器状态 | 数万寄存器/SM，需落回显存 |
| 页表（GPU 页表） | 映射变更，TLB 失效 |
| 显存分配元数据 | 簿记 |
| L2 内容 | 往往被整体失效（脏数据需回写/丢弃） |

一次切换可能 **数十到数百微秒**，且 **L2 被清空**导致下一个进程「冷启动」。对「频繁切换、每次算得少」的场景，这种开销会吃掉大部分收益。

> Hyper-Q（4.6）在这里也起作用：它让多进程的命令能进入不同硬件队列，减少「合并成单队列导致的虚假串行」。但时间片切换本身仍不可避免。

---

## 6.3 MPS：共享一个上下文，砍掉切换

**MPS（Multi-Process Service）** 是 NVIDIA 提供的「用户态服务」：多个客户端进程把 kernel 提交给 **同一个 MPS 守护进程**，由它 **合并进同一个 CUDA 上下文** 再提交给 GPU。

```
进程A \                    共享上下文 ┐
进程B  → MPS 守护进程 ─────────────→ GPU（无频繁上下文切换）
进程C /                                ┘
```

收益：
- **消除进程间上下文切换**：大家共用一份上下文、一份页表。
- **资源合并**：多个进程的 warp 能在同一时间片内交替驻留 SM，提升利用率。
- **支持 Hyper-Q 多队列**，真正并行。

代价/风险：
- **故障隔离弱**：共享上下文意味着「一个进程段错误 / 越界写」可能 **拖垮整个 MPS 上下文**，同卡其他进程一起挂（第 7 章细谈）。
- **显存是共享池**：任一进程 OOM 可能影响他人（无硬限额）。
- 需要显式启动 `nvidia-cuda-mps-control` 守护进程。

> 适用：信任的同团队多任务拼卡（如同一训练作业内的多进程数据并行），或需要低延迟切换的多推理服务。

---

## 6.4 MIG：硬件级强隔离分区

**MIG（Multi-Instance GPU）** 是 A100/H100 独有的「杀手锏」：在 **硬件层面** 把一张卡切成多个 **独立实例（GI）**，每个实例拥有：

- 专属的 **SM 子集**（算力硬隔离）
- 专属的 **L2 缓存切片**
- 专属的 **HBM 容量与带宽份额**
- 专属的 **媒体/拷贝引擎**

```
H100 可被切为：
  [1g.10gb] [1g.10gb] [1g.10gb] [1g.10gb]
              [2g.20gb]
        [3g.30gb]
        [4g.40gb] [4g.40gb]
（共 7 个实例，按「算力档位 + 显存」组合，总和不超过整卡）
```

特点：
- **强隔离**：一个 MIG 实例崩溃 **不影响** 其他实例；彼此显存/算力物理分开。
- **QoS 保障**：每个实例的带宽/算力是预留的，不会被邻居挤占。
- 代价：**切片粒度较粗**（最少 1/7 卡），且 **不能把多个实例合并成一个大实例来跑单任务**（除非重新划分）。
- MIG 实例间 **不能 P2P / 不能组成单一 NCCL 通信组**（因为它们 conceptually 是「独立的小 GPU」）。

> 适用：多租户云、需要 SLA 保障的推理服务（每个客户一个实例，互不干扰）。

---

## 6.5 GPU 虚拟化（vGPU / SR-IOV）

在虚拟化环境（VM、云桌面）里还有更上层的方案：

- **vGPU（NVIDIA 虚拟 GPU）**：把物理 GPU 通过 Hypervisor 虚拟成多个 vGPU 给不同 VM，带授权与调度策略。
- **PCIe SR-IOV**：把单个物理 GPU 暴露为多个「虚拟功能（VF）」，VM 直接透传访问，降低虚拟化开销。

这类方案在「云桌面 / 图形工作站虚拟化」更常见，对 AI 训练/推理的裸金属共享通常由 MPS/MIG 解决。

---

## 6.6 容器与编排：把共享能力交到平台手里

在 Kubernetes 里，GPU 共享通过以下组件落地：

- **NVIDIA Container Toolkit**：让容器内能用 GPU（挂载驱动、设备节点 `/dev/nvidia*`）。
- **Kubernetes Device Plugin（GPU）**：把节点上的 GPU 作为「整数资源」`nvidia.com/gpu` 暴露；默认 **一张卡是一个不可分割单位**（不能写 0.5 卡）。
- **共享方案在 K8s 中的落地**：
  - **MPS**：以 DaemonSet 形式在节点起 MPS 服务，Pod 通过环境变量 `CUDA_MPS_PIPE_DIRECTORY` 接入，多个 Pod 共用一卡（无硬隔离）。
  - **MIG**：Device Plugin 把每个 MIG 实例当成独立「小 GPU」资源，Pod 请求 `nvidia.com/mig-1g.10gb: 1` 即可精确占一个切片。
  - **第三方调度器**（如 Volcano / 腾讯 qGPU / 阿里 cGPU）：在驱动层做「显存 + 算力」的细粒度限制与隔离，弥补原生 K8s 不能按分数分配 GPU 的不足。

> 重要限制：**Linux cgroup 目前不能限制 GPU 算力/显存**（GPU 没有对应的 cgroup 子系统）。所有「按份额限制」都得靠 MPS / MIG / 厂商扩展实现，而非通用 cgroup。

---

## 6.7 公平调度与限制

当多个进程无强隔离地共享（默认模式或 MPS）：
- 驱动按时间片轮转，经典实现中 **偏向「先到先服务 + 优先级」**，并无「按权重公平分配算力」的硬保证。
- 某些场景需要 **优先级**（如在线推理 > 离线训练），可用 `nvidia-smi` 的 compute mode / 优先级类，但能力有限。
- 真正可预测的隔离，还是回到 **MIG** 或厂商级 qGPU/cGPU。

---

## 6.8 本章小结

三种共享强度递增：

| 方案 | 隔离强度 | 切换开销 | 显存 | 适用 |
|---|---|---|---|---|
| 默认时间片 | 进程级（弱） | 高（上下文切换） | 各自独立 | 简单多任务 |
| MPS | 上下文共享（最弱） | 极低 | 共享池 | 同信任域、要低延迟 |
| MIG | 硬件强隔离 | 无（并行） | 物理切片 | 多租户、要 SLA |

> 选择口诀：**要隔离选 MIG，要拼利用率且彼此信任选 MPS，图省事且负载轻用默认时间片**。K8s 下靠 Device Plugin + 厂商扩展落地。
