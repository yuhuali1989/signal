## 1.1 场景：一列 embedding 引发的选择题

假设你有一张 Iceberg 表，里面有一列 **embedding**（图片/文本的向量，如 768 维 float32），现在要支持"给定一个查询词向量，找出内积最大的 Top-K"。

这是多模态数据闭环里最常见的检索需求：找相似图片、找难例、RAG 召回、去重。

摆在你面前的选项，最典型的是这两个：

| | 方案 | 做法 |
|---|---|---|
| **A** | **StarRocks（SR）直查** | 直接在 StarRocks 里读 Iceberg 的 embedding 列，**用内积函数算相似度**，不复制数据 |
| **B** | **导入 Milvus** | 把 embedding **再复制一份进 Milvus**，在 Milvus 里建索引做检索 |

用户最朴素的疑问是：**"我直接在 Iceberg 上算不就行了，为什么要多导一份到 Milvus？"**

这本书就是回答这个问题的。

## 1.2 先把候选路线列全（不止两条）

真实决策里其实有四条路线，先把全景摆出来，避免漏掉更优解：

| 编号 | 路线 | 数据是否复制 | 是否用 ANN 索引 | 一句话特征 |
|---|---|---|---|---|
| **A** | **SR 直查 Iceberg 外表 + 暴力内积** | ❌ 不复制 | ❌ 暴力 | 零额外存储、SQL 友好，但延时随数据量线性增长 |
| **A2** | **导入 StarRocks 内表 + ANN 索引** | ✅ 复制到 SR | ✅ SR 原生 HNSW/IVFPQ | 有索引加速 + 强 SQL 混合查询，代价是复制一份 |
| **B** | **导入 Milvus（专用向量库）** | ✅ 复制到 Milvus | ✅ 成熟 ANN | 毫秒级、高 QPS、可扩展，代价是复制 + 新系统 |
| **B2** | **Milvus 原地索引（External Collections）** | ❌ 不复制 | ✅ 附着 Iceberg 快照 | **既要 ANN 性能又不复制数据**——最优解之一，但要确认产品支持 |

> **本书主线**：用户问的是 **A vs B**。但 A2 和 B2 是绕不开的参照，尤其 **B2** 常常是"又要马儿好又要马儿不吃草"的答案。全书以 A vs B 为主线，其余作为变体对照。

## 1.3 A 与 B 的本质差异：两道分水岭

所有对比最终都归结到两个根本差异：

**分水岭一：暴力计算 vs 索引**

| | A 直查（暴力） | B（ANN 索引） |
|---|---|---|
| 复杂度 | **O(N × D)**，随数据量**线性**增长 | **亚线性**（图导航/倒排剪枝） |
| 100 万条 | 还行 | 很好 |
| 1 亿条 | 分钟级 | 毫秒~几十毫秒 |
| 10 亿条 | **小时级** | 毫秒~几十毫秒 |

**分水岭二：不复制 vs 复制**

| | A 直查 | B 导入 |
|---|---|---|
| 存储 | 0 额外（embedding 只在 Iceberg） | **×2**（Iceberg 一份 + Milvus 一份 + 索引） |
| 一致性 | 天然一致（直接读当前快照） | 需要同步，**最终一致** |
| 运维 | 0 新系统 | 多一套 Milvus 集群 + 同步管道 |

**A 的优势全在"不复制"**（省存储、省同步、天然一致）；**B 的优势全在"有索引"**（快、可扩展）。这就是全部权衡。

## 1.4 StarRocks 直查 Iceberg 的一个关键事实（必须先讲清）

StarRocks 从 **3.4** 起支持向量索引（ANN），包括 **HNSW** 和 **IVFPQ**，并支持 **L2 / Cosine / Inner Product（内积）** 三种度量——这是好消息。

但有一个**致命细节**：

> StarRocks 的向量索引是**基于自身 Segment 文件**构建的（内表）。**读 Iceberg 外表时，数据不在 StarRocks 的 Segment 里，无法在其上建原生 ANN 索引。**

所以：

- **A（直查 Iceberg 外表）** → 只能用向量函数做**分布式暴力内积计算**（MPP 并行扫，比单机快，但仍是 O(N·D)）
- **A2（导入 StarRocks 内表）** → 才能用上 HNSW/IVFPQ 索引

**这是选型时最容易踩的坑**：以为"StarRocks 支持向量索引，那我直查 Iceberg 也能用上索引"——**不能**。要索引就得把数据落进 StarRocks 自己的存储。

## 1.5 三大对比维度（本书主线）

用户关心的核心是三个字：**效果、成本、延时**。全书按这三轴展开，另外补充两个工程上绕不开的维度（一致性、扩展性）：

| 维度 | 章 | 核心问题 |
|---|---|---|
| **延时** | 第 3 章 | 各数据量下 A 和 B 分别多快？QPS 多少？ |
| **成本** | 第 4 章 | 存储、计算、运维、人力分别差多少？ |
| **效果** | 第 5 章 | 召回率/准确率差多少？过滤与混合查询谁强？ |
| **一致性与运维** | 第 6 章 | 数据同步、版本漂移、回溯、监控 |
| **扩展性** | 第 7 章 | 数据量涨、QPS 涨之后谁先撑不住？ |
| **决策** | 第 8 章 | 决策树 + 混合架构 + 上线 Checklist |

## 1.6 先给结论（详细论证在后面各章）

| 场景 | 推荐 |
|---|---|
| 数据量 **< 百万级**，离线/低频检索，需要 join 分析 | **A 直查**够用，零额外成本 |
| 数据量 **千万~亿级**，要求**在线低延时**（< 100ms） | **B（Milvus）**或 **A2（SR 内表索引）** |
| 高 QPS（成百上千并发） | **B（Milvus）**，A 直查扛不住 |
| 想**不复制数据**又要 ANN 性能 | **B2 原地索引**（优先评估） |
| 需要**复杂 SQL 分析 + 向量 + 全文混合** | **A2（StarRocks 内表）**最强 |
| 已有 Milvus/向量库栈 + 纯检索 | **B**，别重复建设 |

**一句话总结**：

> **A 的本质是"用计算换存储"（不复制，每次全算）；B 的本质是"用存储换速度"（复制一份，建索引快速查）。数据量小、频率低 → A 划算；数据量大、要在线快 → B 划算。**

## 1.7 本章小结

- 场景：Iceberg 有 embedding 列，要内积 Top-K 检索。
- 四条路线：**A 直查（暴力）** / **A2 SR 内表 ANN** / **B 导入 Milvus** / **B2 原地索引**。
- 两条分水岭：**暴力 vs 索引**（延时）、**复制 vs 不复制**（成本与一致性）。
- **关键坑**：StarRocks 的 ANN 索引只对**内表**生效；直查 Iceberg 外表是**暴力计算**，没有索引加速。
- 结论预览：小数据量低频 → A；大数据量在线高 QPS → B；既要不复制又要快 → B2。
