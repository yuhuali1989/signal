## 3.1 用户角色与真实诉求

平台设计要从「谁痛」出发，而不是从「marimo 能做什么」出发：

| 角色 | 核心诉求 | 现在的痛 | 平台要给的 |
|---|---|---|---|
| **数据科学家 / 算法工程师** | 探索、建模、可复现 | Jupyter 状态混乱、结果不可复现、协作靠截图 | 响应式 + `.py` + Git + 依赖自描述 |
| **数据分析师** | 查数、出报表、给业务方看 | SQL 与 Python 割裂、交付要另做前端 | SQL cell + **app 形态一键交付** |
| **业务方 / 管理者** | 看结论、自己调参数 | 只能看静态截图，改个条件要再找分析师 | **只读 app**（改控件即出结果） |
| **数据/平台工程** | 稳定、可控、可审计、成本可控 | 环境不一致、无法知道谁在跑什么、资源浪费 | 会话调度 + 审计 + 配额 + 成本计量 |
| **AI/ Agent 场景** | 让 agent 能真跑代码 | agent 生成的代码没人验证 | ★agent 连 kernel，结果可执行可验证 |

> **最重要的一个角色洞察**：**业务方要的不是 notebook，是 app。** 平台最大的产品价值，是把分析师的 notebook 一键变成业务方能自助使用的交互工具——而这恰好是 `marimo run` 免费给的能力。

## 3.2 五大能力模块

```
┌──────────────────────────────────────────────────────────┐
│                     内部 marimo 平台                       │
├──────────┬──────────┬──────────┬──────────┬─────────────┤
│ ① 开发    │ ② 运行    │ ③ 交付    │ ④ 协作复用│ ⑤ 治理       │
├──────────┼──────────┼──────────┼──────────┼─────────────┤
│ 编辑器    │ 会话调度  │ App 托管  │ 工作空间  │ SSO / 权限   │
│ SQL 接入  │ GPU/CPU池 │ 只读分享  │ 版本(Git) │ 审计日志     │
│ 依赖自描述│ 定时调度  │ 嵌入组件  │ 模板库    │ 配额/限额    │
│ AI 辅助   │ 参数化跑  │ 报告导出  │ 内部库    │ 成本计量     │
│ 插件/主题 │ 长任务    │ 静态 WASM │ 复用 import│ 数据合规     │
└──────────┴──────────┴──────────┴──────────┴─────────────┘
```

| 模块 | 关键设计 | 优先级 |
|---|---|---|
| **① 开发** | 编辑器直接用 marimo；关键是**把 SQL 数据源、内部库、AI 端点预置好** | P0 |
| **② 运行** | 会话容器生命周期、资源规格、定时调度、参数化、长任务 | P0 |
| **③ 交付** | ★App 托管与只读分享、嵌入内网门户、报告导出 | **P0（价值最高）** |
| **④ 协作复用** | 工作空间、Git 版本、模板库、notebook 互相 import | P1 |
| **⑤ 治理** | SSO、权限、审计、配额、成本、合规 | P1（但**架构要从第一天预留**） |

> ⚠️ **治理模块可以后做，但不能后设计**。权限模型、租户隔离、审计埋点如果在架构期不预留，后面补的代价是重写——这是所有内部平台的通用教训。

## 3.3 ★ 产品形态矩阵（五种交付物）

同一个 notebook，可以按形态产出五种东西。这是产品架构里最值得讲清楚的一张表：

| 形态 | 面向 | 怎么来的 | 业务价值 | 平台侧要求 |
|---|---|---|---|---|
| **① 探索 notebook** | 作者自己 | `marimo edit` | 分析本身 | 会话调度、持久化 |
| **② 生产 App** | 业务方 | `marimo run` | ★**零前端成本交付工具** | 托管、路由、只读权限、稳定性 |
| **③ 定时任务** | 流水线 | `python nb.py --param` | 定时出数、训练、ETL | 调度器、参数注入、失败告警、产物归档 |
| **④ 嵌入组件** | 内网门户/文档 | WASM 导出 | 富交互的文档/门户 | 静态托管、跨域 |
| **⑤ 报告** | 管理层 | 导出 slides / HTML | 结论呈现 | 模板、定时刷新 |

**产品策略建议**：

- **第一版把 ①②做扎实**——这两个覆盖 80% 需求，且 ② 是最能体现价值的差异化点
- **③ 在确有定时需求时再做**（别为「可能有人要」提前做）
- ④⑤ 属于「锦上添花」，且 marimo 原生支持较好，成本低

## 3.4 工作空间与权限模型

```
组织（Org）
  └─ 工作空间（Workspace）  ← 按部门/项目划分，是隔离与计费单元
       ├─ 成员与角色：Owner / Editor / Viewer
       ├─ Notebook（.py，带 PEP 723 依赖声明）
       ├─ App（由 notebook 发布而来，独立访问控制）
       ├─ 数据源连接（凭证由平台代管，按空间授权）
       └─ 配额：并发会话数、GPU 时长、存储
```

| 角色 | 权限 |
|---|---|
| **Owner** | 管理成员、发布 app、配数据源、看成本 |
| **Editor** | 创建/编辑 notebook、跑会话、调试 |
| **Viewer** | 查看 notebook、使用已发布的 app（**看不到源码或只读**） |

**三条设计原则**：

1. **App 的访问权限独立于源 notebook**——业务方看 app 不等于能看源码
2. **数据源凭证永不进 notebook**——由平台按空间注入，避免密码写进 `.py` 再进 Git（**这是安全事故头号来源**）
3. **配额按工作空间设**，避免个别 notebook 吃满资源

## 3.5 资产与复用机制

marimo 的 `.py` 天然支持复用，平台要把这个优势放大：

| 机制 | 做法 | 价值 |
|---|---|---|
| **notebook 互相 import** | 一个 notebook 的函数/类可被另一个 import | ★把常用逻辑变成可复用模块 |
| **模板库** | 预置「连数仓取数」「建模」「可视化」等模板 | 降低上手成本、统一规范 |
| **内部公共库** | 把公司通用逻辑做成 pip 包，预装进镜像 | 避免每个 notebook 重复实现 |
| **代码片段/AI 提示** | 把常用 SQL、图表起手式沉淀下来 | 提效 + 保证一致性 |
| **示例 Gallery** | 内部优秀 notebook 展示 | 传播最佳实践 |

> ★**「把 notebook 当模块 import」是 marimo 相对 Jupyter 的结构性优势**——它让 notebook 从「一次性脚本」升级为「可组合的软件资产」。平台应当主动推广这个用法，而不是让每个 notebook 成为孤岛。

## 3.6 MVP 范围界定（第一版做什么）

**核心判据：让第一批用户真能用起来、且能看见价值。**

### ✅ MVP 必做

| 项 | 说明 |
|---|---|
| SSO 登录 | 接公司身份源 |
| 会话服务 | 点开 notebook 自动起容器、闲置自动回收 |
| 持久化 | notebook 文件存 Git（或对象存储 + 版本） |
| 数据源接入 | 至少接 1–2 个内部数仓/查询引擎，**凭证平台代管** |
| 依赖管理 | PEP 723 + uv sandbox |
| **App 发布** | ★一键把 notebook 发成只读 app，带访问控制 |
| 基础规格 | CPU 会话为主；GPU 视需求（若没有训练场景可后置） |

### ⏳ 二期

| 项 | 说明 |
|---|---|
| 定时调度 + 参数化 + 失败告警 | 有明确需求再做 |
| 模板库 / Gallery | 用户量起来后沉淀 |
| 成本计量与配额 | 需要先有使用数据 |
| AI 接入内部模型 | 见第 6 章 |
| 长任务 / 异步执行 | 跑批需求出现后 |

### ❌ 明确不做（至少一期内）

- 多租户对外商业化（内部平台不需要）
- 自研编辑器或改响应式语义（**动核心必后悔**）
- 实时多人协同编辑（RTC）——**需求常被高估**，先靠「一个人编辑 + Git 版本 + 评论」解决
- 支持 Jupyter `.ipynb` 双向同步——可单向导入即可，**双向同步是深坑**

## 3.7 本章要点

- 从角色痛点出发：**业务方要的是 app 不是 notebook**；★app 交付是价值最高的差异化点。
- 五大能力模块：**开发 / 运行 / 交付 / 协作复用 / 治理**；治理可后做但**架构必须预留**。
- ★五种产品形态：探索 notebook / 生产 app / 定时任务 / 嵌入组件 / 报告；**第一版做扎实前两个**。
- 权限三原则：**app 权限独立于源码**、**凭证永不进 notebook**、**配额按工作空间**。
- ★放大 marimo 的结构性优势：**notebook 当模块 import**，让它成为可组合资产而非孤岛。
- MVP 边界要写死：不做多租户商业化、不改响应式语义、**不做 RTC 协同、不做 ipynb 双向同步**。
