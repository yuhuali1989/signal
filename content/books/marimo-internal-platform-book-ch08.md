# 第 24 章 · 产出与价值：怎么量化、多久回本、做不做的判据

## 8.1 价值的四个层次（按可信度排序）

| 层次 | 价值 | 可量化性 | 量级 |
|---|---|---|---|
| **① 交付效率** | ★App 模式替代「前端+后端」做看板/工具 | ★**最可量化** | **最大** |
| **② 质量与可复现** | 消除 hidden state，减少返工与数字对不齐 | 中（需基线） | 大 |
| **③ 合规与数据安全** | 数据不出内网、SSO、审计 | 不可量化 | ★**硬约束（决定做不做）** |
| **④ 许可费替代** | 替代 SaaS 订阅 | 易算 | ★**往往不是最大头** |

> ★**关键认知**：很多人把 ④ 当成自建主理由，这是**本末倒置**。真正的钱在 ①；真正的理由在 ③。

## 8.2 ★ 价值①：App 交付替代前端开发（最大的一块）

### 传统做法 vs marimo app

| | 传统（分析师出图 → 前端做页面 → 后端接口） | marimo app |
|---|---|---|
| 参与角色 | 分析师 + 前端 + 后端（2–3 人） | **分析师 1 人** |
| 周期 | **2–3 人周** | **0.5–1 天（≈0.2 人周）** |
| 改需求 | 再走一轮开发 | 改 notebook 重新发布 |
| 代码隐藏 | 需单独做 | ★`marimo run` 天生只读 |

### 量化模型

```
年节省人周 = 年交付 App 数 × (2~3 人周 − 0.2 人周)
           ≈ 年交付数 × 2~2.8 人周
```

| 年交付 App 数 | 节省人周 | 折合金额（按 3 万/人月 ≈ 0.75 万/人周） |
|---|---|---|
| 10 个 | 20–28 | **15–21 万元** |
| 20 个 | 40–56 | **30–42 万元** |
| 40 个 | 80–112 | **60–84 万元** |

> ★**这张表是整个项目最有说服力的数字**：只要团队一年要给业务方交付 **20 个以上**交互式看板/工具，仅此一项的年化收益（30–42 万）就**覆盖甚至超过自建的年成本**（第 7 章：第二年起 20–40 万/年）。

**前提**（必须同时成立，否则这个数字不成立）：

1. 确实存在「分析师反复给业务方做交互式看板」的场景
2. 业务方能接受「控件+图表」形态（而非必须定制 UI）
3. 组织愿意让分析师直接发布 app（流程上放开）

## 8.3 价值②：可复现减少返工

Jupyter 的 hidden state 问题业界有实证（**约 96% 公开 Jupyter notebook 不可复现**）。对企业内部而言，代价是：

- 数字对不齐要重跑、重查
- 交接时要重新理解别人的执行顺序
- 「上周那个数怎么来的」无法回答

### 量化模型（保守估计，需用基线校准）

```
年节省 = 活跃分析人数 × 每周节省小时 × 工作周数
示例：30 人 × 2 小时/周 × 48 周 = 2880 小时 ≈ 1.7 人年
折合（按 30 万/人年全成本）≈ 50 万元/年
```

> ⚠️ 这是**保守但需实证**的数字。建议立项前做一个小调查：「你每周花多少时间在重跑/对数字/解释数字来源上」，用真实基线替换这里的 2 小时假设。

**附带收益**（难量化但不小）：`.py` 进 Git 后，分析产物变成**可评审、可复用、可继承的软件资产**——长期看比省时间更重要。

## 8.4 价值③/④：合规与许可费

| | 说明 |
|---|---|
| **③ 合规** | 数据不出内网、企业 SSO、全链路审计。**不产生收益，但是 Go/No-Go 的硬门槛**——若公司规定敏感数据不得出网，这一条单独就能决定自建 |
| **④ 许可费** | 50 人规模约 **12–28 万元/年**（SaaS 订阅）。注意：自建持续运维 18–36 万/年，**该项未必净节省**（第 7.4 节已诚实说明） |

## 8.5 ROI 与回本周期（三种典型情形）

| 情形 | 特征 | 年化收益（示意） | 回本周期 | 建议 |
|---|---|---|---|---|
| **A. 高频交付型** | 年交付 App ≥ 20 个，50+ 活跃用户 | 30–42 万（①）+ 返工节省 | **< 1 年** | ★**强烈推荐** |
| **B. 合规驱动型** | 数据必须内网，App 交付不多 | 主要靠 ②③ | 2–3 年 | **做，但范围收窄到 MVP** |
| **C. 纯替代自用型** | 只是想换个更好的 notebook | 主要靠 ② | ★**3 年以上或算不过来** | **不建议自建**，用 molab 或直接 SaaS |

> ★**最反直觉也最重要的结论**：**自建划不划算，几乎完全取决于「有没有高频给业务方交付交互式工具」这个场景**。有 → ROI 极好；没有 → 大概率算不过来，别自研。

## 8.6 度量指标（怎么证明做成了）

立项时就要定好「成功的定义」，否则半年后无法评估：

| 类别 | 指标 | 目标示例 |
|---|---|---|
| **采用** | 月活用户 / 目标人群覆盖率 | 6 个月内覆盖 ≥ 60% 目标人群 |
| **★交付价值** | 发布的 App 数、App 月访问量、**业务方自助使用次数** | 首年 ≥ 20 个 App |
| **质量** | 定时任务成功率、同参数重跑一致性 | ≥ 99% |
| **体验** | 会话冷启动 P95、会话失败率 | 冷启动 < 10s |
| **成本** | 人均月成本、GPU 利用率、闲置率 | 闲置率 < 20% |
| **满意度** | 用户 NPS / 季度调研 | 正向 |

> ★**「业务方自助使用次数」是最能体现价值的单一指标**——它直接证明「分析师不用再为改一个筛选条件而重做一遍」。

## 8.7 Go / No-Go 判据

### ✅ 应该做（需同时满足多数）

- 敏感数据**不能出内网**，或必须接企业 SSO / 审计
- 有 **≥ 20 人**的活跃分析/算法人群
- ★存在**高频给业务方交付看板/工具**的场景（年 ≥ 10–20 个）
- 能投入 **2–3 人 × 3–5 个月**，且**有明确的常驻运维归属**
- 已有容器/K8s 与对象存储基建（可显著降成本）

### ❌ 不应该做

- 数据可以放外部、用户 < 10 人
- 只是想「换个更好用的 notebook」（→ 用 molab 或本地 marimo 即可）
- 没有人能长期维护（**这是烂尾的头号原因**）
- 半年内必须见效且无基建（→ 直接买 SaaS）

## 8.8 止损线

| 时点 | 检查 | 不达标怎么办 |
|---|---|---|
| **PoC 后（第 4 周）** | 种子用户是否接受响应式范式 | 不接受 → **停**，不要进 MVP |
| **MVP 上线 +3 月** | 采用率、活跃 notebook 数 | < 20% → 复盘推广与体验 |
| **MVP 上线 +6 月** | ★采用率 < 30% 或 App 数 < 5 | ★**严肃评估是否继续**，必要时止损 |

## 8.9 一页决策摘要

```
要不要自建内部 marimo 平台？

第一问：数据能不能出内网？
  不能 → 进入第二问（合规是硬门槛）
  能   → 进入第二问，但权重降低

第二问：一年要给业务方交付多少个交互式看板/工具？
  ≥ 20 个 → ★做。仅交付替代一项（30–42 万/年）就覆盖成本，回本 < 1 年
  10–20 个 → 可做，但范围收窄到 MVP，先 PoC 验证
  < 10 个 → 不建议自建；用 molab 或买 SaaS，或只在本地推广 marimo

第三问：有没有 2–3 人投 3–5 个月 + 长期运维归属？
  没有 → 不要启动（烂尾风险极高）

都通过 → 先做 2–4 周 PoC，验证「用户接受响应式范式」后再进 MVP
```

## 8.10 本章要点

- 价值四层：**①交付效率（最大、最可量化）> ②可复现质量 > ③合规（硬门槛）> ④许可费替代（常被误当主理由）**。
- ★**App 交付替代是核心账**：单个交互式看板从 2–3 人周降到 0.2 人周；**年交付 ≥ 20 个即可覆盖自建年成本**。
- 可复现收益需**用真实基线校准**（建议立项前做个小调查），不要直接用行业数字套。
- ROI 三情形：**高频交付型 < 1 年回本（强烈推荐）／合规驱动型 2–3 年（收窄到 MVP）／纯替代自用型算不过来（别自建）**。
- ★度量首推「**业务方自助使用次数**」——最能证明价值；立项就要定成功标准。
- Go/No-Go 三问：**数据能否出网 / 年交付 App 数 / 人与运维是否到位**；★**PoC 后不接受响应式范式就停**。
