## 2.1 五层架构总览

一个 AI Native Notebook 平台可以拆成五层。很多团队选型时只盯着最上面的交互层，忽视了下面几层——而**真正的差异几乎都在执行层和 AI 层**。

```text
┌─ ① 交互层 ────────────────────────────────┐
│ 单元格编辑器 / 输出渲染 / UI 组件 / 变量浏览器 │
└──────────────┬────────────────────────────┘
┌─ ② AI 层 ────┴────────────────────────────┐
│ 提示编排 / 上下文组装 / Agent / 工具调用     │
└──────────────┬────────────────────────────┘
┌─ ③ 执行层 ───┴────────────────────────────┐
│ 内核（有状态 / 响应式 DAG）/ 沙箱 / 调度     │
└──────────────┬────────────────────────────┘
┌─ ④ 状态与数据层 ─┴────────────────────────┐
│ 变量状态 / 缓存 / 文件格式 / 数据连接        │
└──────────────┬────────────────────────────┘
┌─ ⑤ 平台服务层 ───┴────────────────────────┐
│ 协作 / 权限 / 版本 / 发布 / 调度 / 成本       │
└───────────────────────────────────────────┘
```

## 2.2 各层职责与典型技术

| 层 | 职责 | 典型技术 / 组件 |
|---|---|---|
| **① 交互层** | 编辑、渲染、交互控件 | JupyterLab 前端、VSCode Notebook UI、响应式 UI（marimo）、变量浏览器、图表渲染 |
| **② AI 层** | 上下文组装、模型调用、Agent 编排、工具协议 | LLM API、MCP（工具/资源协议）、ACP（Agent 通信协议）、Agent runtime |
| **③ 执行层** | 真正跑代码 | IPython kernel（有状态）、响应式 DAG 引擎、远程执行网关、容器沙箱 |
| **④ 状态与数据层** | 状态管理与持久化 | .ipynb / .py / 专有格式、变量检查点、缓存、数仓连接器 |
| **⑤ 平台服务层** | 让团队能用起来 | 实时协作（RTC）、权限、Git、调度、发布 app、成本计量 |

## 2.3 关键分叉：AI 层的两种集成范式

这是 2026 年最重要的一次架构分野，也是选型时最该问清楚的问题。

### 范式 A：外挂式——AI 通过工具协议访问 Notebook

**代表**：Jupyter AI v3 的方向。

```text
Agent（外部）──[ACP / MCP 协议]──→ JupyterLab 平台
                                    ├─ 读 notebook / 文件
                                    ├─ 编辑、执行 cell
                                    └─ 权限控制、协作 persona
```

**特点**：

- AI 通过 **MCP（Model Context Protocol，工具/资源）** 与 **ACP（Agent 通信协议）** 接入
- 支持自定义 local 或 HTTP MCP server，团队可扩展 agent 能触及的范围
- AI 是"拥有工具访问权限的外部协作者"，操作既有 notebook 平台
- **优势**：兼容已有 Jupyter 资产与工作流，可接入多种外部 agent（广度优先）

### 范式 B：内生式——AI 直接以内核为工作区

**代表**：marimo pair。

```text
Agent ──[CLI 直接执行 Python]──→ 运行中的 marimo kernel
                                  ├─ 读取内存中变量（scratchpad）
                                  └─ 持久变更走内部 code-mode API（带校验）
                                       → 进入依赖 DAG → 写入 .py
```

**特点**：

- Agent **直接在运行中的 kernel 里执行 Python**，能检查内存中的数据
- Notebook 变量对 agent 的 scratchpad 可见
- 持久修改走内部 API，**提交前做校验**：语法错误、同名重复定义、依赖循环、删除被下游消费的变量——**无效批次整体拒绝，不会部分应用**
- 接受的 cell 进入 notebook 的依赖图与 .py 产物，继承确定性数据流执行
- **优势**：agent 的编辑继承了响应式执行的可复现保证（深度优先）

### 两种范式对比

| 维度 | 范式 A：外挂式（工具访问） | 范式 B：内生式（内核工作区） |
|---|---|---|
| AI 的位置 | 平台外的协作者 | 运行时内部的执行者 |
| 协议 | MCP / ACP | 直接 kernel 执行 + 内部 API |
| 能否读内存变量 | 通过工具间接读 | **直接读** |
| 编辑校验 | 依赖平台工具实现 | **依赖图校验（语法/循环/重定义）** |
| 执行保证 | 继承原 notebook 的语义（含 hidden state 风险） | **继承响应式 DAG 的确定性** |
| 优势 | 兼容既有资产、可接多种 agent | 修改本身可复现、避免半个坏状态 |
| 适合 | 已有大量 .ipynb 与 JupyterHub 的组织 | 新建、以可复现为第一要求的场景 |

> **核心问题（值得反复问）**：当 agent 开始写相当比例的分析代码时，「**agent 继承了什么样的执行保证？**」至少和「我能接哪个模型？」一样重要。

## 2.4 一次 AI 请求的完整路径（控制流）

以"用自然语言让 AI 画一张图"为例，看数据怎么走：

```text
① 用户在 cell 输入自然语言 / 触发 AI
② AI 层组装上下文：
   - 当前 notebook 的结构与已有代码
   - 运行时变量（范式 B 可直接读 kernel 内存；范式 A 通过工具读）
   - 数据 schema / 样本行
   - 用户权限与可用工具清单
③ 调用模型（可能经内部路由 / 网关 / 成本计量）
④ 模型输出：代码 / 工具调用 / 解释
⑤ 执行：
   - 范式 A：通过 notebook 执行接口跑
   - 范式 B：在 kernel 内执行 + 校验后写入依赖图
⑥ 输出渲染回交互层（图 / 表 / 文本）
⑦ 记录：本次 AI 调用的模型、token、成本（进平台服务层计量）
```

**关键设计点**：第 ② 步的**上下文组装**决定了 AI 好不好用；第 ⑤ 步的**执行与校验**决定了 AI 会不会把 notebook 搞坏。这两处是架构投资回报最高的地方。

## 2.5 部署形态

| 形态 | 说明 | 代表 |
|---|---|---|
| **本地** | 完全本地，无网络依赖 | JupyterLab Desktop（Electron）、marimo 本地、VSCode |
| **自托管** | 自己部署服务端，团队共用 | JupyterHub、自建 Deepnote/企业版（若提供） |
| **云端 SaaS** | 厂商托管，开箱即用 | Colab、Hex、Deepnote、Databricks |
| **混合** | 本地编辑 + 远程执行 | VSCode + 远程内核、Jupyter + 远程 kernel gateway |

**AI 能力对部署形态的影响**：本地形态也能用 AI（只要能调模型 API，或通过 MCP 接本地 agent）；但**涉及数据驻留/合规时，云端 SaaS 的 AI 调用路由（数据是否出境）会成为关键约束**——见 8.5 的 Checklist。

## 2.6 架构决策的三个权衡

| 权衡 | 说明 |
|---|---|
| **兼容 vs 干净** | 兼容 .ipynb 生态（范式 A/Jupyter）vs 改用响应式 .py（范式 B/marimo）——前者省迁移成本，后者消除 hidden state |
| **AI 广度 vs AI 深度** | 接多个外部 agent（Jupyter AI 的广度）vs 让 agent 深度进入运行时（marimo pair 的深度） |
| **自由 vs 托管** | 完全控制环境（Jupyter 自由但环境漂移自己扛）vs 托管环境（Deepnote/Hex 免运维但锁定与成本） |

## 2.7 本章小结

- AI Native Notebook 分**五层**：交互 / AI / 执行 / 状态与数据 / 平台服务；差异主要在执行层与 AI 层。
- **AI 层两种范式**：外挂式（MCP/ACP 工具访问，兼容优先）vs 内生式（kernel 内执行，可复现优先）。
- **marimo pair 的关键设计**：agent 在 kernel 内执行，持久变更**提交前校验**语法/重定义/依赖循环/删除被依赖变量，**无效批次整体拒绝**——避免半个坏状态。
- **核心问题**：agent 继承了什么执行保证，与"能接哪个模型"同等重要。
- AI 请求路径里，**上下文组装**决定好不好用，**执行与校验**决定会不会搞坏。
- 部署形态（本地/自托管/云/混合）会影响 AI 的数据驻留与合规约束。
