# 第 4 章 · 路线之争：Agent 替代 ERP，还是 AI 原生 ERP

## 4.1 两条路线的正面定义

2026 年行业里最响的一个叙事是 **"Agent 替代 ERP"**：既然 Agent 能理解任务意图、调用多个系统、端到端完成流程，那企业为什么还要养一套庞大的 ERP？

金蝶的选择被 IDC 报告明确记录了下来：

> 在 AI Agent 技术路线的选择上，金蝶**并未追随"Agent 替代 ERP"的行业叙事**，而是把 Agent 与自有 ERP 能力融合、**强调 AI 原生 ERP**，用 AI 进一步巩固自身在企业核心业务系统中的优势地位。

把两条路线摆清楚：

| | **路线 A：Agent 替代 ERP** | **路线 B：AI 原生 ERP** |
|---|---|---|
| 核心假设 | Agent 是新的系统层，ERP 退化为数据库 | ERP 是系统层，Agent 长在它上面 |
| 数据来源 | Agent 通过 UI/API 抓取各系统数据 | Agent 直接读取统一主数据与业务规则 |
| 执行方式 | 模拟人操作界面（点击、填表） | 调用原生交易与流程引擎 |
| 权限与合规 | 需要重建，且往往绕过既有治理 | **直接继承**既有组织、权限、审批、审计 |
| 代表声音 | 部分 AI 原生创业公司、市场悲观叙事 | **金蝶、SAP、Oracle、Workday** |

**值得注意的是**：四家上市巨头**不约而同**选了路线 B。这不是巧合，而是因为它们最清楚企业系统里什么东西无法绕过。

## 4.2 为什么系统级工程绕不过去

一位软件从业者在 2026 年 2 月说的一段话，值得逐字引用：

> 企业软件最难复制的部分不是页面和代码，而是**与其他系统长期形成的连接、权限管理、监管合规、历史数据，和已经固化进组织中的业务流程**，以及背后的**完整性保障**——这是复杂的系统级工程。

拆开看，Agent 要真正"干企业的活"，必须解决六件事，而**没有一件能靠大模型能力直接获得**：

| # | 必须解决的问题 | 为什么 LLM 不自带 |
|---|---|---|
| 1 | **主数据一致性** | 同一个供应商在五个系统里有五个编码，模型不知道哪个是权威 |
| 2 | **权限边界** | 谁能审这笔付款，取决于组织层级、金额阈值、回避规则——这些不在模型里 |
| 3 | **审批与审计链** | 谁在什么时候改了什么，需要可追溯的责任链，不是生成式输出 |
| 4 | **事务完整性** | 财务凭证要借贷平衡、要对得上单据，错了要能冲销回滚 |
| 5 | **合规约束** | 税务、外汇、行业监管规则随地区和时间变化 |
| 6 | **历史数据语义** | 三年前的一笔异常怎么处理过，只有系统里有记录 |

**结论**：Agent 可以替代"人点界面"的动作，但替代不了**这套约束体系**。而这套体系恰恰是 ERP 三十年积累下来的。

## 4.3 上下文才是真壁垒：SAP 与金蝶的同一句话

两家公司的表述惊人地一致。

**SAP CEO 柯睿安**：
> 客户越来越倾向于找 SAP 获取真正的业务价值，因为 **AI 智能体必须嵌入业务流程、并以大模型厂商不具备的、富含上下文的企业业务数据来训练**。

**金蝶的架构说明**：
> 智能体与金蝶 AI 套件、金蝶 AI 苍穹、金蝶 AI 星瀚等**共用一套组织、主数据、业务规则和权限，可直接调用原生交易与流程**。这种架构设计既降低了对接成本、减少了数据外发风险，也构成了金蝶灵基的差异化竞争壁垒。

把这两段话抽象成一句可迁移的判断：

> **Agent 的能力上限，不取决于模型多强，而取决于它能触达多少带上下文的业务数据，以及在什么治理约束下执行。**

## 4.4 架构图：两种路线的实际差异

```
【路线 A：Agent 替代 ERP】
   Agent ──► 抓取 UI/API ──► ERP / CRM / MES / OA
     │                          │
     └─ 问题：权限要重建、审计要重建、
        事务完整性靠 Agent 自己保证、
        数据要外发给模型

【路线 B：AI 原生 ERP】
   ┌─────────────────────────────────┐
   │  Agent 层（灵基 / Joule / 22 个 Fusion Apps） │
   ├─────────────────────────────────┤
   │  共用：组织 · 主数据 · 业务规则 · 权限 · 审批 · 审计 │
   ├─────────────────────────────────┤
   │  原生交易与流程引擎（ERP 内核）            │
   └─────────────────────────────────┘
     └─ 优势：零对接成本、数据不外发、
        直接继承治理能力
```

Oracle 的产品说明里有一句话精准概括了路线 B 的卖点：Agent 应用**继承 Fusion Applications 已有的安全、访问权限、审批、审计追踪与治理能力**。

## 4.5 但路线 B 也有三个真实代价

选择"让 Agent 长在自己身上"，意味着要同时承受三件事。

**代价一：必须先把存量客户搬上云。**
SAP 的结构性阻力是**60% 的存量客户尚未迁移上云**，而云迁移是 Agent 路线的前提。中国厂商的存量包袱只会更重。这是路线 B 最大的时间成本——**你无法跳过这一步直接用 AI 覆盖**。

**代价二：Agent 的产品形态会被既有系统约束。**
通用 Agent 可以自由设计交互；长在 ERP 里的 Agent 必须服从既有的数据模型与流程定义。好处是治理完善，代价是**灵活性和体验上限受限**。这也解释了为什么"AI 原生创业公司"在体验上常常更讨喜。

**代价三：要同时维护两套技术栈。**
金蝶要同时推进灵基（Agent 操作系统）、苍穹（PaaS）、星瀚（SaaS）三条线，每套都要投入。组织复杂度和研发成本显著高于单点突破的公司。

## 4.6 一个折中判断：不是二选一，而是看 Agent 落在哪个环节

实务上，企业内的 Agent 可以按**风险等级**分层，不同层适合不同路线：

| Agent 类型 | 例子 | 适合路线 | 原因 |
|---|---|---|---|
| **信息型** | 财报扫描、竞对分析、政策查询 | **A（可外挂）** | 只读，风险低，不需要事务完整性 |
| **辅助型** | 填单建议、异常提示、文案生成 | **A/B 皆可** | 结果由人确认 |
| **交易型** | 生成凭证、过账、付款发起 | **B（必须长在系统内）** | 涉及事务完整性与审计链 |
| **决策型** | 预算分配、信用审批、补货决策 | **B + 人工确认** | 责任无法转移给模型 |

这个分层给传统厂商一个务实结论：

> **不必在所有环节防守。** 信息型、辅助型环节被通用 Agent 拿走是可以接受的损失；**真正的防线是交易型与决策型环节**——那里有事务完整性、审计链和责任边界，是系统级工程的地盘。

这也解释了为什么金蝶把"AI 财务部"（15 个智能体、覆盖费用审核/对账/核算/报表/税务/预算）作为旗舰场景：这些**全是交易型与决策型环节**，正是长在系统内最有优势的地方。

## 4.7 给传统软件厂商的路线自检五问

如果你是一家传统软件公司的决策者，用这五问判断自己该走哪条路：

1. **你的核心系统里，有多少"只有你知道"的业务规则？**（多 → 路线 B 有牌；少 → 危险）
2. **你的存量客户迁移到云/新架构的比例是多少？**（低于 50% → 先解决迁移，别谈 Agent 全覆盖）
3. **你的 Agent 能否直接调用原生交易，还是要模拟 UI 操作？**（后者 → 治理与稳定性都有隐患）
4. **你的权限、审批、审计链能否被 Agent 继承？**（能 → 这是你相对通用 Agent 的核心优势）
5. **如果被通用 Agent 绕过，客户会失去什么？**（答不出来 → 你的价值在界面层，危险）

## 4.8 本章小结

- **两条路线不是理念之争，是对"系统级工程能否被绕过"的判断差异。** 四家巨头用产品选择投了票：绕不过。
- **真壁垒是上下文与治理继承**，不是模型能力。SAP 和金蝶用几乎相同的措辞说了同一件事。
- **路线 B 的代价是云迁移包袱、体验上限与双栈维护成本**——SAP 60% 未上云就是最直观的例子。
- **实务上按风险分层防守**：信息型可以放手，交易型与决策型必须守在系统内。
