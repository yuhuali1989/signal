## 4.1 AI 能力的五个层次

同样是"有 AI"，深浅差别巨大。按能力从浅到深：

| 层 | 能力 | 价值 | 普及度 |
|---|---|---|---|
| L1 | **代码补全** | 打字更快 | 几乎都有（含通用编辑器插件） |
| L2 | **代码生成**（自然语言 → 代码） | 写常见片段 | 主流平台都有 |
| L3 | **解释与修错**（解释代码、自动修 traceback） | 降低调试成本 | 较主流 |
| L4 | **上下文感知**（知道 notebook 已有代码/数据/schema） | 建议真正贴合你的数据 | 分水岭 |
| L5 | **Agent 自主执行**（自己跑、自己看结果、迭代） | 真正提效 | 少数（marimo pair、Deepnote Agent、Jupyter AI v3） |

**判断一个平台 AI 能力强弱，主要看它在 L4 和 L5 做到了什么程度**——L1–L3 通过接个模型 API 都能做到，差异不大。

## 4.2 上下文工程：AI 好不好用，八成看这里

同一个模型，在不同平台表现差异巨大，主要原因是**喂给模型的上下文不同**。

一个 AI Native Notebook 应该能组装这些上下文：

| 上下文 | 说明 | 为什么重要 |
|---|---|---|
| **Notebook 结构** | 已有 cell、执行顺序、依赖关系 | 生成的代码要能接得上前后文 |
| **运行时变量** | 内存里的 DataFrame 名、类型、形状 | "帮我画个图"必须知道画哪个 df |
| **数据 schema** | 列名、类型、取值范围 | 生成的 SQL/列名才不会错 |
| **样本数据** | 前几行真实数据 | 让模型理解数据长什么样 |
| **错误信息** | traceback、日志 | 修错类能力的基础 |
| **可用工具/权限** | 能调哪些库、能访问哪些数据源 | 避免生成用不了的代码 |
| **用户意图历史** | 前几轮对话 / 之前的操作 | 多轮协作连贯 |

**关键技术点**：

- **变量/schema 的可读化**：不能直接把整个大表塞进去——要摘要（schema + 少量样本 + 统计摘要）
- **增量上下文**：只传与当前任务相关的部分，控制 token 成本
- **范式差异**：内生式（marimo pair）能让 agent **直接读 kernel 内存变量**；外挂式需通过工具接口间接读——这会影响上下文的丰富度与延迟

## 4.3 Agent 接入的两种实践路径

第 2 章讲了范式，这里看工程实践。

### 路径 A：外部 Agent 通过协议接入（Jupyter AI v3 路线）

```text
Agent（Claude / Codex / 自研）
   │
   ├── ACP：Agent 与 Agent 之间通信
   └── MCP：访问 notebook / 工具 / 文件
         ├─ 读取 notebook 内容与文件
         ├─ 编辑 cell、执行代码
         └─ 权限控制、协作 persona
```

- 支持自定义 **local 或 HTTP MCP server**，团队可扩展 agent 能触及的范围
- **优势**：一个 notebook 可对接多种外部 agent；与既有 JupyterLab 资产兼容
- **适合**：已有大量 .ipynb、JupyterHub 基础设施、自定义扩展与培训材料的组织

### 路径 B：Agent 进入运行时（marimo pair 路线）

```text
Agent
   ├─ 用 CLI 直接在运行中的 kernel 执行 Python（临时探查）
   │     → notebook 变量对 agent 的 scratchpad 可见
   └─ 持久变更走内部 Python code-mode API
         → 提交前校验：语法错误 / 同名重复定义 / 依赖循环 / 删除被下游消费的变量
         → 无效批次整体拒绝（不会留下半个坏状态）
         → 通过后进入依赖 DAG + .py 产物
```

- 早期实现是"只读 MCP 工具看 notebook + 改 .py 源码 + 靠文件监听重载"，引入了额外调用、延迟与 token 开销；后来改为**直接在 kernel 执行**
- **优势**：agent 的编辑继承了确定性数据流执行与依赖校验——**这是"AI Native"的硬核体现**
- **适合**：以可复现为第一要求、且 Agent 会写相当比例分析代码的场景

### 选择建议

| 如果你的情况是 | 选 |
|---|---|
| 已有数千个 .ipynb、既有 JupyterHub/Lab 基建与培训体系 | 路径 A（兼容优先，迁移成本真实存在） |
| 主要诉求是"agent 触达广"、要接多个 agent、要 MCP 扩展 | 路径 A |
| 消除执行顺序隐藏状态、纯文本版本控制、响应式是**第一要求** | 路径 B |
| Notebook 处在"探索研究"与"agent 驱动工作流"的边界 | **两个都试点** |

## 4.4 模型选择、路由与成本

| 议题 | 要点 |
|---|---|
| **模型可替换** | 平台是否允许切换模型/接自己的端点？还是锁定单一供应商 |
| **企业自建端点** | 部分平台（如 Deepnote Enterprise）支持连接 **OpenAI 兼容的自建端点**，可控制由哪个 provider 服务 AI 请求——对采购、合规、内部路由有意义 |
| **成本计量** | AI 调用按 token 计费，平台是否提供**用量与成本可见性**（谁用了多少） |
| **成本优化** | 上下文裁剪、缓存、小模型处理简单任务（补全用便宜模型，复杂推理用强模型） |
| **数据驻留** | 代码/数据是否会发到外部模型——合规敏感行业要能指定私有部署模型 |

**务实建议**：先问清楚三件事——**能不能换模型、能不能接自己的端点、能不能看到成本账单**。这三个问题的答案往往比"AI 功能演示有多炫"更能决定长期可用性。

## 4.5 Agent 的安全边界（AI 时代的新增风险）

传统 Notebook 的安全假设是"用户手动执行代码"。AI Native 之后变成——**AI 自动执行代码**。安全模型必须升级：

| 风险 | 对策 |
|---|---|
| Agent 执行危险操作 | **最小权限**：限制 agent 可用的工具、数据源、网络 |
| 凭据与数据泄露 | 密钥托管而非硬编码；agent 只能访问授权数据源 |
| 破坏性修改 | **提交前校验 + 可回滚**；关键操作需人工确认（human-in-the-loop） |
| 不可审计 | **记录 agent 的每一次执行与修改**（谁/哪个 agent/改了什么/结果） |
| 依赖破坏 | 校验依赖循环、删除被依赖变量（marimo pair 的做法） |

**一条重要原则**：agent 的修改必须**可审查（reviewable）**——变更要落在版本控制里能被 review，而不是消失在一个黑盒会话中。

## 4.6 怎么评估一个平台的 AI 能力

别看演示视频，用固定任务实测：

| 测试 | 做法 |
|---|---|
| **上下文感知** | 在 notebook 里加载一个自建数据集，问"画各品类销售额"——看它是否知道正确的列名与表名 |
| **错误处理** | 故意写错代码触发 traceback，看能否正确定位并修复 |
| **迭代能力** | 给一个多步任务（取数→清洗→聚合→可视化），看能否一次跑通或自主迭代 |
| **不破坏结构** | 让 agent 改一个被多处依赖的变量，看平台是否阻止/警告 |
| **可审查性** | agent 改完后，能否在 Git/历史里看到清晰的 diff |
| **成本可见** | 跑一批任务后，能否看到 token 与费用 |

**评分建议**：给上面每项按 0–5 打分，加权后比较——比主观印象可靠得多。

## 4.7 本章小结

- AI 能力分五层（补全 / 生成 / 解释修错 / 上下文感知 / Agent 自主执行）；**差异主要在 L4 与 L5**。
- **上下文工程决定 AI 好不好用**：notebook 结构、运行时变量、数据 schema、样本、错误、权限、历史。
- 两种 Agent 接入路径：**外部协议接入（兼容与广度优先）** vs **运行时内执行（可复现与深度优先）**。
- marimo pair 的**提交前校验 + 无效批次整体拒绝**是"AI 编辑继承执行保证"的范例。
- 模型治理三问：**能换模型吗？能接自建端点吗？能看到成本吗？**
- **AI 自动执行代码**让安全模型必须升级：最小权限、密钥托管、提交前校验、人工确认、可审计。
- 评估用**固定任务实测**（上下文感知、修错、多步迭代、不破坏结构、可审查、成本可见），别信演示。
