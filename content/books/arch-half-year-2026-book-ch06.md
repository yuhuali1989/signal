## 6.2 Wan2.6 拆解：一个可抄的工程清单

【站内 `models.json` factSheet】：

| 项 | 值 |
|---|---|
| 主干 | **14B DiT** + 蒸馏版 **1.3B**（24G 消费级显卡可跑 480P） |
| 文本编码 | 沿用**冻结 T5 / UmT5** 路线 |
| 并行 | ★**CFG-Parallel**：正/负条件分支拆到不同 GPU 并行 |
| VAE | ★**Parallel VAE**：高度分片 + `halo_exchange`，长视频解码显存峰值 **-41%** |
| 分数 | VBench-2.0 **90.2**（榜首），单卡吞吐 **2.2×** |

三个做法逐个说：

**① 冻结文本编码器。** 这是 Diffusion 路线从一开始就有的分工，半年里没变：Text Encoder 只提供条件向量，梯度全部流向 DiT。好处是省下 11B 级 encoder 的优化器状态与激活显存，也让「换 prompt 不改语言能力」成立。它与第 5 章 Qwen3.9-VL 的「对齐阶段冻 LLM」是同一种直觉——**先冻住已经够好的部分，只训需要适配的那一段**。

**② CFG-Parallel。** Classifier-Free Guidance 每步要算有条件与无条件两次前向。传统实现串行做，或者 batch 到一起但共享同一张卡；CFG-Parallel 把两条分支拆到不同 GPU 同时跑：

```python
# 【推断】按官方描述的结构骨架，非官方实现
def cfg_step(z, cond, uncond):
    with torch.cuda.stream(s0): eps_c = dit(z, cond)      # GPU 0
    with torch.cuda.stream(s1): eps_u = dit(z, uncond)    # GPU 1
    sync(s0, s1)
    return eps_u + guidance_scale * (eps_c - eps_u)       # 合并
```

代价是多占一份权重与一份激活，收益是每步墙钟近似减半。**在实时/批处理场景里，用显存换时间通常比反过来划算**——和第 3 章「用总参换单步」是同一笔经济账。

**③ Parallel VAE + halo_exchange。** 长视频解码时把潜变量按高度切片分给多卡；但卷积/注意力需要邻域信息，所以每个分片要跟上下邻居交换一圈边界（halo）。关键不在「分片」而在「交换」：不交换会在切片边界出现接缝，交换太多又把并行收益吃回去。-41% 显存峰值让长视频解码不再被单卡容量卡住。

> 这三条合起来说明一件事：**半年里生成侧的进步主要来自系统并行，不是新损失函数**。写趋势时别把 90.2 全归功于模型结构。

## 6.3 3D 因果 VAE 与 tokenizer：时间维必须被建模

视频生成侧这半年收敛到「3D 因果 VAE / 时空 tokenizer → 连续 latent 或离散 ID → DiT / 自回归」，代表配置（部分来自站内全双工全书 ch12 与本次调研）：

| Tokenizer | 压缩 | 词表 / 码本 | 形态 |
|---|---|---|---|
| MAGVIT-v2 | 空间 8×、时间 4× | **LFQ 2^18 = 262144**，无可查表 | 离散 ID |
| Cosmos Tokenizer | `CV4×8×8` / `CV8×8×8` / `DV8×16×16`，最高 2048× | 连续 `C=16` / 离散 FSQ ~64K | 两版都有 |
| C-ViViT（Phenaki） | 空间 8×、时间 2× | VQ 8192, dim 32 | 离散 |
| MAGVIT-v1 | 空间 8×、时间 4× | VQ 1024 | 离散 |
| Wan / Sora 类 3D 因果 VAE | `[T/4, H/8, W/8, 16]` | 无码本 | 连续 latent |

**为什么必须用 3D 因果而不是逐帧 2D VQ**：三条硬伤（站内《全双工全书》ch12 与 VQ-GAN 追问已论证）——

1. 逐帧 `argmin` 让同一物理高光在相邻帧跳到不同码，重建出闪烁（Phenaki 对照：逐帧 VQGAN 重建 **FVD 306.1** vs 时序感知 **65.78**）；
2. 传统 VQ 词表越大越坍缩，8192 里大半是死码；
3. 非因果感受野把未来帧信息泄进条件帧，流式生成不成立（MAGVIT-v2 因果 3D 在 Kinetics-600 帧预测 FVD **5.2±0.2** vs 非因果 **11.6±0.6**）。

还有一个和 LLM 主干相关的规模冲突：**262144 个视觉 ID 塞进统一词表会把输出头撑到 GB 级**（书里算过 `V=75840` 时 head 约 621MB，扩到 30 万约 2.6GB）。三条出路是分区扩容、独立视觉输出头、或 RVQ 分层折中。这也解释了为什么实时系统（Higgs）干脆走连续 latent：**每片只出 2 个 latent，像素交给独立因果 DiT，彻底避开码本与 head 膨胀**。

## 6.4 生成侧与理解侧解耦的半年证据

| 证据 | 含义 |
|---|---|
| Janus-Pro（07-12 站内解读） | 理解与生成解耦的统一多模态基模 |
| Wan2.6 冻结 T5/UmT5 | 文本编码不参与生成训练 |
| Higgs（11-05）参考图/音频只进 decoder | 身份与渲染条件不进主干 |
| Qwen3.9-VL 对齐冻 LLM、SFT 1/20 LR 解冻 | 语言能力被结构性保护 |

【推断】把四条放一起看，半年里的共识不是「要不要统一」，而是**「把哪些东西挡在主干之外」**：文本编码器、参考条件、语言基座、像素解码，能外置的都外置。主干只负责语义与时间对齐。**这也是第 12 章「沙漏形架构」趋势的由来：两端分、中间合。**

## 6.7 回到 Hy4 与本章小结

Hy4 preview 本身没有生成侧，但它内置 **10B / 0.7B 的 MTP 投机解码层**【站内 08-28】，属于「用小模型换大模型单步墙钟」的同族思路；与 Wan2.6 的 1.3B 蒸馏版、CFG-Parallel 的「用显存换时间」一起，构成半年里一条清晰的暗线：**几乎所有性能收益都来自把计算重新分配，而不是把计算量加上去**。

**本章小结**：

- 视频生成榜 88.7 → 89.6 → **90.2**，开源首次反超；Wan2.6 单卡吞吐 +2.2× 主要来自系统并行而非新损失。
- Wan2.6 三条可抄做法：冻结 T5/UmT5、CFG-Parallel 正负分支拆卡、Parallel VAE 高度分片 + `halo_exchange`（显存峰值 -41%）。
- 3D 因果 VAE 是硬要求：逐帧 VQ 闪烁（FVD 306.1 vs 65.78）、码本坍缩、非因果泄漏（5.2 vs 11.6）；LFQ 262144 视觉 ID 塞进统一表会撑爆 head。
- 共识是把文本编码器、参考条件、语言基座、像素解码挡在主干之外，形成「两端分、中间合」的沙漏。
- 世界模型把生成变成状态预测，数据门槛更高；图像/3D 同步走「大定上限、小可部署」。
- 回到 Hy4：MTP 投机解码与蒸馏、并行同属「重分配计算」这条暗线。
