## 7.1 数据量增长：一个线性，一个亚线性

这是两条路线最本质的扩展差异（第 2 章原理的直接后果）：

| 数据量 | A 直查（暴力 O(N×D)） | B（ANN 亚线性） |
|---|---|---|
| ×10 | **延时 ×10** | 延时几乎不变（略增） |
| ×100 | **延时 ×100** | 延时仍在同一量级 |

**图示（直觉）**：

```text
延时
  │                                    ╱ A（线性）
  │                              ╱
  │                        ╱
  │   ────────────────────────────── B（近乎水平）
  │ ╱
  └────────────────────────────────→ 数据量
```

**结论**：数据量越大，B 的优势越显著。**A 在数据量增长时会先撞墙**。

## 7.2 数据量增长时两方案的应对

| | A 直查 | B（Milvus） |
|---|---|---|
| 应对方式 | **加节点并行扫**（MPP 线性加速） | **加分片/副本**（水平扩展） |
| 效果 | 墙钟时间缩短，但**总资源消耗不变** | 容量与吞吐同步扩展 |
| 成本 | 线性上升（要撑住延时就得一直加机器） | 也上升，但**单位查询成本下降** |
| 索引 | 无（不用维护） | 索引随数据量增大，内存/SSD 需求上升 |

**A 的"加机器"本质**：把 3 TB 的扫描摊到更多机器上，时间缩短但总 IO 不变——**是用钱换时间**。而 B 是**用索引避免扫描**，两者成本结构完全不同。

## 7.3 QPS 增长：A 的致命瓶颈

| | A 直查 | B（Milvus） |
|---|---|---|
| 单查询资源 | 扫全表（吃满集群） | probe 索引（轻量） |
| 提升 QPS 的方式 | 加节点（成本高、边际递减） | 加副本/分片（近乎线性） |
| 目标 QPS 100+ | **需要非常大的集群** | 常规集群即可 |
| 目标 QPS 1000+ | 基本不可行（成本失控） | 可行（水平扩展） |

**判断**：任何**在线高并发**场景（每秒几十次以上），A 方案在成本上都不可行。**QPS 要求是选型的硬约束**。

## 7.4 维度增长：两边都变贵

embedding 维度从 768 涨到 1536（换更强的模型）：

| 影响 | A 直查 | B（Milvus） |
|---|---|---|
| 存储 | ×2 | ×2（向量 + 索引） |
| 计算 | ×2（每次扫描与内积都翻倍） | 索引 probe 略增，PQ 码本变化 |
| 索引 | 无 | HNSW 内存上升；可能需要重新建索引 |
| 是否需要重导 | 加新列即可 | **通常要重建集合 + 全量重导** |

**B 在"换模型/变维度"时最痛**——这是扩展性里最容易被忽略的代价（第 6 章详述）。

## 7.5 多租户 / 多集合

| | A 直查 | B（Milvus） |
|---|---|---|
| 隔离方式 | 用 WHERE 条件（业务字段/分区）区分 | 用 **Collection / Partition** 隔离 |
| 优点 | 简单，无需额外结构 | 隔离清晰，可分别配索引与资源 |
| 缺点 | 扫描时过滤依赖谓词下推；租户多了管理散 | 集合多了元数据与运维负担上升 |

**建议**：租户少或按业务字段过滤即可 → A 也够用；租户多且要独立索引/配额 → B 的 Collection/Partition 更清晰。

## 7.6 索引维护（B 独有成本）

A 没有索引，所以也没有索引维护。B 则要考虑：

| 维护项 | 说明 |
|---|---|
| **索引构建** | 首次构建耗时（1 亿条 HNSW 可能数小时）；可离线批量建 |
| **增量插入** | 新向量持续写入；HNSW 支持增量，但**长期增量会让图质量退化**，需定期重建 |
| **索引重建** | 换模型、参数调整、图质量下降时都要重建（成本高） |
| **压缩/量化调整** | 从 FP32 换 FP16/PQ，需要重建索引 |
| **容量规划** | 索引内存随数据量增长，要提前规划（HNSW 尤其吃内存） |

**A 没有这些负担**——这是 A 在运维简洁性上的优势（第 6 章）。

## 7.7 各自的失效边界（什么时候必须换方案）

**A 直查该换掉的信号**：

- ❌ 单次查询延时超过业务容忍（如 > 几秒）
- ❌ QPS 要求超过集群能扛（排队严重）
- ❌ 数据量增长导致扫描成本失控（账单明显上升）
- ❌ 在线业务因检索慢而受影响

**B 方案的失效边界（也要注意）**：

- ❌ 数据量太大导致索引内存放不下 → 换 DiskANN / IVF-PQ / 降维
- ❌ 换模型频繁 → 每次重建 + 重导成本高
- ❌ 团队缺乏向量库运维能力 → 考虑托管服务或 A2（SR 内表，复用现有栈）
- ❌ 需要极强 SQL 分析/混合检索 → Milvus 不擅长，考虑 A2

## 7.8 扩展路径建议

```text
阶段 1（起步）：数据量小、低频
  → A 直查（零成本起步，验证业务价值）

阶段 2（增长）：数据量到千万/亿级，或延时不达标
  → 评估 A2（SR 内表 ANN，复用现有栈）
     或 B（Milvus，性能/扩展性更强）

阶段 3（规模化）：高 QPS、多租户、十亿级
  → B 分片集群 / DiskANN
  → 或 B2（原地索引，避免复制）

全程：保留 A 直查作为降级与对账基准
```

## 7.9 本章小结

- **数据量**：A 线性劣化，B 亚线性——数据量越大 B 优势越明显。
- **QPS**：A 靠加机器硬扛（成本线性、边际递减），B 水平扩展（近乎线性）——**QPS 是硬约束**。
- **维度增长**：两边存储计算都涨；但 B 还多了"重建 + 重导"的代价。
- **多租户**：A 用 WHERE，B 用 Collection/Partition（更清晰但运维更重）。
- **索引维护是 B 的独有成本**：构建、增量退化、重建、容量规划。
- **失效边界**：A 撞延时/QPS/成本墙；B 撞索引内存/换模型/运维能力墙。
- **演进路径**：A 起步 → A2 或 B 增长 → B/B2 规模化，全程保留 A 作降级与对账。
