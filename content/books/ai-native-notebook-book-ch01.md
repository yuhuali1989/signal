## 1.1 Notebook 的本质：为什么它长盛不衰

Notebook 的核心不是"能写代码"，而是**把代码、输出、叙述文本混排在同一份文档里**——这就是文学编程（literate programming）的思想。

它解决了数据科学最本质的需求：**探索过程是叙事性的**。你不是一次性写出正确程序，而是"跑一步、看一眼、改一点"。这种探索-观察-修正的循环，正是 Notebook 的甜蜜区。

四十年来它长盛不衰，因为没有任何其他形态更好地支持这个循环。

## 1.2 四次演进

| 代际 | 标志 | 解决什么 | 代表 |
|---|---|---|---|
| **第一代** | REPL / 交互式解释器 | 交互式执行 | IPython、R console |
| **第二代** | 文学编程 Notebook | 代码+输出+叙述混排，可分享 | Jupyter Notebook / .ipynb |
| **第三代** | 云端协作 Notebook | 环境免运维、多人协作、连接数仓 | Colab、Deepnote、Hex、Databricks |
| **第四代** | **AI Native Notebook** | 让 AI 直接参与并执行分析 | Jupyter AI v3、marimo pair、Deepnote Agent |

我们现在正处在第三代向第四代过渡的节点上。

## 1.3 "AI Native" 到底指什么（严格定义）

**不是**：在 Notebook 里挂一个代码补全插件、或者侧边栏放个聊天框问"这段代码什么意思"。

**是**：**AI 不是附加功能，而是执行模型的一部分**——AI 能真正操作计算环境，并且它所做的修改要继承这个环境的执行保证。

两个判别标准：

| 标准 | 说明 |
|---|---|
| **① AI 能否直接操作运行时** | 能否在 kernel 里执行代码、读取内存中的变量、修改 notebook 结构——而不只是"生成一段文本让你复制" |
| **② AI 的编辑是否继承执行保证** | 修改后 notebook 是否仍能确定性复现（而不是引入新的 hidden state） |

只有同时满足这两条，才算 AI Native。这也是第 4 章要展开的核心论点。

## 1.4 AI Native Notebook 的五个特征

| # | 特征 | 说明 |
|---|---|---|
| 1 | **响应式/确定性执行** | 依赖关系可追踪，上游改动自动传播；消除"执行顺序不同结果不同" |
| 2 | **AI 可操作运行时** | Agent 能执行代码、检查数据、修改 notebook，而非只给建议 |
| 3 | **文本优先的文件格式** | 纯文本（.py/.qmd）便于 Git 版本管理与 code review |
| 4 | **上下文感知** | AI 知道 notebook 里已有的代码、数据、变量、schema，而非只看当前 cell |
| 5 | **可执行到可交付** | 从分析到 app / 报告 / 定时任务 / 端点的路径要短 |

## 1.5 2026 年的 Notebook 版图：四类，不是一把尺子

这是选型时**最重要的一张图**。市面上所有"X 比 Y 好"的争论之所以混乱，是因为大家把不同类别的东西放在同一个词"notebook"下比较。

| 类别 | 代表工具 | 文件格式 | 核心价值 | 主要弱点 |
|---|---|---|---|---|
| **① 经典 Jupyter** | JupyterLab 5、Notebook 7、VSCode Notebook | .ipynb (JSON) | 标准、生态、内核丰富（40+ 语言） | **Hidden state**、难 diff |
| **② 响应式** | Marimo、Observable Framework、Pluto.jl | .py / .md / .jl | 可复现、依赖自动追踪、纯文本 | 学习曲线、生态较小 |
| **③ 出版/发布** | Quarto、R Markdown、Curvenote | .qmd / .Rmd / .myst | 一份源出 PDF/HTML/论文/书 | 交互弱、构建慢 |
| **④ 协作 SaaS** | Deepnote、Hex、Databricks | 云端（多兼容 .ipynb） | 协作、调度、权限、数据连接 | 锁定、价格、无离线 |

**关键洞察**：

> 说「Marimo 比 Jupyter 好」只在"响应式 vs 经典"这个维度上有意义；说「Hex 比 Quarto 好」则是完全跨类的错误比较。**先分类，再比较。**

另一个常被忽略的因素：**语言生态决定了一半的选择**。

- R 用户 → 自然流向 RStudio / Positron / Quarto
- Julia 用户 → Pluto.jl
- JS / D3 用户 → Observable
- **Python 用户在四个类别里都有选项** → 所以 Python 用户选择最多，也最困惑（本书主要面向这一群体）

## 1.6 一个必须先破除的执念

行业里流传一句很实用的忠告：

> **不要只优化 notebook 编辑器。要优化 notebook「完成之后」发生的事——协作、部署、调度、以及把结果送到需要它的人手里。**

三个主流工具的编辑体验其实都已经"足够好"。真正的摩擦在下游：**结果怎么交付、怎么定时跑、怎么给没有代码权限的人看、怎么保证下周跑出来还是这个数**。

本书在讲架构（第 2–6 章）之后，会用第 7–8 章把选型拉回这个务实的视角。

## 1.8 本章小结

- Notebook 的本质是**文学编程 + 探索循环**，四十年没被替代。
- 四次演进：REPL → 文学编程 → 云协作 → **AI Native**。
- **AI Native 的严格定义**：AI 能操作运行时 + AI 的编辑继承执行保证；只挂个补全插件不算。
- 五个特征：响应式执行、AI 操作运行时、文本优先格式、上下文感知、可执行可交付。
- **2026 版图分四类**：经典 / 响应式 / 出版 / 协作 SaaS——**跨类比较必然得出错误结论**。
- 语言生态决定一半选择；Python 用户选择最多也最困惑。
- **别只优化编辑器，要优化"notebook 之后"的流程。**
