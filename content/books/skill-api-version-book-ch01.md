## 1.1 一个典型的错位事故

假设有一个「拉取仓库 Issue 列表」的 Skill，版本 v2.1.0，它调用某服务 API 的 `/issues` 端点，读取返回里的 `title`、`state`、`assignee.name` 三个字段。

某天服务端做了一次重构，发布 API 版本 `2026-09-01`，其中：

- `assignee.name` → 改名为 `assignee.displayName`
- `state` 的取值从 `open/closed` 改为 `OPEN/CLOSED`（全大写）

服务端**没有删除** v1，只是把默认版本切到了新版。Skill 侧**一行代码没动**。

接下来发生的事情是这本书要讨论的全部：

| 现象 | 为什么危险 |
|---|---|
| 请求**没有报错**，HTTP 仍是 200 | 监控系统看不到任何异常 |
| `assignee.name` 读出来是 `undefined` | Skill 不校验字段存在性，直接往下走 |
| `state === "open"` 永远为 false | 大小写变了，比较逻辑静默失效 |
| 最终产出的报表「0 个未关闭 Issue」 | **错误结果以正确的姿态交付出去** |

这就是**静默失败**：系统没崩、日志没红、指标没抖，但答案是错的。它比报错难查一百倍，因为你根本不知道要查。

## 1.2 版本错配的三种代价

| 类型 | 表现 | 可发现性 | 危害 |
|---|---|---|---|
| **① 静默失败**（Silent Failure） | 请求成功、字段缺失或语义变了，结果错误 | ★最低，几乎不可见 | ★最高 |
| **② 字段丢失**（Field Loss） | 新增字段读不到、旧字段被删、类型变了 | 中（若做了字段校验） | 高 |
| **③ 行为漂移**（Behavior Drift） | 分页语义、排序、默认值、错误码含义变了 | 低 | 中～高 |

三者的共同点是：**它们都不会让进程崩溃**。一个 Skill 如果只检查「HTTP 状态码 == 200」，对这三种代价**全部免疫失败**。

> 核心判断：**对 API 消费方来说，最危险的不是调用失败，是调用成功但内容已经不是你以为的那个。** 版本检查的全部意义，就是把这个「成功但错了」变成「在调用前就知道它要错」。

## 1.3 ★ 三层版本模型（本书的地基）

这是全书最重要的一张图。很多人把「Skill 的版本」和「API 的版本」当成一件事，其实它们中间还夹着第三层：

```
┌─────────────────────────────────────────────────┐
│ ① Skill 版本（消费方）                           │
│    skill v2.1.0 —— 我的代码、我的假设、我的能力   │
│    演进动力：功能迭代、bug 修复                   │
├─────────────────────────────────────────────────┤
│ ② 服务 API 版本（契约）                          │
│    API 2026-09-01 —— 端点、参数、错误码、行为     │
│    演进动力：服务端重构、业务变更                 │
├─────────────────────────────────────────────────┤
│ ③ 数据 schema 版本（载荷）                       │
│    响应体字段结构：assignee.name → displayName    │
│    演进动力：领域模型变化                         │
└─────────────────────────────────────────────────┘
```

**关键点：这三层各自独立演进，任何人都可以单独升级。**

| 谁动了 | 会发生什么 | 谁该负责对齐 |
|---|---|---|
| Skill 升级 | 新代码可能用到 API 还没有的能力 | Skill 自己（调用前检查） |
| API 升级 | 旧 Skill 假设的字段/语义变了 | Skill 自己（调用前检查） |
| schema 升级 | 载荷形状变了，版本可能没变 | Skill 自己（字段级校验） |

结论很直接：**在绝大多数真实场景里，对齐的责任在消费方（Skill），而不在提供方**。因为服务端不知道有多少个 Skill 在调它，也不知道每个 Skill 依赖了哪些字段。

## 1.4 为什么「调用前检查」是必选项，不是加分项

有四种常见的反对意见，逐个拆：

| 反对意见 | 为什么站不住 |
|---|---|
| 「我在 manifest 里声明了依赖版本，够了」 | 声明是**契约**，不是**事实**。服务端实际跑什么版本，只有问它才知道 |
| 「我们的 API 很稳定，不会乱改」 | 稳定是过程不是承诺；灰度、租户差异、区域部署都会让同一个版本号下的行为不同 |
| 「检查一次要多一个 RTT，太贵」 | 检查可以**缓存**（第 5 章详述），摊薄后成本接近零；而静默失败的成本是无限大 |
| 「错了会报 4xx，我看到了再修」 | 只有**版本不存在**会报 4xx；**字段改名、语义变更**照样返回 200 |

> 一句话：**声明解决「我打算用什么」，检查解决「对面现在到底是什么」。这两件事不能互相替代。**

## 1.5 检查的三个层次（从粗到细）

版本对应不是一次布尔判断，而是三层递进：

| 层次 | 检查什么 | 典型手段 | 失败后果 |
|---|---|---|---|
| **L1 版本对应** | 对面支持的版本区间是否包含我要的版本 | 版本发现端点 / 错误码带 supported 列表 | 明确不兼容 → 拒绝或降级 |
| **L2 能力齐全** | 我要用的可选能力对面是否开启 | capabilities 对象 / extensions map | 缺能力 → 降级到核心行为 |
| **L3 形状校验** | 响应里的字段、类型、取值是否符合预期 | schema 校验 / 字段存在性断言 | 缺字段 → 显式报错而非静默 |

**只做 L1 是不够的**——版本号相同不代表能力相同（灰度、可选能力）。**只做 L3 也不够**——等拿到响应才发现，虽然比静默好，但已经浪费了一次调用且可能已经污染了下游。

第 4、5 章会分别展开 L2（能力协商）和 L1+L2 的调用前落地。

## 1.7 本章要点

- 版本错配最危险的形式是**静默失败**：200 状态码 + 错误内容，监控完全看不见。
- **三层版本模型**：Skill 版本 / 服务 API 版本 / 数据 schema 版本，各自独立演进。
- 对齐的**责任在消费方**——服务端不知道谁依赖了它的哪个字段。
- 声明 ≠ 事实：**manifest 里的声明替代不了调用前的实际检查**。
- 检查分三层：**L1 版本对应 → L2 能力齐全 → L3 形状校验**，缺一层就留一个静默失败的口子。
