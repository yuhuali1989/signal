# 第 1 章 · 判断框架：新增一个架构，到底要不要动手

## 1.1 先破除一个误解

很多团队的默认反应是：**新来一个模型架构 → 要给它写 vLLM 支持 → 要写 CUDA kernel。**

实际上绝大多数情况不是这样。vLLM 能在两年内支持上百种架构，靠的不是给每个模型写算子，而是**把模型拆成可复用的 layer module**——注意力、归一化、RoPE、MLP、MoE、量化线性层——新模型只要能由这些积木拼出来，就不需要写任何 kernel。

真正需要动手的，只有那些**积木盒子里没有的零件**。

> **一句话结论**：vLLM 的模型支持工作量，取决于**新架构与已有实现的「结构距离」**，而不是它有多新、多火。

## 1.2 三档判断框架

把新增架构按工作量分成三档：

| 档位 | 工作量 | 典型情形 | 你要做的事 |
|---|---|---|---|
| **A 档 · 零成本** | 0 行 kernel | 架构与已有模型同构，仅权重名/超参不同 | 什么都不用写，可能只需一个 `--model` 参数 |
| **B 档 · 改配置/改接入** | 几行到几百行 Python，**0 行 CUDA** | 结构可复用，但权重名对不上、config 字段变了、forward 拼装顺序变了 | 加权重名映射、写 model 文件的 `forward`、必要时加一个轻量 layer 子类 |
| **C 档 · 必须开发算子** | 需要写 kernel（CUDA / Triton） | 出现了全新的计算原语 | 写 kernel + 注册 + 接进 layer module |

**经验分布**：真实项目里 A 档约占一半，B 档占三到四成，**C 档不足两成**。但 C 档往往决定了模型能不能跑出可接受的性能。

## 1.3 决策树

```
新架构进来
    │
    ├─ 注意力是不是已有后端能表达的？
    │    （MHA / GQA / MQA / MLA / 线性注意力 / SSM）
    │      ├─ 是 → 继续
    │      └─ 否 → 【C 档】新 AttentionBackend + kernel
    │
    ├─ 归一化、激活、位置编码是否都在已有 CustomOp 列表里？
    │    （rms_norm / fused_add_rms_norm / silu_and_mul / rotary_embedding / poly_norm …）
    │      ├─ 是 → 继续
    │      └─ 否 → 【C 档】新 kernel（先查能不能用 Triton 或直接 torch 组合）
    │
    ├─ 是不是 MoE？路由/专家计算方式是否已有 FusedMoE 覆盖？
    │      ├─ 是 → 继续
    │      └─ 否 → 【C 档】MoE kernel（或至少新的 dispatch 逻辑）
    │
    ├─ 权重能否映射到已有 layer 的参数名？
    │      ├─ 能 → 【A 档】直接跑
    │      └─ 不能 → 【B 档】加权重名映射
    │
    └─ forward 的计算图拼装顺序是否能用已有积木表达？
           ├─ 能 → 【A/B 档】写 model 文件即可
           └─ 否 → 【B 档】扩展 model 文件，必要时加轻量 layer
```

## 1.4 为什么「同构」这么值钱

举个直觉例子：LLaMA 之后出现的绝大多数 dense  decoder-only 模型（Mistral、Qwen2/3、Gemma 的部分版本、Baichuan、InternLM、Yi…）在**计算图层面几乎是同一个东西**：

```
token → embed → [ RMSNorm → QKVProj → RoPE → Attention → OProj → 残差加
                → RMSNorm → GateUpProj → SiLU·Mul → DownProj → 残差加 ] × N
      → 最终 RMSNorm → LM Head
```

差别只在于：注意力头数与 GQA 分组、RoPE 的变体、MLP 的激活、归一化位置（pre/post）、是否有 bias。

**只要这些差异落在已有算子的参数空间里，新模型就是一个新的拼装方式，不是一个新算子问题。** 这就是为什么 vLLM 里很多"新模型支持 PR"只有几十行 Python。

## 1.5 C 档的六类真实情形

真正需要动 kernel 的，翻来覆去就这六类：

| # | 情形 | 例子 | 为什么躲不掉 |
|---|---|---|---|
| 1 | **全新注意力机制** | MLA（DeepSeek 的多头潜在注意力）、线性注意力、SSM / Mamba | 改变了 KV cache 的内容与形状，PagedAttention 的既有 kernel 无法直接读写 |
| 2 | **全新归一化/激活** | 新的 norm 变体（如 poly_norm）、门控变体 | 没有对应算子，且往往是热点路径 |
| 3 | **全新 MoE 形态** | 非标准路由、专家分组方式、共享专家 | dispatch/聚合逻辑不同，FusedMoE 假设不成立 |
| 4 | **新的位置编码** | 非 RoPE 的编码、需要跨模态对齐的位置 | RoPE kernel 不适用，且常与 QK norm 耦合 |
| 5 | **多模态融合新方式** | 视觉 token 与文本 token 的非标准拼接/交叉 | 影响 attention 的 metadata（cu_seqlens、block table 语义） |
| 6 | **全新计算原语** | 自定义稀疏、自定义量化格式 | 无对应 kernel |

**注意第 5 类的隐蔽性**：很多多模态模型"能跑但慢"，问题不在算子缺失，而在**视觉 token 的注意力 metadata 没被正确表达**——这类问题不报错，只掉性能。

## 1.6 一个反直觉的判断：先别写 kernel

即使命中 C 档，动手前还有三个更省力的选项，按顺序试：

**① 先用 torch 原语组合跑通。**
正确性优先。很多"看起来需要新算子"的东西，用几个 `torch` 操作拼起来就能跑，性能不够再优化。

**② 让 torch.compile 去融合。**
vLLM 的编译管线里有针对性的 fusion pass（第 6 章详述）。**如果你的实现用的是标准原语，编译器可能已经自动融合了**——这时手写 kernel 是重复劳动。

**③ 用 Triton 而不是 CUDA。**
除非有明确证据表明 Triton 性能不够，否则先写 Triton：可读性好一个数量级、跨平台（CUDA/ROCm 都能跑）、迭代快。CUDA 留给最后 10% 的极致优化。

> 一条来自 vLLM 贡献经验的实用提醒：**在写融合 kernel 之前先查 `vllm/compilation/`**——vLLM 对已知模式已有融合 hook，只要底层原语暴露得正确，图编译器会自动融合。**手写一个编译器已经会做的融合，是最常见的一种白费功夫。**

## 1.7 本章小结

- **工作量由「结构距离」决定，不由「模型有多新」决定。**
- 三档：**A 零成本**（同构直接跑）/ **B 改接入**（权重映射 + model 文件）/ **C 写算子**（全新原语）。C 档不足两成。
- C 档只有六类：新注意力、新归一化/激活、新 MoE、新位置编码、新多模态融合、全新原语。
- **动手前先试三条省力路径**：torch 原语组合 → 让编译器融合 → 用 Triton 而非 CUDA。
