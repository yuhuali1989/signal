## 4.1 成本不能只看"多存一份"

方案 B 一眼可见的成本是"embedding 多存一份"。但真实 TCO 有五个维度，其中**计算成本**和**运维成本**往往比存储更关键：

| 维度 | A 直查 | B 导入 Milvus |
|---|---|---|
| ① 存储 | 0 额外 | **多一份向量 + 索引**（约 1–2 倍） |
| ② 计算 | **随查询次数 × 数据量线性增长** | 小（只 probe 索引）+ 一次性索引构建 |
| ③ 运维 | 0 新系统（复用 SR） | **新增 Milvus 集群** |
| ④ 同步 | 无 | **ETL 管道 + 一致性维护** |
| ⑤ 人力 | 低（会 SQL 就行） | 中~高（两栈 + 管道 + 调优） |

## 4.2 存储成本：算一笔具体的账

以 **1 亿条、768 维 float32** 为例（单条 3072 字节）：

| 项 | 大小 | 说明 |
|---|---|---|
| Iceberg 原始 embedding | **~300 GB** | 压缩后可能小些（float 数组压缩率有限） |
| Milvus 存一份向量 | **~300 GB** | 复制 |
| HNSW 索引开销 | 每向量约 `4D + 8M` 字节 ≈ 3.3 KB → **~330 GB** | 图结构常驻内存，开销与原始向量同量级 |
| IVF-PQ 索引 | 压缩码本，每向量 m 字节（如 96 B）→ **~10 GB** 量级 | 省内存，但需原始向量做精排 |
| DiskANN | SSD 为主，内存占用低 | 十亿级方案 |

**结论**：

- **B 方案存储 ≈ 原来的 2 倍**（向量复制）+ 索引开销（HNSW 再 +1 倍量级；PQ 则小得多）
- 用 **IVF-PQ / DiskANN** 可显著压低索引内存，代价是召回略降
- 1 亿条尚可控；**10 亿条时这个翻倍会非常肉疼**

## 4.3 计算成本：A 方案真正的钱坑

这是最容易被低估的一项。A 方案**每次查询都要扫一遍全量 embedding**：

```text
单次查询扫描量 = 数据量 × 单条大小
1 亿条 × 3 KB = 300 GB / 次查询
```

**查询频率决定成本**：

| 日查询次数 | A 方案日扫描量（1 亿条） |
|---|---|
| 10 次 | 3 TB / 天 |
| 100 次 | 30 TB / 天 |
| 1000 次 | 300 TB / 天 |

而 B 方案：

```text
索引常驻内存，每次查询只 probe 少量候选
日扫描量 ≈ 与查询次数成正比的小量 + 索引内存常驻成本
```

**换算成钱**：

- A：为撑住高频查询，要么扩大 SR 集群（加节点 = 加钱），要么接受排队
- B：一次索引构建（分摊），之后每次查询极便宜

**成本拐点直觉**：

> 查询频率 × 数据量越大，A 越贵、B 越划算。反之，低频 + 小数据量，A 的"零额外成本"优势明显。

## 4.4 运维成本：引入一个新系统的代价

方案 B 意味着生产环境多一套 **Milvus 集群**（以及它依赖的组件，如元数据存储、对象存储等）：

| 运维项 | A（无新系统） | B（新增 Milvus） |
|---|---|---|
| 部署 | — | 集群规划、组件部署、网络/存储配置 |
| 监控告警 | 复用现有 | 新增：索引健康、内存、QPS、延时、召回 |
| 扩缩容 | 复用 SR 扩容 | Milvus 也要扩（分片、副本） |
| 升级 | — | 版本升级与兼容性验证 |
| 备份恢复 | — | 向量数据备份方案 |
| 故障处理 | — | 多一套系统的 oncall |

**隐性成本**：组织里多一项技术栈，招人/培养/知识传递都有成本。如果团队**已有 Milvus 或向量库经验**，这部分成本大幅下降。

## 4.5 同步管道成本：B 独有的负担

A 直接读 Iceberg，**天然一致、无管道**。B 需要把数据搬过去：

| 管道环节 | 成本/风险 |
|---|---|
| **首次全量导入** | 1 亿条 300 GB 的写入，耗时与资源 |
| **增量同步** | Iceberg 新增数据要持续同步到 Milvus（CDC / 定时批） |
| **一致性对账** | 定期校验两边条数/版本是否一致 |
| **失败重试与幂等** | 同步失败不能产生重复或丢失 |
| **版本漂移** | Iceberg 更新了但 Milvus 还没同步 → 检索结果"过期" |
| **Schema 演进** | 加列/改类型时两边都要跟 |

**这是 B 方案最容易"线上出事"的地方**：检索结果基于的是 Milvus 里的数据，而不是 Iceberg 的真源；一旦同步延迟或失败，业务看到的是旧数据/不完整数据，且不容易被发现。

## 4.6 人力与复杂度成本

| | A | B |
|---|---|---|
| 技能要求 | SQL + StarRocks（团队大概率已有） | SQL + Milvus 调优（索引参数、召回调优、容量规划） |
| 排障链路 | 一条（SR → Iceberg） | 两条（SR/Iceberg + Milvus 同步） |
| 上线速度 | 快（写个 SQL 就能跑） | 慢（导入 + 建索引 + 调参 + 管道） |

## 4.7 TCO 测算示例（1 亿条，日查询 100 次）

以下为**相对量级示意**（实际请用自家云报价）：

| 成本项 | A 直查 | B 导入 Milvus |
|---|---|---|
| 存储 | 0（复用 Iceberg 300 GB） | +300 GB 向量 + 索引（HNSW 约 +330 GB） |
| 计算（日 100 次 × 300 GB 扫描） | **30 TB/天 扫描** —— 需要较大 SR 集群支撑 | 索引内存常驻 + 少量 probe |
| 集群 | 需扩 SR 以撑住并发扫描 | Milvus 集群（内存型为主） |
| 运维 | 0 新增 | +1 套系统 |
| 同步 | 无 | 全量导入 + 增量管道 + 对账 |
| **适用判断** | 若查询集中在离线批量、能错峰，尚可 | 若要求在线低延时，B 反而更省 |

**关键洞察**：日 100 次查询看起来不多，但 A 要扫 30 TB/天。若这些查询要求在**秒级返回**（在线），A 需要的集群规模会远超 B——**此时 B 反而更便宜**。

## 4.8 成本拐点：什么时候选谁

```text
成本优势区（粗略）：

数据量 ↑
  │  千万级+ & 高频   → B（索引摊薄查询成本）
  │  百万级 & 中频    → 临界，看延时要求
  │  十万级 & 低频    → A（零额外成本）
  └────────────────────────→ 查询频率 ↑
```

**判断三问**：

1. **QPS 要求多少？** 高于几十 → 基本必须 B（或 A2）
2. **数据量多大？** 千万级以上 → A 的扫描成本开始失控
3. **能否容忍同步延迟？** 不能（要强一致）→ A 或 B2（原地索引）

## 4.9 降本的几个实用手段

| 手段 | 适用 | 效果 |
|---|---|---|
| **降维**（PCA/投影到 256–512 维） | 两边都行 | 存储与计算同比下降，注意召回损失 |
| **量化**（PQ/SQ） | B | 索引内存大幅下降 |
| **标量过滤前置** | 两边都行 | 先按标签/时间过滤，减少参与检索的向量 |
| **分区检索** | A | 按业务分区只扫部分数据，避免全表 |
| **冷热分层** | B | 冷数据放 DiskANN/SSD，热数据放内存 |
| **错峰批量** | A | 把检索放到离线窗口，避开在线资源竞争 |

## 4.10 本章小结

- TCO 五维：**存储、计算、运维、同步、人力**——存储只是其中一项。
- **存储**：B 约翻倍（向量 + 索引；PQ/DiskANN 可压低）。
- **计算是 A 的钱坑**：每次查询全量扫描，日 100 次 × 1 亿条 = 30 TB/天。
- **运维**：B 多一套 Milvus（部署、监控、扩容、升级、oncall）。
- **同步是 B 的独有负担**：全量导入 + 增量管道 + 一致性对账 + 版本漂移风险。
- **成本拐点**：低频小数据量 → A 划算；高频大数据量/低延时要求 → B 反而更省。
- 降本手段：降维、量化、标量过滤前置、分区、冷热分层、错峰。
