## 7.1 谁能连数据源

| 形态 | 能连数据库/数仓吗 | 说明 |
|---|---|---|
| **Notebook** | ★**能** | 可在 cell 里直连（SQL cell、DuckDB、各类驱动），是探索的必要条件 |
| **脚本** | ★**能** | 生产 ETL / 训练管线的主力 |
| **HTML** | ❌ **不能** | 它是静态文件；除非内嵌 JS 去调一个后端 API（那就不是纯 HTML 了） |

> 这条差异看似显然，却常被忽略：**HTML 天然与数据源隔绝，这是它「只能呈现结论」的根本原因**。任何「让业务方在 HTML 里查最新数据」的想法，都需要额外的后端，那时它已经是 App 而不是 HTML 了（第 4.5 节）。

## 7.2 ★ 下推 vs 拉进内存：最关键的工程概念

同样一句「做个聚合」，做法不同，代价差几个数量级：

| 做法 | 过程 | 代价 |
|---|---|---|
| **下推（pushdown）** | 让 SQL 在数仓里聚合，只把结果（几行）取回来 | ★小 |
| **拉进内存** | `SELECT *` 拉几千万行，再用 pandas 聚合 | 内存爆、慢、贵 |

```python
# ❌ 反例：把全表拉进内存再聚合
df = pd.read_sql("SELECT * FROM events", conn)
summary = df.groupby("channel").size()

# ✅ 正例：下推，只取结果
summary = pd.read_sql("""
    SELECT channel, COUNT(*) AS n
    FROM events
    WHERE dt BETWEEN %(start)s AND %(end)s
    GROUP BY channel
""", conn, params={...})
```

| 形态 | 下推能力 |
|---|---|
| **Notebook** | ★能做，且应优先做（SQL cell、DuckDB 直查 parquet、连数仓） |
| **脚本** | ★能做，生产管线里是标准实践 |
| **HTML** | 无（数据已经固化在页面里，谈不上推） |

> **这是区分「会做数据分析」和「会做数据分析工程」的分水岭**：不在于用不用 notebook，而在于**有没有把计算放到离数据最近的地方**。

## 7.3 三者在数据链路中的角色

```
数据源（数仓 / 数据湖 / 业务库）
   │
   ├─ ② 脚本 / 流水线：ETL、清洗、特征、训练  ← 全量数据的主战场
   │        ↓ 产出结果表 / 特征集 / 模型
   │
   ├─ ① Notebook：探索、验证、建模、解释      ← 结果集 + 采样的主战场
   │        ↓ 产出结论与图表
   │
   └─ ③ HTML / App：呈现结论给业务方          ← 只装结果集
```

| 环节 | 用什么 | 为什么 |
|---|---|---|
| 处理 TB 级原始数据 | **脚本 / 数仓 SQL** | notebook 与 HTML 都装不下 |
| 探索、可视化、假设验证 | **Notebook** | 要交互、要立刻看到 |
| 给人看结论 | **HTML / App** | 好分发 |

## 7.4 内存与规模边界

| 形态 | 边界 | 越界后果 |
|---|---|---|
| **Notebook** | 受内核所在机器内存限制；大 DataFrame 渲染 200–800 ms；文件 > 100 MB 性能骤降 | 卡死、OOM、保存缓慢 |
| **脚本** | 同样受机器内存限制，但**可批处理/流式/分布式** | 可通过架构扩展 |
| **HTML** | ★**页面大小随嵌入数据量线性膨胀** | 打开慢、移动端崩溃 |

**Notebook 侧的三条实用策略**：

| 策略 | 做法 |
|---|---|
| **先看采样** | `df.head()` / `df.sample()` / `LIMIT 1000`，别一上来全量渲染 |
| **只取需要的列** | 别 `SELECT *` |
| **大表存文件** | 中间结果落 parquet，notebook 只读结果 |

**HTML 侧**：只嵌入聚合后的结果（通常 KB 级），全量明细靠「下载」或「跳转到系统查询」。

## 7.5 缓存与中间结果

| 形态 | 缓存做法 |
|---|---|
| **Notebook** | `mo.cache` / `mo.persistent_cache`（marimo）；或手动落盘 parquet + `if not exists` 判断 |
| **脚本** | 中间结果落盘、断点续跑、工作流引擎的缓存（Airflow / Ray 等） |
| **HTML** | 无缓存概念（数据已固化） |

> 缓存对 notebook 的意义很特殊：**它让「增量探索」不必每次付全量代价**，从而缓解了第 2 章「脚本必须全量重跑」的痛点。

## 7.6 ★ 凭证与安全：notebook 的隐蔽风险

| 风险 | 说明 | 解法 |
|---|---|---|
| **密码写进 notebook** | 连接串硬编码 → 随文件进 Git → 泄露 | ★凭证由平台/环境变量注入，**永不写进文件** |
| **输出里含敏感数据** | 打印了含手机号的明细 → 输出被导出分享 | 脱敏、只展示聚合、导出前审查 |
| **HTML 快照外泄** | 报告被转发到不该看的人手里 | 权限控制、水印、过期链接 |

> **三者的风险面不同**：脚本的凭证问题靠 CI/CD 的 secret 管理解决（较成熟）；**notebook 的问题是「人在交互中随手写的」，最容易失控**；HTML 的问题则是「一旦发出去就收不回」。

## 7.7 本章要点

- **HTML 天然与数据源隔绝**——这是它只能呈现结论的根本原因；要「查最新数据」就得升级成 App。
- ★**下推 vs 拉进内存**是数据工程的分水岭：`GROUP BY` 应该发生在数仓，而不是 pandas 里。
- 数据链路角色：**脚本/数仓处理全量 → Notebook 探索结果集 → HTML/App 呈现结论**。
- 边界：notebook 受内存与文件大小（>100 MB 骤降）限制；★**HTML 页面随嵌入数据线性膨胀**；脚本可通过架构扩展。
- Notebook 三策略：**先看采样、只取需要的列、大表落 parquet**。
- ★**凭证绝不写进 notebook**（最容易失控的一环）；HTML 一旦发出就收不回，需权限与水印。
