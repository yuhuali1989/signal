# 第 3 章 · 执行模型：状态才是根本分野

## 2.1 四种执行模型

| 形态 | 执行模型 | 什么时候跑 | 状态存续 |
|---|---|---|---|
| **Jupyter Notebook** | **有状态内核**（cell 逐个送进常驻 kernel） | 用户手动触发某个 cell | ★**一直存在**，直到 kernel 重启 |
| **marimo Notebook** | **响应式 DAG**（依赖驱动） | 变更沿依赖图传播 | 状态由代码推导，无隐藏残留 |
| **Python 脚本** | **一次性进程**（从上到下执行） | 运行即全量执行 | ★进程结束即消失 |
| **HTML** | **不执行**（或仅前端 JS） | 打开时渲染 | 无 |

**一句话概括差异**：

- Notebook：**交互式增量执行**——你可以只跑第 5 个 cell
- 脚本：**批处理全量执行**——每次都必须从头跑到尾
- HTML：**没有执行**——它只是上一次执行的化石

## 2.2 ★ hidden state：Notebook 的阿喀琉斯之踵

Jupyter 的执行模型带来一个致命副作用：**你在屏幕上看到的，未必是「从头跑一遍」的结果**。

典型场景：

```
① 跑 cell 1（读数据）→ 跑 cell 2（清洗）→ 跑 cell 3（聚合）→ 得到「增长 23.5%」
② 回头改了 cell 2 的筛选条件，但忘了重跑 cell 3
③ 你看到 cell 3 输出「23.5%」——但那是旧 cell 2 的结果
④ 你把这个数写进报告
```

更隐蔽的三种情况：

| 情况 | 现象 |
|---|---|
| **删掉的 cell，变量还在** | 删除 cell 不会清除它定义的变量，下游仍在用「幽灵变量」 |
| **执行顺序 ≠ 页面顺序** | 页面从上到下读起来通顺，实际执行顺序可能是 1→5→3→2 |
| **重复执行同一 cell** | 有副作用的操作（如 append、累加）跑两次结果就变了 |

**业界实证**：**约 96% 的公开 Jupyter notebook 不可复现**——根源就在这里。

### 三种解法

| 解法 | 做法 | 效果 |
|---|---|---|
| **纪律** | 分享/提交前必须 **Restart Kernel & Run All** | 有效但靠人 |
| **工具** | `nbconvert --execute`（headless 全量跑，有 cell 报错即失败）接进 CI | ★把纪律变成流水线 |
| **换执行模型** | 用响应式 notebook（marimo）：依赖驱动、删除真生效、**无 hidden state** | ★从运行时层面根治 |

## 2.3 脚本的一次性执行：代价与红利

脚本每次运行都是**全新进程、从头到尾**，这既是成本也是它最大的优点：

| | 说明 |
|---|---|
| **代价** | 探索时很痛——改一行要重跑全部（可能几分钟到几小时）；看不到中间结果，只能靠 print/log |
| **★红利** | **结果必然等于「从头跑一遍」的结果**，不存在 hidden state；可复现性天然最高；可预测、可调度 |

> 这就是为什么「跑批任务应该用脚本而不是 notebook」——**不是脚本更好写，而是脚本没有「上次跑的残留」这种不确定性**。

### 折中手段

| 手段 | 说明 |
|---|---|
| **缓存** | 把中间结果落盘（joblib / pickle / parquet），下次跳过已完成步骤 |
| **断点续跑** | 记录进度，失败后从断点继续 |
| **参数化** | CLI 传入日期/阈值，避免改代码 |
| **%%cache / marimo 的 mo.cache** | Notebook 侧也能拿到类似收益 |

## 2.4 响应式 DAG：第三种可能

响应式 notebook（marimo）给出了既交互又可复现的模型：

```
改 cell A → 静态分析出依赖 A 的所有 cell → 自动重跑（或标记 stale）
删 cell A → A 定义的变量被真正清除 → 下游随之更新
```

| 相比 Jupyter | 相比脚本 |
|---|---|
| ★消除 hidden state（删除真生效、顺序由依赖决定） | ★保留交互（不必每次全量重跑） |
| 执行顺序 = 依赖顺序，不是页面顺序 | 改一个 cell 不用等全流程 |

**代价**：需要遵守新约束——**不要跨 cell 修改对象**（marimo 只跟踪变量定义与引用，不跟踪运行时对象变更）；可变状态要用 `mo.state`。

## 2.5 增量 vs 全量：什么时候该付哪种代价

| 场景 | 该用 | 理由 |
|---|---|---|
| 探索、调参、看中间结果 | **Notebook（增量）** | 全量重跑的等待会扼杀探索 |
| 跑批、定时、生产 | **脚本（全量）** | 要的是确定性与可预测 |
| 又想交互又想可复现 | **响应式 Notebook** | 两者兼得，但需遵守约束 |
| 只给人看结论 | **HTML** | 不需要执行 |

**一个实用的经验规则**：

> **如果一个分析需要「跑一次看一眼」超过 10 次，就该在 Notebook 里做；如果它开始被定时执行，就该变成脚本。**

## 2.6 本章要点

- 四种执行模型：**Jupyter=有状态内核 ／ marimo=响应式 DAG ／ 脚本=一次性进程 ／ HTML=不执行**。
- ★**hidden state** 是 Notebook 最大弱点（删 cell 变量残留、顺序错乱、重复执行副作用），实证约 **96% 公开 notebook 不可复现**。
- 三条解法：**Restart & Run All 纪律 ／ `nbconvert --execute` 接 CI ／ 换响应式引擎根治**。
- 脚本的「一次性全量」看似笨，却是**可复现性与可调度性的来源**；可用缓存/断点续跑缓解重跑成本。
- 响应式 DAG 兼得交互与可复现，代价是**不能跨 cell 改对象**。
- 经验规则：**探索超过 10 次「跑一次看一眼」→ 用 Notebook；开始被定时执行 → 转脚本**。
