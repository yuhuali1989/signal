## 6.1 适配器模式：把版本差异关在一个地方

**问题**：如果 `if version == "v1": ... else: ...` 散落在业务代码各处，每加一个版本就要改 N 处，且极易漏改——这是版本适配最常见的崩溃点。

**解法**：**适配器（Adapter）模式**——把「外部形状」翻译成「内部统一模型」，业务代码只认内部模型。

```
外部 API v1  ─┐
外部 API v2  ─┼─→ Adapter(v1) ─┐
外部 API v3  ─┘   Adapter(v2) ─┼─→ 内部统一模型 ─→ 业务代码
                  Adapter(v3) ─┘      (Domain Model)
```

三条硬规则：

| 规则 | 说明 |
|---|---|
| **① 内部模型稳定，外部差异全在适配器** | 业务代码**永远不出现版本号判断** |
| **② 一个版本一个适配器，互不 if-else** | 加新版本 = 加一个新类，不改老代码（开闭原则） |
| **③ 适配器负责双向翻译** | 不只是解析响应，**请求参数也要翻译**（v1 用 `name`，v2 用 `displayName`） |

```python
class V1Adapter:
    def to_domain(self, raw): 
        return Issue(title=raw["title"],
                     assignee=raw.get("assignee", {}).get("name"),   # 旧字段
                     state=raw["state"].lower())                     # open/closed
    def to_request(self, issue): return {"title": issue.title, "state": issue.state.upper()}

class V2Adapter:
    def to_domain(self, raw):
        return Issue(title=raw["title"],
                     assignee=raw.get("assignee", {}).get("displayName"),  # 新字段
                     state=raw["state"].lower())                     # OPEN/CLOSED → 统一成小写
```

注意 V2 适配器把 `OPEN/CLOSED` 归一成小写——**第 1 章那个「大小写变了导致比较失效」的事故，在适配层就消掉了**，业务代码毫无感知。

## 6.2 字段兜底与 fallback 链

第 3 章 manifest 里的 `fallback` 字段在代码层落地：

| 场景 | 兜底策略 |
|---|---|
| 字段改名（`name → displayName`） | **fallback 链**：先取新名，取不到回退旧名 |
| 字段被删且无替代 | 判为必需 → 显式报错；判为可选 → 用默认值 |
| 类型变化（string → object） | 适配器按类型分支归一到内部模型 |
| 枚举取值变化 | 适配器做**取值映射表**（`OPEN → open`） |
| 多了未知字段 | **忽略**（第 2.5 节铁律） |

**fallback 链的两个纪律**：

1. **有限长度**（通常 1～2 级）。无限 fallback 会把「字段到底叫什么」变成考古问题。
2. **★fallback 命中要打点**。每次走 fallback 说明「你以为的版本」和「实际的版本」不一致，这是第 7 章版本漂移监控的**最重要信号源**。

## 6.3 渐进迁移：不要一次性切换

版本迁移最大的风险是「一刀切」。推荐三段式：

| 阶段 | 做法 | 目的 |
|---|---|---|
| **① 双跑（Dual-run）** | 新旧版本**都调**，比对结果，以旧版为准对外 | 在真实流量上验证新适配器正确性 |
| **② 影子流量（Shadow）** | 新版处理真实请求但**结果不对外**，只记录差异 | 评估新版行为差异，零业务风险 |
| **③ 灰度切换（Canary）** | 按 1% → 5% → 20% → ... 逐步把新版结果切为对外 | 出问题影响面可控 |

**双跑期的差异告警**：新旧适配器产出的内部模型若不一致（比如某字段值不同），**必须告警并保留原始响应**——这就是「行为漂移」的探测器。

**切换的成功判据**（建议）：连续 N 天（如 7 天）双跑差异率 < 阈值（如 0.1%）后，才进入灰度。

## 6.4 网关代协商：把复杂度集中到一处

当一个 Skill（或客户端）要对接**很多个**服务时，逐个做 preflight 与版本协商会重复且难统一。

**方案**：引入**网关 / 代理层**代协商：

```
Skill ──→ Gateway（统一做：版本发现、能力协商、协议转换、缓存、重试）
             ├──→ 服务 A（v1）
             ├──→ 服务 B（2026-05-01）
             └──→ 服务 C（2026-09-01）
```

| 网关承担 | 收益 |
|---|---|
| 版本发现与选择 | Skill 不必知道每个服务的版本细节 |
| 能力协商与降级 | 统一策略，避免各 Skill 各写一套 |
| 协议 era 转换（如 legacy ↔ modern） | 让老客户端能调新服务 |
| 探测结果缓存 | 缓存命中率更高（多 Skill 共享） |
| 统一重试与幂等 | 一致的错误处理语义 |

> **代价**：网关成为新的关键依赖与单点。需配套高可用设计，且**网关自身的版本兼容也要被监控**（它是另一个消费方）。

## 6.5 回滚预案：迁移必须有退路

任何版本切换都要预先写好回滚：

| 要素 | 要求 |
|---|---|
| **开关** | 版本选择走**配置项**而非硬编码，可一键切回 |
| **旧适配器保留** | 切换后**不要立刻删除**旧适配器，保留至少一个废弃周期 |
| **回滚判据** | 事先定义：错误率 > X%、差异率 > Y%、P99 > Z 就回滚 |
| **演练** | 回滚动作要在迁移前**演练过**，不能是纸面预案 |

**常见失误**：切换成功后立刻清理旧代码，结果新版出问题却回不去——**清理旧适配器应当发生在「新版稳定运行 + 旧版已过废弃窗口」之后，而不是切换完成的那一刻**。

## 6.6 CI 必须覆盖所有活跃版本

「只在最新版上跑测试」是最常见的多版本翻车原因。

| 测试层 | 做法 |
|---|---|
| **单元测试** | 每个适配器一套，用**对应版本的真实样例响应**做 fixture |
| **契约测试** | 见第 7.2 节（consumer-driven） |
| **矩阵 CI** | ★对每个「Skill 版本 × API 版本」组合跑一遍核心用例（直接对应第 3.3 节矩阵） |
| **回归fixture** | 把线上出现过的真实响应（尤其是出问题的）固化为 fixture |

**矩阵 CI 的规模控制**：组合爆炸时用「**最新版本 + 上一个版本 + 最老仍支持的版本**」三点采样，而不是全组合——覆盖典型代际即可，成本可控。

## 6.7 本章要点

- **适配器模式**是版本适配的正解：内部模型稳定，外部差异全在适配器，**业务代码永不出现版本判断**。
- 加新版本 = **加一个新适配器**，不改老代码。
- **fallback 链要有限长度，且命中必须打点**——它是版本漂移最灵敏的信号。
- 迁移走 **双跑 → 影子 → 灰度**三段式，切换判据量化（差异率 < 阈值 + 连续 N 天）。
- 多服务场景用**网关代协商**统一策略；但网关自身也要被监控、要做高可用。
- **回滚预案必须先于切换存在**；旧适配器在废弃窗口结束前**不要删**。
- CI 要跑**版本矩阵**，至少覆盖「最新 / 上一个 / 最老仍支持」三点。
