# 第 9 章 · 治理三线合流：红线、标准与企业采购

2026 年 10–11 月最值得记录的现象，不是某个模型变强了，而是**三条原本互不相干的线在两周内合流**：学术侧在做测量、工作联盟在写控制条款、标准组织在统一报告格式。三者指向同一个对象——「一次自我修改」的完整证据链。

## 9.1 三线总览

| 线 | 核心机制 | 代表 | 回答什么 |
|---|---|---|---|
| **测量线** | L0–L3 证据阶梯、治理级测量、跨轮 replay | 三篇综述（arXiv 2607.07663 / 2610.38266） | 「这算不算进步」 |
| **控制线** | 冻结评估器、速率上限、算力回收权、不可变日志、回滚快照 | RSI 红线草案 24 条（10-23） | 「允许怎么改」 |
| **标准线** | 冻结集最低清单、统一报告字段、可变集披露 | MLCommons 清单（11-06） | 「怎么报才可比」 |

三线不是层层加码，而是补三个不同的洞：没有测量线，「变好」是 subjective；没有控制线，评估器会被改；没有标准线，各家报告无法横向比，等于没有外部约束。

## 9.2 控制线：红线 24 条按五类读

24 条全部要求**可外部验证**，这是它与一般 AI 伦理原则最大的区别。按机制归成五类：

| 类 | 条款要点 | 工程实现 | 对应本书 |
|---|---|---|---|
| **① 冻结评估器** | 任何自我修改必须在**冻结的评估器**上通过回归；评估器本身不得被本次修改触及 | `frozen_suite` + hash 校验 + `forbidden_paths: ["eval/**"]` | 第 6 章 V0–V2、第 8 章 F4 |
| **② 改进速率上限** | 单次修改带来的能力提升不得超过上一版本某比例，超出强制拆成多次 | 准入阈值 `delta ≤ k · delta_prev`，超限拆分 PR | 第 7 章改进速率（间接约束） |
| **③ 算力回收权** | 运营方必须保留远程切断训练集群的能力 | 带外管理通道、训练作业 kill switch、凭据独立于模型 | 第 6 章「人在环的最终兜底」 |
| **④ 不可变日志** | 所有权重变更、评估记录写入只追加日志 | append-only 存储 + hash 链 + 第三方时间戳 | 第 8 章 old/new_state_hash |
| **⑤ 母亲版本保全** | 必须保留可回滚到 30 天前的完整版本 | 30 天快照 + hash 链 + 定期恢复演练 | 第 8 章反事实臂 `arm_ancestor` |

**① 是整套红线的地基**，其余四条都建立在「有一个不被本次改动污染的真值」之上。这也解释了为什么第 6 章要不惜篇幅讲验证层级：冻结评估器不是一条行政规定，是把 V0–V2 的强信号从可改集合里物理隔离出来的工程动作。

② 值得多说一句：它是唯一一条直接试图给「改进速率」设限的条款。但因为第 7 章说的量纲问题，工程上只能退化成「单次 delta 阈值 + 强制拆分」这种粗粒度控制——**这恰好反证了治理级测量有多空白**。

## 9.3 标准线：MLCommons 冻结集最低清单（11-06）

继红线草案后，MLCommons 联合 11 家实验室推出清单，四条：

1. **数学推理、代码正确性、安全红线三类必须进入冻结集**，其余类目各实验室自定；
2. **统一审计报告字段**：冻结集清单 / 回归阈值 / 回滚 hash 链 / 可变集与公开榜单重合度声明，格式与 K3.5 现有报告兼容；
3. ★**要求披露「可变集与公开 leaderboard 的重合度」**——堵住「在可变集上讨好下游评测」这条隐性绕过路径；
4. 首批 **6 家签署，含两家中国实验室**。

第 3 条是整份清单里最有洞察力的一刀。它不假设厂商会守规矩，也不试图禁止刷分（禁不了），只要求**把重合度摆到台面上**。这和前面讨论过的「L7 出口管控防的是合规 + 无意泄漏 + 提高恶意成本，不是绝对安全」是同一种务实思路：**治理不消灭动机，治理让动机可见、让越界可追责。**

## 9.4 测量线：可信 RSI 的四个主题与三层评估

人大/UCAS 的可信 RSI 综述给了四个必须**同时成立**的主题：

- 真实且持续的能力提升（不是一次性刷分）；
- 行为约束与对齐（能力提升不能伴随越界）；
- 系统安全 / 隐私 / 韧性（自改不能把系统变脆）；
- 透明与可控（能解释、能停、能退）。

以及第 7 章已展开的三层评估：单次更新 / 后续继承系统 / 改进机制本身。把四主题 × 三层叠起来就是一张 12 格的评估矩阵——**多数产业报告只填了左上那一格**（单次更新的能力提升）。

## 9.5 审计报告字段结构（K3.5 兼容）

```json
{
  "run_id": "rsi-20261101-07",
  "model": "Kimi-K3.5",
  "round": 7,
  "mutation": {
    "diff": "s3://…/0007.diff",
    "target": "triton_kernel/attention",
    "scope_ok": true,
    "v0_numerical_equiv": "pass@1e-5"
  },
  "frozen_evaluators": {
    "list_hash": "sha256:…",
    "classes": ["math_reasoning", "code_correctness", "safety_redline"],
    "touched_by_this_change": false
  },
  "regression": {
    "math_subset_delta": -2.3,
    "threshold": 0.0,
    "canary_failures": 0,
    "verdict": "REJECT"
  },
  "rollback": { "to_hash": "sha256:…", "auto": true, "human_intervention": false },
  "disclosure": { "mutable_vs_public_leaderboard_overlap": 0.12 },
  "log_chain": "sha256:… → sha256:…"
}
```

这正好是站内 11-01 首例拦截案例的字段形状：第 7 轮数学子集 -2.3 点 → `verdict: REJECT` → 自动回滚、零人工。**报告不是事后补的文档，是流水线里决定 accept/reject 的那个数据结构**——这一点最关键，很多团队把「审计」做成旁路日志，那就退化成无法拦截的旁观者。

## 9.6 企业采购十问

采购一个声称支持自改进的系统时，按这十条问，比看 benchmark 有用：

1. 冻结集包含哪些类目？谁定的？hash 能否提供？
2. 自改产物的 **mutation scope** 是什么？`eval/**` 在不在禁止路径里？
3. 评估器被本次改动碰过没有？怎么证明（`list_hash` 前后一致）？
4. 回归阈值多少？金丝雀集从哪来？
5. 回滚是自动还是人工？演练过吗？RTO 多少？
6. 是否保留 30 天母亲版本？能否现场演示一次恢复？
7. 算力回收权在谁手上？带外通道是否独立于模型权限？
8. 审计报告是否第三方可验？可变集与公开榜单重合度披露了吗？
9. **改进速率**怎么定义？分母包含人工审核预算吗？
10. 有没有公开的失败/拦截案例？只报成功不报拦截的流水线不可信。

第 10 条是经验之谈：K3.5 那条线之所以可信，恰恰因为它敢公开一次被拦截的失败。**一个从不拦截的评估器，大概率只是没接进准入路径。**

## 9.7 治理的能力边界（必须说清）

- 治理**不阻止模型变强**，只保证「变强这件事可归因、可复现、可退」；
- 它防的是**合规风险、无意泄漏、把恶意成本抬高**，不是绝对安全——真正恶意的内部人员仍有无数旁路，那是行为审计与水印溯源的另一个量级；
- 条款也会**被优化**：一旦「冻结集分数」变成 KPI，第 6 章第 ④ 类失败就会以「训练集悄悄覆盖冻结集分布」的形式回来。所以标准线要求披露重合度、要求独立留出，而不是相信一纸承诺。

这也解释了为什么 2026 年的治理成果看起来「很工程、很不哲学」：24 条红线谈的是 hash 链和 kill switch，MLCommons 谈的是字段和重合度。**在一个连「改进速率」都没有量纲的领域，能落地的只有证据链，不是价值判断。**

## 9.8 本章小结

- 三线合流：测量线管「算不算进步」、控制线管「允许怎么改」、标准线管「怎么报才可比」。
- 红线 24 条归五类，冻结评估器是地基；速率上限因缺量纲只能退化成粗粒度 delta 阈值。
- MLCommons 四条里最有洞察力的是「披露可变集与公开榜单重合度」——不禁止刷分，只让它可见。
- 审计报告是准入路径里的判定数据结构，不是旁路日志；企业采购十问里「有没有公开拦截案例」最能验真。
- 治理不阻止变强，只保证可归因；它防的是合规与无意风险，不是绝对安全。
