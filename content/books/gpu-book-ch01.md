# 第 1 章：GPU 的诞生——为什么需要为并行而生的处理器

> **学习目标**：理解 CPU 与 GPU 在设计哲学上的根本差异（延迟优化 vs 吞吐优化），搞清 SIMD 与 SIMT 的区别，并能判断「什么任务适合 GPU、什么不适合」。

---

## 1.1 一个朴素的问题：为什么 CPU 不够用

2007 年前后，计算机图形学遇到一个瓶颈：屏幕分辨率从 1024×768 涨到 1920×1080，每个像素都要做一次光照计算。一个 1080p 画面有约 **207 万像素**，如果每帧要让 CPU 串行地挨个计算——即便 4 核、每核 3GHz——也远远赶不上每秒 60 帧（即 16.7ms 内算完 207 万次光照）的要求。

问题的本质不在于「单条指令慢」，而在于「要算的东西高度同质、数量巨大」。这正是 GPU（Graphics Processing Unit）被发明出来的动机：**把芯片面积从「聪明的控制单元」让给「大量的、简单的计算单元」**。

一句话概括 GPU 的设计哲学：

> **CPU 为「一个任务尽快完成」优化（低延迟）；GPU 为「一百万个任务同时推进」优化（高吞吐）。**

---

## 1.2 延迟优化 vs 吞吐优化

看一组对比（典型桌面级，数量级示意）：

| 维度 | CPU（如 x86 服务器核） | GPU（如 NVIDIA H100） |
|---|---|---|
| 核心数 | 数十个「大核」 | 数千到上万个「小核」（SM 内 CUDA Core） |
| 单核控制能力 | 乱序执行、分支预测、多级缓存 | 顺序、轻量控制，依赖硬件调度器 |
| 缓存 | 大（每核数十 MB L2/L3） | 小（每 SM 约 256KB 寄存器文件 + 共享内存） |
| 目标 | 单线程延迟低 | 总体吞吐高 |
| 典型 FLOPS（FP32） | 单核 ~0.1 TFLOPS | 整卡 ~67 TFLOPS（H100 SXM） |

CPU 把大量晶体管花在 **预测、缓存、乱序、超标量** 上，保证一条指令「尽可能快」。GPU 把这些晶体管花在 **计算单元** 上，容忍单条指令慢，但让海量线程轮转，用「并行」掩盖延迟。

这引出一个关键概念——**延迟隐藏（latency hiding）**：当一个线程在等内存返回数据时，GPU 立刻切换到另一个就绪线程继续算。只要「就绪线程足够多」，计算单元就永远有活干。这正是 GPU 并发模型的基石（第 4 章详述）。

---

## 1.3 阿姆达尔定律：并行不是万能药

在兴奋之前，先泼一盆冷水。阿姆达尔定律（Amdahl's Law）告诉我们：

$$
\text{加速比} \le \frac{1}{(1 - p) + \frac{p}{n}}
$$

其中 $p$ 是可并行部分的比例，$n$ 是并行资源数。

**推论**：如果程序里有 10% 必须串行，那么无论你堆多少 GPU，加速比上限也只有 10 倍。GPU 擅长的是 $p \to 1$ 的任务（矩阵乘法、卷积、图像变换、物理仿真），对强串行、强分支的任务（解析 JSON、递归搜索、操作系统调度）无能为力。

> 实践启示：**GPU 是加速器，不是替代 CPU。** 现实中几乎总是「CPU 负责控制流与 I/O，GPU 负责内核计算」的异构协作。

## 1.4 SIMD 与 SIMT：两种「一起算」的方式

「让很多线程一起算」有两种经典实现，理解它们的差别是理解 GPU 并发的前提。

### 1.4.1 SIMD（单指令多数据）

CPU 的向量指令（如 AVX-512、ARM SVE）属于 **SIMD**：一条指令同时作用在一组连续数据上。

```c
// 伪代码：8 个 float 同时加
__m256 a = _mm256_load_ps(x);
__m256 b = _mm256_load_ps(y);
__m256 c = _mm256_add_ps(a, b);   // 一条指令算 8 个
```

特点：**程序员显式地「把数据装进向量」**，硬件对程序员可见。SIMD 宽度固定（如 8/16/32），且不擅长处理「每个元素走不同分支」。

### 1.4.2 SIMT（单指令多线程）

GPU 采用 **SIMT（Single Instruction, Multiple Threads）**：程序员写的是「单个线程的逻辑」，硬件自动把 **32 个线程编成一组（warp，NVIDIA）/ 64 个编成一组（wavefront，AMD）**，让它们 **同步地执行同一条指令**，但每个线程有自己独立的寄存器和程序计数器语义。

```cuda
// CUDA：看起来像串行代码，实际被硬件复制成成千上万线程
__global__ void add(float* a, float* b, float* c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) c[i] = a[i] + b[i];   // 每个线程只算一个元素
}
```

SIMT 与 SIMD 的本质区别：

- **SIMD**：程序员看到向量，硬件收拢数据。
- **SIMT**：程序员看到「独立线程」，硬件在底层把线程聚合成 warp 同步执行。分支由硬件用「谓词 + 掩码」处理（第 3 章详述）。

> SIMT 的好处是 **编程模型友好**——你写的是普通 C，不用手动向量化；代价是分支发散时会「两条分支都执行、用掩码屏蔽不要的结果」，造成算力浪费。

## 1.5 GPU 适合什么、不适合什么

**适合（高并行、同质、可预测访问）：**
- 矩阵/张量运算（深度学习训练与推理的核心）
- 图像/视频处理（滤镜、编码、光栅化）
- 物理仿真、分子动力学、蒙特卡洛
- 密码学哈希、数据库列式扫描

**不适合（强串行、不规则、分支多、随机访存）：**
- 操作系统、调度器、复杂业务控制流
- 递归、链表遍历、随机图搜索
- 频繁的小数据量任务（kernel 启动本身有 ~微秒级开销，得不偿失）

---

## 1.6 本章小结

- GPU 是为 **高吞吐、同质子任务** 而生的处理器，与 CPU 的「低延迟」哲学互补。
- 吞吐的背后是 **延迟隐藏**：用海量就绪线程掩盖内存延迟。
- SIMT = 程序员写单线程逻辑，硬件聚合成 warp 同步执行；它比 SIMD 更友好，但怕分支发散。
- 阿姆达尔定律提醒我们：GPU 的价值上限由「可并行比例」决定。
