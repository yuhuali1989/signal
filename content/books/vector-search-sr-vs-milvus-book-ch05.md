## 5.1 "效果"到底指什么

讨论效果前先统一口径，否则各说各话：

| 指标 | 定义 | 关注者 |
|---|---|---|
| **召回率 Recall@K** | ANN 返回的 K 个里，有几个是真的 Top-K | 工程（决定"漏不漏"） |
| **准确率 / Precision** | 返回结果里真正相关的比例 | 业务 |
| **排序质量（NDCG/MRR）** | 结果排序是否合理 | 搜索/推荐 |
| **端到端业务指标** | 下游任务（如难例挖掘、RAG 正确率）的提升 | 业务方 |

**本书主要用 Recall@K** 作为效果的量化口径。

## 5.2 A 是精确，B 是近似

| | A 暴力内积 | B ANN 索引 |
|---|---|---|
| 召回 | **100%**（就是精确答案） | **90%–99%+**（近似） |
| 原因 | 每条都算了 | 只算剪枝后的候选 |
| 需要调参 | 否 | 是（`nprobe` / `ef_search`） |

**这是 A 唯一的效果优势**：答案精确、无需调参、结果可解释、可复现。

但要注意——**B 的"近似"是可控的**：调大搜索参数可以逼近 100%，代价是变慢。所以本质上是**效果-延时的权衡曲线**，不是"准不准"的二选一。

## 5.3 召回-延时权衡曲线（B 的核心调优）

以 IVF 为例（HNSW 同理，参数名不同）：

| `nprobe`（探几个簇） | 召回 | 延时 |
|---|---|---|
| 小（如 8） | 偏低（~90%） | 快 |
| 中（如 32–64） | 高（~97–99%） | 中 |
| 大（如 256+） | 接近 100% | 慢（接近暴力） |

```text
召回
100% │                          ●  ← nprobe 很大（接近暴力，失去意义）
     │                     ●
 99% │                ●
     │           ●
 95% │      ●
 90% │  ●  ← nprobe 小（最快，但漏得多）
     └────────────────────────→ 延时
```

**实践**：先定**业务可接受的召回下限**（如 95%），再在满足下限的前提下选最快参数。不要盲目追求 100%——那等于放弃索引。

## 5.4 粗排 + 精排：把召回补回来的标准做法

这是工业界补精度的标准套路，**两个方案都支持**：

```text
① 粗排（ANN）：快速召回一个大候选集（如 Top-1000）   ← 快，召回兜底
② 精排（精确）：对这 1000 个算精确内积/距离          ← 只算 1000 个，很便宜
③ 取最终 Top-10
```

**效果**：召回可以补到 **99%+ 甚至接近 100%**，而增加的开销只是"1000 次精确计算"（相对全表微乎其微）。

| 方案 | 支持情况 |
|---|---|
| **A 直查** | 天然就是精确，不需要 |
| **A2（SR 内表 ANN）** | 支持（可用 SQL 组合近似函数 + 精确重排） |
| **B（Milvus）** | 支持（`refine` / rerank，或二次查询） |

**结论**：**只要做了粗排+精排，B 的效果损失可以压到可忽略**。所以"效果"通常**不是**选 A 的充分理由——除非你的业务对 100% 精确有硬性要求（如合规审计场景）。

## 5.5 归一化与度量选择：最常见的效果坑

这是**比 ANN 近似更容易出错**的地方：

| 度量 | 公式 | 注意 |
|---|---|---|
| **内积（IP）** | $q·v$ | **未归一化时受向量模长影响**——长向量的内积天然更大，检索会偏向"模长大的向量"，语义错误 |
| **余弦（Cosine）** | $\frac{q·v}{\|q\|\|v\|}$ | 归一化后 = 内积 |
| **L2 距离** | $\|q-v\|$ | 归一化后与 cosine 单调等价（排序一致） |

**关键规则**：

> 如果 embedding 模型训练/使用时的语义是**余弦相似度**（绝大多数对比学习模型，如 CLIP、SigLIP、bge），那么检索时必须：
> - **要么**用 cosine 度量
> - **要么**入库时对所有向量做 L2 归一化，然后用**内积**（最快）

**不归一化直接用内积 = 效果静默变差**，而且很难排查（结果看起来"还行"但排序不对）。

| 方案 | 度量支持 |
|---|---|
| A / A2（StarRocks） | 支持 L2 / Cosine / **Inner Product**；索引参数里有 `is_vector_normed` 之类的归一化开关（以版本文档为准） |
| B（Milvus） | 支持 IP / Cosine / L2 等；常用 `IP` + 归一化向量 |

## 5.6 过滤能力：带条件的向量检索

真实业务几乎不会"纯向量检索"，都要带条件：

```sql
-- 例：找相似图片，但只看最近 7 天、某个业务线、且未处理的
WHERE collect_date >= '2026-09-11'
  AND biz_line = 'auto'
  AND status = 'pending'
ORDER BY inner_product(query_vec, embedding) DESC
LIMIT 10
```

这里有两种执行策略（StarRocks 3.4+ 会基于代价自动选）：

| 策略 | 做法 | 适合 |
|---|---|---|
| **Pre-Filter** | 先用标量条件缩小候选集，再在候选集上做向量检索 | 过滤选择率高（条件很严） |
| **Post-Filter** | 先扩大向量召回，再从结果里筛标量条件 | 过滤条件宽 / 向量召回便宜 |

| 方案 | 过滤能力 |
|---|---|
| **A / A2（StarRocks）** | ⭐ **强**——SQL 原生 WHERE，优化器自动选 Pre/Post-Filter，还能 join 维表、做聚合/窗口函数 |
| **B（Milvus）** | 支持标量过滤（表达式），但对**复杂 SQL**（join、聚合、子查询）能力弱，通常要回业务库再做 |

## 5.7 混合检索：全文 + 向量 + 标量

更高阶的需求是**多路召回再融合**（RAG、电商搜索常见）：

```text
① 全文召回（BM25 / 倒排）
② 向量召回（ANN）
③ 标量过滤
④ 融合排序（RRF / 加权 / 自定义 Reranker）
```

| 方案 | 混合检索 |
|---|---|
| **A2（StarRocks 内表）** | ⭐ **强**——原生支持全文（BM25、倒排、分词）+ 向量 + 标量统一在 SQL 里，支持 RRF 等融合与自定义 Reranker，**共享统一 SQL、执行框架、缓存与一致性语义** |
| **B（Milvus）** | 向量强，但**全文检索弱**（不是它的设计目标），混合通常要外部拼装（业务层做多路召回 + 融合） |

**如果你要的是"多模态混合检索"**（如图文互搜 + 标签过滤 + 关键词），**StarRocks 内表方案（A2）是更强的选择**；Milvus 适合"纯向量 + 简单标量过滤"。

## 5.8 效果差异的业务含义

对下游任务而言，召回从 100% 掉到 95% 意味着什么？

| 下游场景 | 影响 |
|---|---|
| **相似图片检索 / 以图搜图** | 影响小——用户对"少了几张相似图"不敏感 |
| **难例挖掘 / 主动学习** | 中等——可能漏掉少量边缘样本，但挖掘本身是统计性的 |
| **去重** | 有影响——漏召回 = 重复数据没去掉 |
| **RAG 召回** | 中等——漏掉关键文档会影响生成质量 |
| **合规/审计场景** | **不可接受**——要求精确，只能 A（或 ANN + 精排到 100%） |

**判断方法**：先用 B 的粗排+精排跑一批，对比 A 的精确结果，**统计实际召回率**；再评估这个召回率对下游指标（如训练效果、搜索 CTR）的影响。用数据说话，别拍脑袋。

## 5.9 本章小结

- **效果口径**：主要看 Recall@K。A 是精确（100%），B 是近似（可调）。
- **B 的近似可控**：调 `nprobe`/`ef_search` 在召回与延时间权衡；**粗排+精排**可把召回补到 99%+。
- **归一化是大坑**：语义是余弦就必须归一化（或用 cosine 度量），否则内积偏向长向量，效果静默变差。
- **过滤与混合**：StarRocks（A/A2）**强**——SQL 原生、自动 Pre/Post-Filter、支持全文+向量+标量混合与 RRF 融合；Milvus（B）向量强但复杂 SQL 与全文弱。
- **业务含义**：多数场景 95% 召回可接受；合规/去重场景要精确。
- 结论：**"效果"通常不足以成为选 A 的理由**（粗排+精排能补回），真正的决策依据还是**延时、成本、以及是否需要复杂 SQL/混合检索**。
