# 第 6 章 · 版本控制与协作：ipynb 的 diff 灾难与三个解法

## 5.1 .ipynb 的 diff 灾难

`.ipynb` 是一个 JSON 文件，里面同时装着：**代码 + 输出（含 base64 编码的图片）+ 元数据 + 执行计数（execution_count）**。

后果非常直接：

| 问题 | 现象 |
|---|---|
| **改一行代码，diff 几百行** | 输出混在中间，真正的改动被淹没 |
| **图表里一个像素变了** | 整个 base64 字符串变化 → diff 是一坨不可读的乱码 |
| **execution_count 变动** | 每次运行都产生无意义的 diff 噪声 |
| **合并冲突几乎无法手解** | 两个人都跑过 → JSON 结构冲突 |
| **仓库体积膨胀** | 二进制输出反复累积 |

> 一句很到位的话：一个 notebook 的 diff 不会告诉你「我改了这一行」，它只会告诉你「有个图的某个像素变了」。**于是 notebook 在团队里逐渐沦为没人真正 review 的黑盒。**

## 5.2 三个工具解法（Jupyter 阵营）

| 工具 | 做法 | 优点 | 适用 |
|---|---|---|---|
| **nbstripout** | Git filter，提交时自动剥离输出与 execution_count | ★**最省事**，装一次全队受益 | 只想让 diff 干净 |
| **jupytext** | 为每个 `.ipynb` 配对一个 `.py`（percent 格式，用 `# %%` 分格） | ★**最利于 review**：评审看 `.py`，编辑还在 notebook | 要正经做 Code Review |
| **nbdime** | 内容感知的 diff / merge 工具 | 能看懂 notebook 结构 | 必须直接 diff ipynb 时 |

**团队建议**：**至少选一个，且全队统一**。两个都不用的团队，实际上等于放弃了 notebook 的代码评审。

> 实践中最常见的组合是 **nbstripout（提交即剥离）+ jupytext（配 .py 供评审）**，即所谓「双轨制」：交互在 notebook，版本库里躺着可 diff 的纯文本。

## 5.3 marimo 的 .py：从格式上根治

响应式 notebook（marimo）直接把 notebook 存成**纯 Python 文件**，于是不需要任何过滤器：

| 对比 | `.ipynb` + 工具 | `marimo .py` |
|---|---|---|
| diff 可读性 | 需 nbstripout/jupytext | ★**原生可读** |
| 输出是否入库 | 需剥离 | 不入库（输出是运行产物） |
| 能否 import | 不能（需额外工具） | ★**能**，可被其他 notebook/脚本 import |
| 能否跑 pytest | 需 nbval/testbook | ★**能** |
| 依赖声明 | 靠外部文件 | ★PEP 723 内联在文件头 |

> 这不是「更好一点」，是**省掉一整层工具链**。选 notebook 形态时，这是最实际的加分项之一。

## 5.4 脚本：版本控制的天然赢家

| 维度 | 脚本 |
|---|---|
| diff | ★一行改动就是一行 diff |
| 评审 | ★与生产代码同一套流程、同一套工具 |
| 合并 | 标准三方合并，冲突可手解 |
| 依赖 | 锁文件可评审 |
| 测试 | pytest 原生 |

**脚本在协作上没有短板**——它本来就是生产代码的一等公民。这也是「稳定逻辑应该提升到脚本/模块」的核心理由之一。

## 5.5 HTML：生成物，不该进版本库

| 原则 | 说明 |
|---|---|
| **HTML 是构建产物** | 像 `dist/`、`build/` 一样，**不入库**（或只在发布分支/制品库） |
| **入库的是生成它的源** | Notebook 或脚本 + 数据快照 |
| **可重建优于可保存** | 应该能从源重新生成同一份 HTML，而不是把 HTML 存起来 |

> 常见反模式：把 HTML 报告提交进 Git 当「交付物存档」。正确做法是**存源 + 存构建产物到制品库/对象存储**，并带上运行指纹（第 3.6 节）。

## 5.6 Code Review 体验对比

| | Notebook | 脚本 | HTML |
|---|---|---|---|
| 能评审逻辑 | ⚠️ 依赖工具（jupytext）或格式（marimo） | ★能，标准流程 | ❌ 不能 |
| 能评审结论 | ★能（输出就在旁边） | ⚠️ 需跑一遍看结果 | ⚠️ 只能看结果，看不到过程 |
| 能验证 | ★能重跑 | ★能跑测试 | ❌ 无法验证 |
| 评审成本 | 中～高 | ★低 | 高（只能肉眼看数） |

> 一个反直觉的观察：**Notebook 是唯一能同时评审「逻辑」和「结论」的形态**——评审者能看到代码，也能看到它跑出来的数。脚本评审时，评审者往往要自己跑一遍才知道结果；HTML 评审时，评审者只能选择相信。

## 5.7 协作的其他维度

| 维度 | Notebook | 脚本 | HTML |
|---|---|---|---|
| 叙述与代码共存 | ★**最强**（讲故事的天然载体） | 靠注释/文档 | 靠人工写 |
| 给非技术方看 | 需要平台/导出 | 不可直接看 | ★**最强** |
| 并发编辑 | 部分平台支持 RTC（常被高估） | 标准 Git 流程 | 无此问题 |
| 评论讨论 | 平台内或导出后另说 | PR 评论 | 需外部工具 |

> **RTC（实时协同编辑）常被高估**：多数分析场景是「一个人写、多人看」，用 Git + PR + 导出分享就够了。真正需要多人同时改一份 notebook 的场景很少，不要为它做过度设计。

## 5.8 本章要点

- ★**`.ipynb` 的 diff 灾难**：base64 输出 + 执行计数 → 改一行 diff 几百行、冲突难解、评审沦为形式。
- 三个工具：**nbstripout**（最省事，提交剥离）／**jupytext**（配 `.py` 供评审，最利于 review）／**nbdime**（内容感知 diff）。**全队必须统一选一个。**
- **marimo 的 `.py` 从格式上根治**：原生可 diff、可 import、可 pytest、PEP 723 内联依赖——省掉一整层工具。
- **脚本是版本控制的天然赢家**；**HTML 是生成物，不该进版本库**（存源 + 制品库 + 运行指纹）。
- ★**Notebook 是唯一能同时评审逻辑与结论的形态**——这是它相对脚本的隐藏优势。
- **RTC 协同常被高估**，多数场景 Git + PR + 导出分享足够。
