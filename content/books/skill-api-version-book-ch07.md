## 7.1 监控什么：版本漂移的核心指标

版本兼容不是上线那一刻的事，是持续状态。以下指标应当进监控：

| 指标 | 含义 | 为什么重要 |
|---|---|---|
| **① 版本分布** | 各 Skill / 客户端实际使用的 API 版本占比 | 知道谁还没迁移 |
| **② 版本不符率** | preflight 判定「不兼容」的比例 | 突增 = 服务端变了或配置漂移 |
| **③ fallback 命中率** | ★走字段兜底路径的比例 | **版本漂移最灵敏的信号**（第 6.2 节） |
| **④ 降级率** | 以 `degraded` 状态完成的调用占比 | 业务方要知道「结果范围缩水了」 |
| **⑤ schema 漂移告警数** | `SchemaDriftError` 触发次数 | 直接对应第 1 章静默失败被成功拦截的次数 |
| **⑥ 探测失败率** | preflight 探测失败比例 | 探测层自身故障 |
| **⑦ 旧版本流量** | 仍在用已废弃版本的调用量 | 决定能否按时下线 |

**③ fallback 命中率值得单独强调**：它平时应该是 0。一旦从 0 变成非 0，说明「你声明的版本」与「实际服务的版本/形状」已经不一致了——**这往往比任何报错都早**。

**告警设计原则**：

- ①②③⑤ 做**突变告警**（环比突增）
- ④ 做**水位告警**（持续高位说明能力长期缺失，应评估升级）
- ⑦ 做**趋势告警**（临近 sunset 日期仍未清零，要人工介入）

## 7.2 契约测试：把「版本对应」变成自动化断言

单元测试验证的是「我的代码对不对」，**契约测试**验证的是「我和对面还契不契」。

| | 单元测试 | 契约测试（Consumer-Driven） |
|---|---|---|
| 验证对象 | 我的逻辑 | **我依赖的契约是否还成立** |
| 依据 | 我的假设 | **我实际用到**的字段与能力 |
| 谁维护期望 | 开发者 | ★**消费方**维护，推送给提供方 |
| 典型工具 | 各语言 test fw | Pact（最主流）、Spring Cloud Contract |

**消费者驱动的核心流程**：

```
① 消费方（Skill）在测试里声明：我调用 X，期望返回里有字段 a、b，类型分别是什么
        ↓
② 生成「契约文件」（pact）
        ↓
③ 提供方在 CI 里拿这份契约回放，验证自己的服务是否仍满足
        ↓
④ 不满足 → 提供方 CI 直接红 → 破坏性变更在发布前被拦住
```

**为什么这比文档强**：文档会过期，契约文件是**可执行、会在 CI 里红**的。它把「别破坏我」从一句请求变成了流水线上的一道闸。

**适配版本场景的做法**：

- 每个**活跃 API 版本**各生成一份契约，在提供方 CI 里逐份回放
- 提供方要加破坏性变更时，**旧版本契约必须仍然通过**（因为它承诺支持旧版）
- 新版本契约通过 + 旧版本契约通过 = 可以发布新版

## 7.3 Sunset / Deprecation 的自动告警（成本极低，收益极高）

第 2.6 节讲过标准信号，这里讲工程落地：

```
1. 在响应拦截器里统一抓取：Deprecation 头、Sunset 头、以及各家自定义的告警头
2. 落到一个「版本生命周期」表里：api_name / version / deprecated_at / sunset_at
3. 告警规则：
   - 出现 Sunset 头 → 立即告警（说明版本已进入下线倒计时）
   - sunset_at - now < 90 天 且 该版本仍有流量 → 升级为 P1，通知负责人
   - sunset_at - now < 30 天 且 仍有流量 → 每日提醒
4. 与第 7.1 节的「旧版本流量」指标联动：流量不清零就不允许静默到期
```

> 这一整套的成本大概就是几十行拦截器代码。**而它的收益是：把「某天突然全量 410」变成「提前 3 个月知道，从容迁移」。** 这是所有版本治理工作里投入产出比最高的一项。

## 7.4 兼容性看板：一张表说清全局

建议维护一张**实时**看板（不是静态文档），字段：

| 列 | 内容 |
|---|---|
| API / 服务 | 名称 |
| 当前默认版本 | 服务端默认（Skill 不该依赖，但要盯着） |
| 支持的版本列表 | 从探测结果汇总 |
| 各版本流量占比 | 来自监控 |
| 各版本状态 | active / deprecated / sunset-scheduled / retired |
| sunset 日期 | 来自 Sunset 头 |
| 依赖它的 Skill | 反向索引（★最关键：改 API 时知道要通知谁） |
| 兼容状态 | ✅ / ⚠ 降级 / ❌ 不兼容 |

★**「反向索引」这一列是治理的地基**：没有它，服务端做破坏性变更时根本不知道会影响谁——这也是第 1.3 节说「对齐责任在消费方」的现实原因（因为提供方常常不知道消费方是谁）。

## 7.5 废弃流程：时间表与职责

综合业界实践（Public APIs、WSO2、GitHub 承诺）给出可执行模板：

| 阶段 | 时间点 | 提供方动作 | 消费方动作 |
|---|---|---|---|
| **宣布** | Day 0 | 发 changelog + 邮件 + 加 `Deprecation` 头 + 发迁移指南 | 记录待办、评估影响 |
| **提醒** | +3～6 个月 | 对仍在用的活跃调用方定向提醒 | 完成适配开发 |
| **软下线** | +6 个月 | 响应内加强警告、可加轻微延迟 | 完成灰度切换 |
| **硬下线** | +12 个月 | 返回 `410 Gone` + 迁移链接 | 已迁移（未迁移则故障） |
| **退役** | +18 个月 | 代码库移除 | 移除旧适配器 |

**参考承诺**：业界普遍 **6～12 个月**为公开 API 废弃下限；**GitHub 承诺新版发布后旧版至少支持 24 个月**；MCP 规范则明确「2026-07-28 废弃的特性和最早 2027-07-28 之后的第一个修订版起才可被移除」——**给出明确的可计算日期，是最好的沟通方式**。

**三条纪律**：

1. **时间点是日期，不是「近期」**。「近期下线」等于没说。
2. **不要在流量清零的瞬间就下线**。长尾任务（季度批处理）会「本周无流量」然后在季末跑一次并失败——**按公布的日期走，而不是按当前流量走**。
3. **硬下线时返回明确错误 + 迁移链接**，不要返回一个「看起来成功但内容不同」的响应。

## 7.6 组织级治理：让规则自动执行

| 手段 | 做法 |
|---|---|
| **规范即代码** | 用 Spectral 之类的 linter 把版本约定（必须有版本号、必须有 Deprecation 策略等）写成规则，在 CI 里强制 |
| **生命周期状态机** | API 有明确状态：Created → Pre-Released → Published → Deprecated → Retired；Deprecated 状态**新订阅关闭、老订阅保留** |
| **合规看板** | 规则违规按 error/warn/info 分级展示，违反即通知 |
| **版本变更评审** | 破坏性变更必须过评审，且评审清单包含「影响哪些 Skill」（依赖第 7.4 节反向索引） |

## 7.7 本章要点

- 核心监控指标：版本分布、不兼容率、★**fallback 命中率**（最灵敏）、降级率、schema 漂移数、探测失败率、旧版本流量。
- **契约测试**（Pact 等消费者驱动）把「别破坏我」变成 CI 里会红的闸；每个活跃版本各一份契约，旧版契约必须继续通过。
- ★**Sunset / Deprecation 头自动告警是投入产出比最高的一项**——几十行代码换「提前三个月知道」。
- 兼容性看板必须有**反向索引**（哪个 Skill 依赖哪个 API），否则破坏性变更无法评估影响面。
- 废弃时间表用**确切日期**，按日期走而非按当前流量走；硬下线返回 `410 + 迁移链接`。
- 组织级：规范写成 linter 规则进 CI，API 走生命周期状态机，破坏性变更强制评审。
