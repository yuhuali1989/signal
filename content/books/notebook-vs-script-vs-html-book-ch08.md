## 8.1 ★ 标准管线：三者是接力，不是三选一

```
① 探索（Notebook）
   在台面上试配方：读采样、画图、试特征、讲清楚「为什么」
   产物：可复现的 notebook + 结论
        ↓（确认有效、需要重复执行）
② 固化（Python 脚本 / 模块）
   把逻辑提升为 .py：加单测、参数化、接 CI、可调度
   产物：可测试、可部署的脚本与库
        ↓（需要给人看/给人用）
③ 交付（HTML / App）
   静态报告或交互 App，附运行指纹，可回溯到源
   产物：一个链接
```

| 阶段 | 形态 | 关键动作 | 常见错误 |
|---|---|---|---|
| ① 探索 | Notebook | 采样、下推、断言 cell、Restart & Run All | 直接把探索产物当交付物 |
| ② 固化 | 脚本 | 提升逻辑、加测试、参数化 | 跳过，让 notebook 直接上 cron |
| ③ 交付 | HTML/App | 附源与指纹、控制权限 | 只发 HTML，答不出「哪来的」 |

> ★**最常见的错误不是选错了某一个，而是跳过了中间那一棒**——让 notebook 直接承担生产任务，或者直接产出没有源的 HTML。

## 8.2 六个信号：该从 Notebook 转脚本了

| # | 信号 | 说明 |
|---|---|---|
| 1 | **开始被定时执行** | ★最强信号。挂了会叫醒人的东西不该是 notebook |
| 2 | **需要换个参数重复跑** | 该参数化 → 脚本更顺手 |
| 3 | **同一段代码被复制到第二个 notebook** | 逻辑属于 `.py` 模块 |
| 4 | **需要被其他代码 import** | notebook 不该是依赖源 |
| 5 | **需要单元测试 / 要进 CI** | 脚本天然支持 |
| 6 | **别人开始依赖它的输出** | 有依赖就要有契约与测试 |

> 一句话记忆：**「一旦它需要准点运行、被人依赖、或要被 import，它就不是 notebook 了。」**

## 8.3 什么时候直接产出 HTML（不做 app）

| 场景 | 理由 |
|---|---|
| 结论已确定，只需呈现 | 不需要重算 |
| 面向外部/离线分发（邮件、存档） | 一个文件走天下 |
| 一次性材料，不需要更新 | 省掉后端成本 |
| 交互只需筛选/排序（L2 足够） | 前端 JS 就够，零后端 |

**前提**：★**必须能回答「它是从哪个源、哪份数据算出来的」**（源链接/源 commit + 数据快照时间 + 生成时间）。

## 8.4 什么时候升级为 App（而不是静态 HTML）

| 判据 | 升级 |
|---|---|
| 业务方需要**自己换条件并看到重算结果**（L1） | ✅ 升级 |
| 需要看**最新数据**（不能是快照） | ✅ 升级 |
| 需要连接内部数据源做查询 | ✅ 升级 |
| 只是换个筛选角度看一下 | ❌ 不必，L2 就够 |
| 一次性汇报 | ❌ 不必 |

> 成本提醒：App 需要**后端常驻 + 运维**。选型时要问：**这个交互值不值得养一个后端？**

## 8.5 决策树（一张图选形态）

```
这份工作是什么性质？
  │
  ├─ 还在探索、要看中间结果、要讲"为什么"
  │     └→ ★ Notebook
  │           若会被定时执行/被 import → 逻辑提升到脚本（8.2 六信号）
  │
  ├─ 已经确定、要准点跑、要可测试、要被依赖
  │     └→ ★ Python 脚本（+ 单测 + CI + 调度）
  │
  └─ 要给人看/给人用
        ├─ 只看结论、一次性、离线分发     → ★ HTML（附源与指纹）
        ├─ 要前端筛/排/缩放              → HTML + JS 图表库
        └─ ★要换条件重算 / 看最新数据     → App（marimo run / Streamlit）
```

## 8.6 反模式清单

| # | 反模式 | 后果 | 正解 |
|---|---|---|---|
| 1 | **让 notebook 挂 cron** | 带漂亮 UI 的技术债，故障难排查 | 转脚本 |
| 2 | **只交付 HTML，没有源** | 答不出数字哪来的，不可信 | 附源与运行指纹 |
| 3 | **让 AI 直接生成 HTML 报告** | ★数字可能从未被算过 | 在 notebook/脚本里跑出来再渲染 |
| 4 | **把全表 `SELECT *` 拉进 notebook** | 内存爆、慢 | 下推聚合 |
| 5 | **凭证写进 notebook** | 泄露 | 平台/环境变量注入 |
| 6 | **`.ipynb` 不做剥离就入库** | diff 不可读、评审形同虚设 | nbstripout / jupytext / 用 marimo |
| 7 | **逻辑只存在于 notebook 里** | 无法复用、无法测试 | 提升到 `.py` 模块 |
| 8 | **一份 notebook 几千行** | 性能与可维护性崩塌 | 拆分 + 模块化 |
| 9 | **HTML 里嵌全量明细** | 页面膨胀打不开 | 只嵌聚合结果 |
| 10 | **把 HTML 当存档提交进 Git** | 仓库膨胀 | 存源，产物进制品库 |
| 11 | **分享前不 Restart & Run All** | 输出与代码不一致 | 纪律 + CI 闸门 |
| 12 | **为「多人同时编辑」过度设计 RTC** | 需求被高估，成本高 | Git + PR + 导出分享 |

## 8.7 全书对照总表（收束）

| 维度 | **Notebook** | **Python 脚本** | **HTML** |
|---|---|---|---|
| 定位 | 探索（厨房台面） | 固化（工厂产线） | 交付（成品橱窗） |
| 执行 | 分段/响应式 | 一次性全量 | 不执行 |
| 状态 | 有（响应式则无隐患） | 无残留 | 无 |
| 可复现 | 中（marimo 强） | ★最强 | ★最弱 |
| 交互 | ★L1 真重算 | 仅启动参数 | L2 过滤 |
| 版本控制 | .ipynb 差 / .py 好 | ★最好 | 生成物，不入库 |
| 测试与 CI | 需配置（nbconvert） | ★原生 | 无 |
| 参数化 | papermill | ★argparse | 无 |
| 调度 | ⚠️ 不推荐 | ★是 | 否 |
| 数据连接 | ★能（应下推） | ★能（主力） | 否 |
| 分发 | 需环境/平台 | 需环境 | ★一个链接 |
| 评审 | ★逻辑+结论都能看 | 逻辑好评，结论要跑 | 只能看结论 |
| AI 可信度 | ★最高（跑过才算） | 高（可跑验证） | ★最低（无法自证） |

## 8.8 全书二十条结论

**定位**
1. 三者不是同类：**Notebook=探索 / 脚本=固化 / HTML=交付**，是一条管线上的三棒。
2. 绝大多数「谁更好」的争论，都是跨层比较造成的。
3. Notebook 是厨房台面不是工厂产线；HTML 是橱窗不是厨房。
4. 实验记录本（Notebook）与 SOP（脚本）**都要有**，不能互相替代。

**执行与复现**
5. 状态是根本分野：Notebook 有状态、脚本一次性、HTML 无执行。
6. ★hidden state 导致约 96% 公开 notebook 不可复现。
7. 脚本可复现性最强，是因为**它没给人犯错的空间**。
8. ★**AI 时代：能不能重跑 = 能不能相信**；HTML 无法自证，风险最高。
9. `nbconvert --execute` 接 CI，是性价比最高的可复现手段。

**交互**
10. 交互三层级：**L1 真重算 / L2 前端过滤 / L0 无**。
11. ★判据：这个交互能不能算出数据里原本没有的东西？
12. App = HTML 的外壳 + Notebook 的内核，是 Notebook 家族对纯 HTML 的最大反超。
13. 选型要问：这个交互值不值得养一个后端？

**工程**
14. ★**.ipynb 的 diff 灾难**是 notebook 协作的头号障碍；nbstripout / jupytext / nbdime 至少选一个。
15. marimo 的 `.py` 从格式上根治：可 diff、可 import、可 pytest。
16. ★**notebook 是库代码的消费者，不是源码**；被复制/需测试/要 import = 提升为 `.py`。
17. ★**「一旦它需要准点运行、被人依赖、或要被 import，它就不是 notebook 了」**。
18. 数据工程的分水岭是**下推还是拉进内存**，与用不用 notebook 无关。
19. ★**凭证绝不写进 notebook**；HTML 一旦发出就收不回。
20. **HTML 不是原罪，但不能是唯一产物**——必须能回答「从哪来」。

## 8.9 本章要点

- ★标准管线：**Notebook 探索 → 脚本固化 → HTML/App 交付**；最常见错误是**跳过中间那一棒**。
- 转脚本六信号：**定时执行 / 换参重跑 / 被复制 / 被 import / 要测试 / 被人依赖**。
- 直接 HTML 的前提：**能回答从哪来**（源 + 数据快照 + 生成时间）；App 的前提：**需要真重算或看最新数据**。
- 决策树与 12 条反模式对照表（**反模式表比正向建议更好用**）。
- 全书对照总表按 13 个维度收束三者差异。
- 二十条结论按「定位 → 执行与复现 → 交互 → 工程」四层归纳。
