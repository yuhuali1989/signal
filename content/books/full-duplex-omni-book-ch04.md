# 第 4 章 · 视频怎么 embedding：不查表、186MB 压成 64 个向量

`t=3200ms` 摄像头送来一帧 `frame[3, 448, 448]`。这一章把它变成 `pos 1..64` 那 64 个 4096 维向量。**整条链路里不会出现 `E`**。

## 4.1 先回答「有没有词表」

| 问题 | 答案 |
|---|---|
| 视频 token 有 ID 吗 | 理解侧**没有** |
| 要查 `E` 吗 | **不查** |
| 那它是什么 | 一个 `[4096]` 浮点向量，由 `Conv2d` + `MLP` 从像素算出来 |
| 为什么叫 token | 只因为它在序列里占一个位置 |
| 什么时候才有 ID | 生成画面时（第 8 章），走 `IMAGE` 区间采样 |

原因在第 1 章那句判断：词表是「写」侧概念。摄像头画面只用来回答「这个是什么」，不需要被采样出来，量化成 8192 个码字是**纯亏**——损失细节、多训一个码本、还让主干去学一个本来不需要的离散分布。

具体到例子：金属杯那道镜面高光恰恰是判断材质的关键，VQ 量化最容易把它抹成普通灰块。**只在必须生成时才量化**，这是方案 B 的核心取舍。

## 4.2 三层压缩的精确演算

一秒 1080p@30fps 的原始量：

```
1920 × 1080 × 3 × 30 = 1.866 亿个 uint8 标量 ≈ 186 MB / 秒
```

**① 空间压缩**

```python
frame = resize(frame, (448, 448))        # [3, 448, 448]
patch = Conv2d(3, 1152, kernel_size=14, stride=14)(frame)
# 448 / 14 = 32 → 32×32 = 1024 个 patch，每个 1152 维
x = pixel_shuffle_2x2(patch)             # [256, 1152]  1024 → 256
```

`Conv2d(3, d, k=patch, s=patch)` 这一个算子同时完成「切 patch」和「线性投影」。它的输出不是 ID，是浮点数；词表的等价物是「所有可能的 patch 组合」，但我们不枚举它，只学一个线性函数处理任意 patch。

**② 时间压缩**

30fps 不会全进模型。三种做法：

| 做法 | 本例取值 | 说明 |
|---|---|---|
| 关键帧采样 | 1~2 fps | 全双工里 80ms 一片，画面没变化就整片跳过 |
| tubelet | 2~4 帧卷成一个时空块 | `Conv3d` 一次吃多帧 |
| 3D 因果 VAE | 时间下采样 4× | **生成侧**用，81 帧 → 21 个 latent 帧 |

本例 `t=3200ms` 这一片取 1 帧；`t=3280ms` 画面没变，视觉片**整片缺席**。这正是第 5 章必须用绝对时间 ID 的原因：跳帧后「第 5 个视觉 token」不再对应「第 5 个音频片」。

**③ 语义 / 预算压缩**

```python
class Resampler(nn.Module):
    def __init__(self, d=1152, out_d=4096, n_query=64):
        super().__init__()
        self.queries = nn.Parameter(torch.randn(64, d))
        self.cross   = nn.MultiheadAttention(d, 8, batch_first=True)
        self.proj    = nn.Linear(d, out_d)
    def forward(self, patch_feat):        # [256, 1152]
        q = self.queries.unsqueeze(0)     # [1, 64, 1152]
        z, _ = self.cross(q, patch_feat.unsqueeze(0), patch_feat.unsqueeze(0))
        return self.proj(z.squeeze(0))    # [64, 4096]
```

64 个可学习 query 做 cross-attention，把任意数量的 patch 压成**固定 64 个槽位**。这一步的真正价值不是压缩率，是**预算固定**：每片进主干的视觉 token 数恒定，延迟可算、KV cache 可规划、调度有确定性。

## 4.3 压缩前后对账

| 阶段 | 形态 | 标量数 |
|---|---|---|
| 原始 1 秒 1080p@30fps | `uint8` 像素 | 1.866 亿 |
| 缩放 + patch 14 | `1024 × 1152` fp | 118 万 / 帧 |
| pixel shuffle 2×2 | `256 × 1152` fp | 29.5 万 / 帧 |
| 采样到 1 fps | 同上 × 1 帧 | 29.5 万 / 秒 |
| resampler 64 query | `64 × 4096` bf16 | 26.2 万 / 秒 |

按标量数算约 **360×** 压缩；按字节算 `186MB → 64×4096×2B ≈ 512KB`，同样约 360 倍。全双工能跑起来，全靠这笔账。

## 4.4 8×8 网格与 `pos 29`

64 个 query 排成 8×8，每个带 `(h, w)` 空间坐标：

```
pos_in_visual = h * 8 + w
(h=3, w=5) → 29  → 序列里 pos 30（前面有 BOV）
```

为简洁，全书把这个槽位记作 `pos29`（视觉段内编号）。训练中它稳定对应画面中央偏右的区域，本例正好覆盖杯身金属高光。第 6 章会看到 `Q(pos86「这个」)` 对它的注意力权重从 0.02 长到 0.31。

**为什么它会被注意到**：一是 `(h,w)` 编码让它带空间身份，二是同一 `t=3200` 让 TMRoPE 旋转角接近，三是训练数据里大量「指代词 + 视线/手势所指物体」的共现，让模型学会把「这个」指向画面里显著、被举起的物体。

## 4.5 静态背景持久表示（全双工特有）

摄像头大部分时间画面不变。每 80ms 重算一遍 1024 个 patch 是巨大浪费，实践做法：

```python
# 每片先算一个廉价变化分数
delta = 1 - ssim(frame_t, frame_prev)     # SSIM 结构相似度
if delta < 0.02:
    visual_tokens = cached_scene_state    # 复用上片，本片不新增视觉 token
else:
    changed_mask = build_motion_mask(frame_t, frame_prev)
    patches = patchify(frame_t, mask=changed_mask)   # 只编码变化区域
    visual_tokens = resampler(patches)
    cached_scene_state = merge(cached_scene_state, visual_tokens)
```

要点：

- **静态背景做持久表示**，只发增量；
- token 数随「信息量」增长，不随时长或帧率增长（GRT / Token Dynamics 这类做法能压到原始 token 的 0.07% 而几乎不掉精度）；
- 但**预算仍需固定上限**：动态速率不能变成变长序列，否则延迟不可预测。做法是「固定 64 个槽位，没变化时用持久状态填充或整片跳过」。

这跟语音形成鲜明对照：语音是「等间隔必达」，视频是「预算内选择性到达」。所以视频必须自带时间戳，语音可以靠片序号。

## 4.6 因果性：双向 ViT 是隐形杀手

SigLIP / CLIP 视觉编码器默认全局双向注意力。直接拿来做流式输入，会**看到未来帧**——训练时指标漂亮，部署时信息泄漏。

```python
# 必须改成 chunk-causal：块内双向、块间只看过去
attn_mask = build_chunk_causal_mask(t_ids)   # 片 t 屏蔽片 t+1 及之后
x = vit(frame, attn_mask=attn_mask)
```

主干侧配持久 KV cache + 分块 prefill：新片只把增量 append 进 cache，不重算历史。长会话再叠滑窗、压缩记忆、分层状态。

## 4.7 生成侧才需要 3D 因果 VAE（预告第 8 章）

如果这一路是要**输出**视频，链路完全不同：

```
视频帧 [T, 3, H, W]
  → 3D 因果 VAE：空间 8×8 下采样、时间 4× 下采样、latent 16 通道
  → [T/4, H/8, W/8, 16] 连续 latent
  → 可选 VQ 量化成 ID（走 IMAGE 区间）
  → DiT / 流匹配生成
```

时间维必须因果卷积，否则 latent 里混入未来帧信息，没法流式生成。理解侧（本章）用连续 embedding，生成侧（第 8 章）才量化——**同一模态，读写两套表示**，这是全书反复出现的模式。

## 4.8 五个必踩的坑

1. **给理解侧加 VQ**：白丢细节、白训码本，还让主干学一个不需要的离散分布。
2. **均匀 25fps 全帧进主干**：显存、上下文、首包延迟三堵墙一起撞。
3. **直接用双向 ViT**：看未来帧，流式部署静默失效。
4. **时间片太长**：>300ms 会把「抬手—停顿—开口」压成一块，因果顺序糊掉；太短则序列暴涨。取语音片 80ms 的整数倍最省事。
5. **忘了加模态类型 embedding**：理解侧音视频都是连续向量、同一个 4096 维，不加 `type_emb` 主干分不清这 64 个槽位是画还是声。

## 4.9 本章小结

- 视频理解侧没有 ID、不查表，`Conv2d(k=s=14)` 直接投影出浮点向量。
- 三层压缩：空间（1024→256 patch）、时间（30fps→1~2fps / 跳过）、语义（resampler 固定 64 query），约 360×。
- `pos29 = (h=3,w=5)` 覆盖金属高光，是指代消解的目标格子。
- 静态背景持久表示 + 只发增量；但每片预算要固定，否则延迟不可预测。
- 双向 ViT 必须改 chunk-causal；生成侧才用 3D 因果 VAE 与量化。

## 4.10 真实产品校准：视频到底该多稀

Higgs Realtime Duplex 的官方数字给了一个很反直觉的答案：**摄像头每 6 个 160ms chunk 才采 1 帧**（约 960ms 一帧、约 1 fps），每帧约 **12 个 token**。折算下来视频只占约 12.5 token/s，而本书示意是每片 64 个视觉 token（800 token/s）——差 64 倍。

| | 本书示意 | Higgs 真实 |
|---|---|---|
| 时间片 | 80 ms | 160 ms |
| 视觉采样 | 每片 1 帧 | 每 6 片 1 帧（约 1 fps） |
| 每帧 token | 64 | 约 12 |
| 静音期间 | 画面没变化就跳过视觉片 | **视频帧继续流入**，模型从不停止看 |

最后一行是本书判断需要收紧的地方：本章 4.5 写「画面没变化就整片跳过」，Higgs 的做法是**静音也作为一个 chunk 编码，且静音期间视频帧照常流入**。两者不冲突（一个按视觉变化跳、一个按音频静音跳），但合起来给出更完整的规则：**视觉是否跳过只看画面变化，与用户有没有在说话无关**。理由是用户不说话不等于没信息——他在看白板、在皱眉、在把杯子转个面，这些都是后续回答的依据；若为了省算力把「静音」当作跳过视觉片的信号，模型会在用户停顿的那一秒「瞎掉」。

**保留的部分**：不查表、连续投影、chunk-causal、固定预算这四条结论都成立，只是预算比本书示意小得多。真实工程的第一原则是「把每条流的 token 数压到不能再压」，而不是「尽量多给视觉信息」。
