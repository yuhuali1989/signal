## 引子：同一个品类，四家同时出手

2026 年 10 月的第一周，几条消息指向同一个方向：

| 时间 | 事件 |
|---|---|
| 10-01 | **Cloudflare** 发布 Clef（27B，基于 Qwen3.8-27B，64K 上下文，多模态）与 Clef-flash（9B），开放权重 |
| 10-01 | **AWS** 发布 Strands Decider 2B（Qwen3.5-2B 衍生，**移除文本生成头**），单张 RTX 3090 上决策中位延迟约 115ms |
| 10-06 | **OpenAI** 推出 **Decisions API** 公测，称决策速度最高比 Responses API 调 GPT-6 Luna **快 10 倍** |
| 10-06 | **Musubi** 开源 **PolicyLM-1.7B**，约 50ms 内把自然语言政策应用到消息上，**政策变更无需重训** |
| 10-06 | **Perplexity** 把 Decision API 价格减半至每百万输入 token **2 美分** |

独立的创业公司、云厂商、头部实验室同时涌进同一个细分——这通常意味着**一个新类别正在成形**。

## 1. 决策模型与生成模型，根本不是一回事

| | 生成模型 | **决策模型** |
|---|---|---|
| 输出 | 自由文本（token 逐个生成） | ★**有界结构化输出**：从固定候选里选一个 |
| 附带 | — | ★**校准后的置信度 / 概率** |
| 延迟 | 随输出长度增长 | ★**固定、毫秒级** |
| 可预测性 | 低（同样的输入可能不同输出） | ★高（同输入基本同输出） |
| 成本 | 高（尤其长输出） | ★低一个量级 |

**一句话定义**：

> **决策模型不回答「是什么」，而回答「选哪个」——并且告诉你它有多确定。**

AWS 的 Strands Decider 2B 把**文本生成头直接移除**，是这条路线最直白的表达：既然只做裁决，就别留着生成的包袱。

## 2. 为什么是现在：三个成本压力同时到位

| 压力 | 说明 |
|---|---|
| **① 成本错配** | 大量生产任务其实只是「分类 / 路由 / 打标」，却用全尺寸 LLM 去做，成本高出 **10–100 倍** |
| **② 延迟预算** | Agent 的每一步如果要等几百毫秒的生成，长链条就不可用；决策需要**毫秒级** |
| **③ 可预测性** | 生产系统要求「同样输入同样输出」，生成模型的随机性在这里是负债不是资产 |

> ★**这是 LLM 应用成熟的分水岭**：当大家开始把「思考」和「选择」拆开，说明已经在按工程约束而非模型能力来设计系统了。

## 3. 玩家与定位一览

| 产品 | 规模 / 形态 | 特点 |
|---|---|---|
| **Cloudflare Clef / Clef-flash** | 27B / 9B，开放权重 | 多模态（27B，64K 上下文），跑在 Workers AI，配 RL 微调平台；官方称在边缘 GPU 上精度与延迟均优于闭源 Jev |
| **AWS Strands Decider 2B** | 2B，**移除文本生成头** | 极轻量，RTX 3090 上中位约 115ms |
| **OpenAI Decisions API** | 基于 gpt-6-luna | ★快 10 倍；支持并行评估多个问题、语音控制集成、HIPAA 合规数据保护；输入 $0.10/百万 token |
| **Musubi PolicyLM-1.7B** | 1.7B，开放权重 | ★**自然语言写政策 → 直接应用，改政策不用重训**；约 50ms |
| **Scale Jev**（对照） | 闭源决策模型 | 这一类别的早期闭源代表 |

**Cloudflare 与 AWS 同时选择「开放权重 + 边缘可跑」**，说明竞争焦点不只是精度，而是**能不能部署在你自己的边上**。

## 4. 典型用法（OpenAI 官方列出的四类 + 两类补充）

| 用法 | 说明 |
|---|---|
| **① 路由** | 把请求分派到正确的模型 / 工具 / 智能体 —— ★**最典型的成本优化点** |
| **② 打标与评分** | 把规模化输入转成标签、分数（内容审核、风险分级、意图识别） |
| **③ 界面操作** | 从截图中「选按钮」——GUI Agent 的低成本替代方案 |
| **④ 风险标记** | 标记有风险的工具调用，交给人工或阻断 |
| **⑤ 缓存/命中判定** | 语义缓存是否命中、检索是否足够 |
| **⑥ 兜底判断** | 上一环节结果是否可信、是否需要降级 |

> ★**第 ① 项（路由）几乎是每个多模型系统的必答题**：用大模型去猜「该用哪个模型」，本身就要花一次大模型的钱——决策模型把这一刀砍到可忽略。

## 5. 工程落地建议

| 建议 | 说明 |
|---|---|
| **在架构里预留「决策位」** | 别把路由/判定硬编码进提示词，留给专用决策模型 |
| **用置信度做分流** | 高置信直接执行、中置信加校验、低置信走保守路径 —— ★这与物理 AI 的「降级兜底」是同一套思想 |
| **把决策当独立可观测单元** | 记录决策分布、置信度分布、低置信占比，作为系统健康度指标 |
| **评估要按任务族分别算** | 决策模型的「参差能力」同样存在（见第 68 轮新增论文 *Where Does Jagged Competence Come From?*） |
| **与生成模型互备** | 决策模型不可用 → 降级到大模型（慢但可用），保证可用性 |

## 6. 局限与风险

| 风险 | 说明 |
|---|---|
| **置信度未必校准** | 「说自己 90% 确定」不等于真的 90% 正确；★上线前必须在自有数据上做校准检验 |
| **有界不等于安全** | 决策模型仍可能被对抗输入影响；高风险决策应保留人工环节 |
| **责任边界** | 自动裁决错了谁负责？★审核/风控类场景要留痕、可申诉 |
| **供应商锁定** | 闭源决策 API 若停服，与嵌入模型同理（参见 Simon Willison 关于嵌入模型必须开放权重的论点） |

> ★**最实用的一条**：**把决策模型当成一个「可观测、可校准、可降级」的组件，而不是一个更便宜的 LLM。**

## 7. 小结

- **决策模型 = 有界结构化输出 + 校准置信度 + 毫秒级延迟**，与生成模型是两类东西。
- 2026 年 10 月第一周，Cloudflare、AWS、OpenAI、Musubi 同时出手，**这个品类已经独立成形**。
- 驱动力是**成本（10–100 倍差）、延迟（毫秒级）、可预测性**三重压力。
- 最大价值点是**路由**——把「用哪个模型」这一刀的开销压到可忽略。
- 落地铁律：**预留决策位、用置信度分流、独立可观测、与生成模型互备**。
- 风险在**置信度校准**与**责任边界**；高风险场景必须留痕与人工兜底。
