## 4.1 三种「交互」，本质完全不同

很多人把「能拖滑块」都叫交互，但这三种交互的能力边界差了一个量级：

| 层级 | 交互发生了什么 | 代表 |
|---|---|---|
| **L1：触发真实重算** | 用户操作 → **后端/kernel 重新执行代码** → 产生新结果 | Notebook 控件、`marimo run`、Streamlit、Shiny |
| **L2：对已有数据过滤** | 用户操作 → **前端 JS 筛已有数据** → 换一种展示 | 带 ECharts/D3 的 HTML 报告 |
| **L0：无交互** | 用户只能看 | 静态 HTML、PDF、脚本输出 |

★**核心判据**：**这个交互，能不能算出「数据里原本没有的东西」？**

- 能 → L1（真重算，需要后端）
- 不能 → L2（只是换角度看同一份数据，纯前端）
- 都不行 → L0

## 4.2 Notebook 的交互：控件触发 kernel 真跑

```
用户拖动滑块（mo.ui.slider）
   → 新值送回 Python kernel
   → 响应式重跑依赖该控件的所有 cell
   → 图表、表格、结论全部按新值重算
```

| 特点 | 说明 |
|---|---|
| **是真的重算** | 不是在已有结果里挑，而是真的重新查询/重新计算 |
| **可以碰到数据源** | 拖个日期 → 重新查数仓 → 拿新数据 |
| **输出是一致的** | 因为响应式，所有依赖它的输出同步更新，不会出现「图变了但数字没变」 |
| **代价** | 需要后端常驻、有计算成本 |

## 4.3 HTML 的交互：只能给已有数据换角度

纯 HTML + JS（ECharts、D3、Plotly）能做出非常漂亮的交互，但它的能力边界很明确：

| 能做 | 不能做 |
|---|---|
| 筛选、排序、缩放、切换维度 | 重新查询数据库 |
| 对**已加载到页面的数据**做聚合 | 跑模型、跑复杂计算 |
| 切换主题、展开折叠 | 访问内部数据源（除非额外调 API） |

**关键限制**：HTML 里能交互的数据，**必须是生成这份 HTML 时就已经算好并嵌入进去了的**。用户看到的永远是「当时那批数据的不同切法」。

> 这带来一个隐蔽风险：业务方以为自己在「查最新数据」，实际上看的是一周前的快照的不同切角。**如果页面没有显著标注数据时间，这就是一种误导。**

## 4.4 脚本的交互：只有一次性参数

脚本没有运行时交互，它只有**启动前的一次性参数**：

```bash
python report.py --date 2026-09-30 --category electronics
```

| 优点 | 缺点 |
|---|---|
| 简单、确定、易调度、易审计 | 想换个参数就得重跑一次（可能很久） |

**折中**：脚本跑出结果 → 落成 HTML/看板给业务方做 L2 过滤——这是最常见的组合（第 8 章管线）。

## 4.5 ★ App 形态：HTML 的外壳 + Notebook 的内核

这是本章最值得记住的一点。像 `marimo run`、Streamlit、Hex app 这类形态，本质上是：

```
用户看到的：一个网页（和 HTML 一样好分发）
实际发生的：每次交互都触发后端真实计算（和 Notebook 一样能重算）
```

| | 纯 HTML 报告 | **App 形态（marimo run / Streamlit）** |
|---|---|---|
| 交互 | L2 过滤 | ★**L1 真重算** |
| 数据新鲜度 | 生成时的快照 | ★可实时查源 |
| 分发 | 一个链接 | 一个链接（同样好分发） |
| 维护 | 需重跑重发 | ★改代码即可，业务方自助 |
| 成本 | 静态托管极便宜 | 需要后端常驻 |

> ★**这是 Notebook 家族相对「纯 HTML」最大的反超点**：它保留了 HTML 的好分发，却拿到了真实重算能力。所以「用 Notebook 做 App」常常比「用 HTML 做报告」更接近业务方真正想要的东西——他们要的不是看，是**自己换个条件再看**。

## 4.6 交互能力的选型判据

```
业务方需要自己换条件看结果吗？
  │
  ├─ 不需要，只要看结论
  │     └→ 静态 HTML（最省，可 CDN、可离线保存）
  │
  ├─ 需要，但只是换角度（筛/排/缩放）
  │     └→ HTML + JS 图表库（ECharts/D3/Plotly）——前端搞定，零后端成本
  │
  └─ ★需要，且要基于新条件重新计算/查库
        └→ App 形态（marimo run / Streamlit / Hex app）
             代价：需要后端常驻 + 运维
```

**成本提示**：L1 需要后端常驻，这是实打实的成本。选型时要问：**「这个交互值不值得养一个后端？」** ——很多看板其实用 L2 就够了。

## 4.7 本章要点

- 交互三层级：**L1 触发真实重算 ／ L2 对已有数据前端过滤 ／ L0 无交互**。
- ★判据：**这个交互能不能算出数据里原本没有的东西？**
- Notebook 控件与 App 形态 = **L1**，能碰数据源，输出一致（响应式保证）。
- 纯 HTML = **L2**，能交互的数据必须是生成时已嵌入的；★**若页面不标注数据时间，就是在误导用户**。
- 脚本 = **只有启动前的一次性参数**（CLI），但简单确定易调度。
- ★**App 形态 = HTML 的外壳 + Notebook 的内核**，保留好分发又拿到真重算——这是 Notebook 家族对纯 HTML 的最大反超。
- 选型要问：**这个交互值不值得养一个后端？** 很多场景 L2 就够。
