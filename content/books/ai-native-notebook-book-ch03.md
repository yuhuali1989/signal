# 第 10 章 · 执行引擎与内核：有状态内核 vs 响应式 DAG

## 3.1 执行层为什么是最核心的一层

交互层决定"好不好看"，AI 层决定"聪不聪明"，但**执行层决定"结果可不可信"**。

一个残酷的事实：

> **约 96% 的公开 Jupyter notebook 无法原样复现。**

这个数字背后的主因不是算力、不是代码质量，而是 Notebook 的**执行模型本身**——具体来说就是下节的 hidden state。

## 3.2 Jupyter 的有状态内核模型

Jupyter 的执行模型是**有状态内核（stateful kernel）**：

- 启动一个长期存活的进程（kernel），所有 cell 在这个进程里执行
- 变量、导入、函数定义**常驻内存**，跨 cell 共享
- 用户**手动决定**执行哪个 cell、以什么顺序执行
- 技术底座：kernel 与前端通过消息协议通信（Jupyter 使用 ZeroMQ 的多通道：shell / iopub / stdin / control / heartbeat）

```text
前端 cell ──[执行请求]──→ kernel（长期进程，保存状态）
       ←──[输出 / 结果]──
```

**这个模型的好处**：极度自由。你可以跑第 7 格、改第 3 格、再跑第 5 格——探索时非常舒服，这也是 Jupyter 流行的原因。

## 3.3 Hidden state：自由的代价

自由执行顺序带来一个致命副作用——**隐藏状态（hidden state）**。

一个最小复现例子：

```python
# Cell 1
x = 10

# Cell 2
y = x * 2

# Cell 3（后来加的）
x = 100
```

| 执行顺序 | y 的值 |
|---|---|
| 1 → 2 → 3 | y = 20 |
| 3 → 2 → 1 | **y = 200** |
| 1 → 3 → 2 | **y = 200** |

**同一个 notebook 文件，执行顺序不同，结果完全不同。**

更隐蔽的情况：你删掉 Cell 3，但 kernel 内存里 `x` 仍然是 100——**文件里已经看不到 x=100 这行，但状态还在**。

**后果**：

- 打开的旧 notebook 缓存输出与"Restart & Run All"的结果不一致
- 分析报告交上去，别人跑不出来同样的数
- 这个问题自 2018 年起就被反复记录，出现过 papermill、nbdev、jupytext 等补救方案，但都是"外围修补"

## 3.4 响应式执行：把 notebook 变成数据流图

响应式 Notebook（以 Marimo 为代表）从**运行时层面**解决 hidden state。

**核心机制**：

```text
① 静态分析每个 cell：定义了哪些变量（def）、读取了哪些变量（ref）
② 构建有向无环图（DAG）：变量为边，cell 为节点
③ 运行某个 cell 或改了上游代码 / UI 输入
      → 自动重跑所有下游依赖 cell
④ 删除 cell 时，它定义的变量从状态里真正消失
```

**心智模型**：像电子表格 / 构建系统——改一个输入，依赖它的都重算。

```text
# marimo 的依赖关系（概念示意）
cell A: df = load_data()      ──→ 定义 df
cell B: df2 = df.filter(...)   ──→ 读 df，定义 df2
cell C: chart(df2)             ──→ 读 df2

改 cell A → cell B、C 自动重跑
```

**带来的保证**：

| 保证 | 说明 |
|---|---|
| **无隐藏状态** | 状态与文件一致，不存在"内存有但文件没有"的变量 |
| **确定性执行** | 执行顺序由依赖决定，不靠人记 |
| **删除真正生效** | 删除 cell 后其变量不再存在 |
| **纯文本格式** | notebook 就是 .py，Git diff 干净、可当脚本跑 |

## 3.5 两种执行模型对比

| 维度 | 有状态内核（Jupyter） | 响应式 DAG（Marimo 类） |
|---|---|---|
| 执行方式 | 手动、线性、允许乱序 | 依赖驱动、自动传播 |
| 隐藏状态 | **存在（96% 不可复现的主因）** | 消除 |
| 删除 cell | 变量可能残留 | 变量真正移除 |
| 心智模型 | 按顺序执行的脚本 | 电子表格 / 构建系统 |
| 自由探索 | ⭐ 极高（随便跑） | 稍受约束（要符合依赖） |
| 长耗时 cell | 可只跑一次、复用结果 | 上游一改下游全重跑（可用缓存缓解） |
| 文件格式 | .ipynb（JSON） | .py（纯文本） |
| 生态 | 极大 | 较新、较小 |

**公平地说**：响应式不是"全面更好"。如果你的场景是"每一步都要跑 10 分钟，只想手动挑着跑"，有状态内核反而更顺手——响应式会让你每次改上游都触发重跑（虽然有缓存机制可缓解）。

## 3.6 远程与分布式执行

Notebook 的执行不一定在本地：

| 模式 | 说明 |
|---|---|
| **本地 kernel** | 默认形态，简单直接 |
| **远程 kernel gateway** | 前端在本地，kernel 在远端服务器/集群（计算资源更弹性） |
| **连接计算引擎** | cell 里的代码被编译/下发到 Spark、DuckDB、数仓执行（Hex / Deepnote 的 SQL cell 即此思路） |
| **托管计算** | SaaS 平台提供预配置环境，免去环境运维 |

**架构提示**：SQL cell 看似简单，实际上决定了平台能否"把计算下推到数仓"——这对大数据场景是**架构级差异**（在分析型 notebook 里尤其关键）。

## 3.7 沙箱与安全

Notebook 会执行任意代码，因此执行层的安全设计不可省：

| 风险 | 对策 |
|---|---|
| 任意代码执行 | 容器/进程沙箱隔离，限制系统调用与网络 |
| 凭据泄露 | 密钥托管（不写在 cell 里）、细粒度数据连接权限 |
| 资源滥用 | CPU/内存/运行时长限额，超时终止 |
| Agent 执行风险 | 限制 agent 可执行的操作范围；marimo pair 的"提交前校验"本质上也是一种保护 |

**AI 时代的新增风险**：agent 会在 kernel 里执行代码——这意味着**安全边界从"用户手动执行"变成"AI 自动执行"**。因此执行层的沙箱、权限、审计变得比以往更重要（详见第 4 章）。

## 3.8 多语言内核

| 场景 | 支持 |
|---|---|
| Jupyter | **100+ 内核**（Python、R、Julia、Scala、SQL…），生态最广 |
| Marimo | Python 为主 |
| Pluto.jl | Julia |
| Observable | JS / D3 |
| Hex / Deepnote | Python + SQL（原生），R（部分支持） |

**选型含义**：如果你的工作**必须跨多种语言**（如 R + Python 混用），Jupyter 生态几乎是唯一现实选择；响应式工具目前主要覆盖单一语言。

## 3.9 本章小结

- **执行层决定结果可不可信**；约 **96% 的公开 Jupyter notebook 不可复现**，主因是执行模型。
- **有状态内核**：自由但存在 hidden state——执行顺序不同结果不同，删除 cell 变量仍残留。
- **响应式 DAG**：依赖驱动、自动传播、删除真正生效、纯文本格式；心智模型像电子表格。
- **响应式不是全面更好**：长耗时、想手动挑着跑的场景，有状态内核更顺手。
- 远程执行与 SQL 下推是大数据场景的架构级能力。
- **AI 让执行风险升级**：从"用户手动执行"变成"AI 自动执行"，沙箱与权限更重要。
- 多语言需求强 → Jupyter 生态优势明显。
